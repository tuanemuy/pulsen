# ADR: 判定結果に skipped を導入し、判定コマンドのプロトコルでのみ表現する

## ステータス

承認済み

## コンテキスト

PRレビュー監視のような「チェック → なければ待機 → あれば処理」のポーリング型ワークフローを表現する手段がなかった。判定の分類は completed / failed の2値であり、チェックが「やることがなかった」場合に、completed では無条件に次ステータスへ遷移してしまい、failed では attempt_count が蓄積して正常な待機が凍結(stopped)に至る。

ポーリングをツールの外(cron + `add`)へ出す案は、重複排除がツールの責務外(§2)であるため、処理中に次のチェックが発火すると同一対象へのタスクが多重登録され、1タスク = 1worktree による直列化が失われる。ワークフロー内のループとして表現する必要がある。

## 前提

- tick は冪等で、判定は「running かつ exitファイルあり」の条件から毎回再導出される
- エスカレーションは stopped への到達と通知に一本化されている(§8、`.adr/2026-08-10-permanent-failure-escalates-to-stopped.md`)
- 判定コマンドは利用者が意図的に書くスクリプトであり、exit code の意味を自分で管理できる

## 決定

判定の分類を completed / failed / **skipped** の3値にする。skipped は「実行したが、やることがなかった(現状維持)」を表す。

- skipped の挙動: タスクステータスは変更せず、実行状態を pending に書き戻す。attempt_count は消費せず、通知も行わない。次の tick が同じステータスの実行を新しい attempt で起動する(再実行の周期は tick 間隔に律速される)
- skipped は7つ目の実行状態ではなく、判定の分類結果である。実行状態は6値のまま変わらない
- エンコーディングは**判定コマンドの exit code プロトコルの拡張のみ**とする: 0 = completed、10 = failed、**20 = skipped**、それ以外 = 判定失敗
- デフォルト判定(エージェントの exit code)は 0 = completed、非0 = failed の2値のまま。エージェントの exit code に skipped 用のコードをグローバルに予約しない

グローバル予約をしない理由: エージェントが偶然その exit code で異常終了すると failed ではなく skipped に分類され、attempt_count を消費しないまま tick ごとに永遠に再実行され続ける。stopped に到達しないため通知も発生せず、エスカレーションの一本化(§8)が静かに壊れる。判定コマンドは利用者が意図的に書くため、この偶発衝突が起きない。

## 検討した代替案

- エージェントの exit code にグローバル予約(例: 常に 20 = skipped) — 上記の偶発衝突により「カウンタを消費しない無限スピン」の故障モードを作るため不採用
- 汎用の条件分岐(`next` を exit code でマッピング) — 状態機械が一本道でなくなる大きな拡張。ポーリング型は「next へ進む / 現状維持」の2択で必要十分であり、skipped は将来の分岐拡張とも競合しないため、最小の拡張を採る
- ポーリングをツール外(cron + `add`)に置く — コンテキストに記載のとおり、多重登録と直列化の喪失により不成立
- 「何もしない」ステータスでの滞留 — 進行が人間の set-status 頼みになり、自動ポーリングにならない

## 影響

- ポーリング型ワークフローは「判定コマンドを持つステータスの循環」(`.adr/2026-08-11-workflow-cycles-allowed.md`)として表現できる
- skipped を使うステータスには判定コマンドの定義が必須になる(エージェントの exit code を判定プロトコルへ写像するスクリプトを書く)
- skipped の周回ごとに新しい attempt = runディレクトリが生まれるため、gc が実用上必須になる(`.adr/2026-08-11-run-dir-gc-in-scope.md`)
- カウンタのリセット規則(`.adr/2026-08-11-counters-track-consecutive-failures.md`)が skipped の成立の前提になる
