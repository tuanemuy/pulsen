# ADR: tick の分岐は判断を値（`Branch`）にしてからタスクを手続きへ渡す

## ステータス

承認済み

## コンテキスト

tick は走査した各タスクを実行状態（および待機ステータスでは動作種別）で分岐させ、それぞれの手続きへ渡す。素直に `match task.execution() { ... }` と書くと、アームの中でタスクを消費する手続き（`launch` / `confirm_spawn` はいずれも `self` を消費する遷移関数を呼ぶ）へ渡せない — 走査対象の借用が `match` 全体で生きるためである。

## 決定

判断だけを所有する値に落としてから分岐する。`Branch`（`Launch { input }` / `Wait` / `Cleanup` / `ConfirmSpawn { recorded_at }` / `Observe` / `Advance` / `Notify`）を private な列挙として定義し、`branch_of(&task) -> Branch` が実行状態と動作種別の網羅 `match` を1箇所で担う。手続きは判断済みの付随データ（エージェント入力・猶予の起点）を引数で受け取る。

これにより、手続きの中に「ここには来ないはずの実行状態」のアームが現れない。残る `expect` は起動手続きの2箇所（確定済みワークスペースの取り出し・エージェント実行ステータスのリトライ上限）だけで、どちらも分岐が構成として保証する不変条件であり、CLAUDE.md の「パニックは不変条件違反にのみ使う」に収まる。

未配線のアームには「そのアームを埋めるスライス」を why コメントとして残し、ダミーの処理もエラー報告も置かない。

## 検討した代替案

- **手続き側で実行状態を再度 `match` する** — 同じ場合分けが2箇所に分かれ、どちらかにアームを足し忘れても網羅検査が通る
- **`clone()` して渡す** — タスクは走査で全件をメモリに載せる値であり、分岐のためだけに複製する理由がない

## 影響

- 未配線のアームが1箇所に並び、後続スライスの作業が「アームを1つ書き換える」に閉じる
- 手続き側が実行状態を見ないので、前提の再検査はドメインの遷移関数だけが持つ
- トレードオフ: 分岐の付随データ（`AgentInput`）を1回複製する。ステータス定義から取り出す小さな値であり、起動経路でしか通らない
