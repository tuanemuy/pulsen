# 012: ツール操作の失敗は実行状態 failed として観測させる

## ステータス

承認済み

## コンテキスト

worktree作成・削除、アーカイブ移動といったツール操作の失敗は「failed相当として attempt_count を消費し、次のtickで再試行する」と確定済み(requirements §5・§9.1)だが、失敗から再試行までの間、タスクが `ls --state` でどの実行状態として観測されるか(pending 維持か failed 化か)が未確定だった。

## 前提

- 実行状態は6値固定(pending / launching / running / completed / failed / stopped)で、ユーザー定義不可(requirements §6)
- failed の次のtickの行動は「リトライする」であり、pending と同じく「現在のタスクステータスの定義に従って起動(または終端処理)を試みる」に帰着する(requirements §6.4)
- 利用者は「注意が必要なタスク(失敗・凍結・滞留)を素早く見つける」ために `ls` の実行状態を手がかりにする(monitoring.md)

## 決定

ツール操作(worktree作成・削除、アーカイブ移動)の失敗時は、attempt_count の加算と同時に**実行状態を failed に書き換える**。直近の失敗要因(requirements §9)も同時に記録する。上限超過なら failed を経由せず stopped とする。

- failed の意味は「直前の試行(エージェント実行またはツール操作)が失敗と確定した」と定義する。エージェント実行の失敗とツール操作の失敗を実行状態のレベルでは区別せず、区別は直近の失敗要因の記録で行う
- 次のtickは failed のタスクを pending と同様に扱い、現在のタスクステータスの定義に従って再試行する(エージェント実行ステータスなら worktree 確認 → 起動、クリーンアップステータスなら終端処理)

## 検討した代替案

- pending 維持(attempt_count と失敗要因だけ記録) — `ls --state failed` でリトライ中の問題タスクを発見できず、「実行待ち」と「失敗して再試行待ち」が観測上区別できない。attempt_count > 0 なのに pending という表示は monitoring.md の「実行状態を手がかりに読む」流れと噛み合わないため不採用
- ツール操作失敗専用の実行状態を追加 — 実行状態の6値固定(requirements §6)に反する拡張であり、次のtickの行動が failed と同一である以上、状態を分ける意味がないため不採用

## 影響

- tick の遷移ロジックで pending と failed は「起動(再試行)対象」として同じ分岐に合流し、分岐の追加が不要になる
- `ls --state failed` が「エージェント実行の失敗」と「ツール操作の失敗」の両方を拾う。内訳は `show` の直近の失敗要因で判別する
- クリーンアップステータスの再試行待ち(worktree削除・アーカイブ移動の失敗後)も failed として観測される
