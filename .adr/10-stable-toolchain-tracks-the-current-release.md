# ADR: 安定版のツールチェーンは固定せず、常に現行の stable を使う

## ステータス

承認済み

## コンテキスト

CI で stable をどう指すかに選択肢がある。

1. ランナーイメージ同梱の stable をそのまま使う — イメージの更新タイミングで版が動く。どの版だったかがログを見ないと分からない
2. **`rustup update stable` で現行の stable にする** — 常に最新の安定版で検証する。新しい clippy lint が追加された日に、コードを1行も変えていないのに CI が赤くなりうる
3. `1.97.0` のように固定する — 再現性は最高だが、CLAUDE.md の「安定版ツールチェーンを前提とし、`cargo clippy` を通る状態を保つ」が意味するのは「現行の安定版」であり、固定すると新しい lint に追随しない状態が静かに続く。それは CI の導入が壊しにいった「1環境でしか回っていない」構造の再生産でもある

## 決定

`rustup update stable --no-self-update` で現行の stable に上げてから回す。版は固定しない。新しい lint で赤くなったら lint を直す。`allow` での握り潰しやツールチェーンの固定は取らない。

この決定は **fmt ジョブにも等しく掛かる**。rustfmt は版によって整形結果が変わるため、clippy が新 stable・rustfmt がイメージ同梱の旧 stable という状態だと、「CI は緑だが開発者が新 stable で `cargo fmt` すると差分が出る」というズレが CI に映らない。fmt ジョブも `rustup update stable` を踏み、使った版(`rustc --version` / `cargo fmt --version`)をログに残す。この構成では **fmt ジョブが版差で赤になることが起こりうる**(ローカルは nixpkgs の rustc)。その場合の解消は clippy と同じく「現行 stable に合わせる」で、CI と同じ版の rustfmt で `cargo fmt --all` を掛け直して差分をコミットする。`rustfmt.toml` に整形を抑止する設定を足すことも、rustfmt の版を固定することもしない。

## 影響

- 「安定版で通る」という宣言が、宣言した時点の版ではなく常に現時点の版について成り立つ。整形についても同じ版で成り立つ
- トレードオフ: 無関係な PR が新 stable のリリース直後に赤くなることがある。原因が自分の変更でないと分かる形(clippy の lint 名がログに出る)なので、切り分けのコストは低い
- トレードオフ: 過去の実行を厳密に再現できない。再現が必要になる場面(退行の二分探索など)では、そのとき明示的に版を指定して手元で回す
