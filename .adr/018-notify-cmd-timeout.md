# 018: notify_cmd に組み込み60秒のtimeoutを適用する

## ステータス

承認済み

## コンテキスト

requirements §8 は notify_cmd の実行を定めるが timeout を規定していなかった。通知は stopped 確定処理の一部として tick / abort が排他ロックを保持したまま同期実行するため、応答しない notify_cmd が1つあるだけで、以後のすべての tick と状態変更CLIが恒久的に停止する。

## 前提

- 通知は at-least-once であり、失敗(`notified_at` 未記録)は次のtickが自動再試行する(requirements §8)
- config.yaml のキーは requirements が「グローバル設定」と明記するものに限定している(ADR-014)

## 決定

notify_cmd の実行に**組み込み定数 60秒**のtimeoutを必ず適用する。超過は起動不能・非0終了と同じく通知失敗として扱い、`notified_at` を書かずに終える(次のtickが再通知する)。config.yaml のキーは設けない。

## 検討した代替案

- timeoutなし(現状の requirements の素直な読み) — ハングした通知コマンド1つが排他ロックごと全機能を止める。通知の欠落を許さない設計(§8)が「通知でツール全体が死ぬ」故障モードと引き換えになるため不採用
- グローバル設定キー(`notify_timeout`)の新設 — ADR-014 の「config キーは requirements 明記のものに限る」に反する。通知コマンドは即応する軽量なもの(デスクトップ通知・チャット投稿)が想定であり、60秒で足りないケースは通知コマンド側の非同期化(キューに書いて即 exit する等)で解決するのが筋のため不採用

## 影響

- 正当に60秒を超える通知コマンドは毎回失敗し、tickごとに重複通知が発生し続ける(at-least-once の許容範囲だが、利用者には故障として見える)。長時間かかる通知はコマンド側で非同期化する
- requirements §8 にこの規定を反映する(仕様の正本とドメイン設計の乖離を残さない)
