# ADR: runディレクトリのgcを保持期間設定としてスコープに含める

## ステータス

承認済み

## コンテキスト

runディレクトリの肥大化対応は「明示的なgc操作または保持期間のグローバル設定として別途提供する」(将来機能)としていた。skipped(`.adr/2026-08-11-skipped-judgement-outcome.md`)と循環(`.adr/2026-08-11-workflow-cycles-allowed.md`)により常駐ポーリングタスクが正当な使い方になると、1周ごとに新しい attempt = runディレクトリが生まれ、tick 間隔1分なら1タスクで1日数百ディレクトリが蓄積する。「将来別途」の前提が崩れ、gc は実用上ほぼ必須の機能になった。

## 前提

- runディレクトリは凍結・過去タスクの調査材料であり、無差別な削除は調査可能性を壊す(§9.2)
- tick は排他ロック下で状態を扱う唯一の定期実行点であり、外部スケジューラーが周期性を担っている

## 決定

保持期間のグローバル設定(`run_retention`)によるgcをスコープに含める。

- `run_retention` を設定した場合のみ、tick が各パスで保持期間を超えた attempt のrunディレクトリを削除する。**未設定なら gc は行われない**(明示オプトイン。既存運用のログを黙って消さない)
- attempt の経過時間は、ディレクトリ内ファイルの最終更新時刻の最大値で判定する(ファイルが1つもない場合はディレクトリ自体の最終更新時刻)
- 保護規則: (a) 現役タスク(`state/tasks/`)のタスクファイルが現在参照している attempt、(b) stopped タスクの全 attempt は、期間によらず削除しない(調査材料の保護)。アーカイブ済みタスク・タスクファイルが存在しない孤児のrunディレクトリは保護しない。パース不能なタスクファイルが存在するタスクIDのrunディレクトリは、保護規則を判定できないため全 attempt を保護する(読めない帳簿に対して何もしない原則と同じ)
- 削除失敗は当該 attempt をスキップして報告し、次の tick が再試行する。gc の失敗はどのタスクのカウンタも消費せず、stopped を発生させない(タスクの帳簿と無関係な掃除であるため)
- attempt がすべて削除され空になった `state/runs/<task-id>/` も削除する

## 検討した代替案

- 将来機能のまま先送り — 常駐ポーリングの導入(`.adr/2026-08-11-skipped-judgement-outcome.md`)と同時に実用上破綻するため不採用
- skipped だった attempt のrunディレクトリのみ即時削除 — 「ポーリングの不具合を調査したいときに限ってログが消えている」事故を作る。保持期間による一律の規則のほうが予測可能
- 明示的な gc コマンドの追加 — 周期性は外部スケジューラーが既に担っており、tick への統合なら書き込み経路と排他ロックが一元化される。コマンド面の拡大に見合う利点がない
- デフォルトで gc 有効 — 設定を知らない利用者のログを黙って削除するため不採用

## 影響

- 常駐ポーリング運用では `run_retention` の設定が推奨になる(セットアップ・シナリオに記載)
- 長期運用後に初めて設定すると、次の tick で大量の attempt が一括削除対象になる(設定時の注意点としてシナリオに記載)
- gc 済みのrunディレクトリへの参照は `show` が「存在しない」と明示する(既存挙動のまま)
- アーカイブ済み**タスクファイル**(`state/archive/`)の整理は本決定の対象外であり、引き続き将来機能とする
