# 055: 適合スイートの適用側は「スキップを許容するケースの集合」を環境の能力から宣言する

## ステータス

承認済み

## コンテキスト

適合スイートのフックは既定実装が `None` を返し、そのケースはスキップされる（ADR-027）。スキップは標準出力に報告するが、libtest は成功したテストの標準出力を握り潰すため（stderr も同様に捕捉するので `eprintln!` にしても変わらない）、「125件 PASS」の意味が環境で静かに変わる。権限操作を持たないプラットフォームでは8件が素通りし、その差が出力に現れない。

一方、権限操作を伴うフックは「制限が実際に効いたことを確認してから `Some` を返す」（ADR-027）。`chmod` は root では効かないため、**root 実行の unix でもこの8件はスキップになる**。プラットフォーム（`cfg(unix)`）で許容件数を決めると、この環境ではスキップが失敗に変わり、「環境が前提を作れない行はスキップして理由を残す」という運用と正面から食い違う。

件数だけの宣言にも穴がある。想定した行が走った代わりに別の行がフックを得られずスキップしても、合計が宣言以内なら緑のまま通る。後続スライスが in-memory 実装に同じスイートを適用する場面では、宣言と実態のズレが集計で相殺される。

## 決定

スイートを適用するテストファイルは、**スキップを許容するケースの集合**を宣言する（`SkipBudget`）。

- 集合の外のスキップは、そのケース自身の失敗にする。どのケースが想定外に走らなかったかがテスト名で分かる
- 集合の中のスキップも `SKIP` 行として必ず出力する。走らなかった行は `cargo test -- --nocapture` で理由まで辿れる
- 宣言の要素はケース名の接頭辞となる TC ID（`tc_port_config_store_023`）。ケース関数は `<TC ID>_<仕様の言葉>` で名付けるため、説明部分を言い換えても宣言は腐らない
- 集合は**プラットフォームではなく環境の能力**から実行時に決める。権限制限が実際に効くか（一時ファイルを `chmod 000` して読めるか）を1度だけ調べる `permission_restrictions_effective` を用意し、効かない環境では区分 C のケース名を集合に入れ、効く環境では空集合にする

宣言は最初のケースが走るときに1度だけ評価する（`LazyLock`）。定数だと環境を調べる式を書けない。

## 検討した代替案

- 許容件数を `cfg(unix)` で分ける — root 実行が8件の失敗になる。`SkipBudget::new` が `const fn` である限り、利用者はテストのソースを書き換えないと回避できない
- スキップを常に失敗にする — 「時刻を過去に設定できる環境に限る」（TC-port-clock-005）のように、どの環境でも前提を作れない行が残る
- 報告を `eprintln!` にする — libtest は stderr も捕捉するため何も変わらない

## 影響

- 環境が変わって走る行が減れば、その差がテストの失敗として現れる。どの行がどの条件で走らないかが、宣言と probe の形でテストファイルに残る
- root 実行・Windows・権限を持たないファイルシステムでは、区分 C の行がスキップとして記録される。plan.md の「権限操作でしか再現できない行は root では skip する」と ADR-027 の運用がそのまま成立する
- 同じ probe を受け入れテスト側のスキップ集計にも使えるため、適合スイートと CLI テストで root への態度が割れない
- トレードオフ: 宣言が「件数」より長くなる。区分 C の行を足すたびに、その行を宣言に加える必要がある
