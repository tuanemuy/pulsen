# 017: ドメイン境界を definition / task / execution の3つに切る

## ステータス

承認済み

## コンテキスト

Phase 3(技術設計)の開始にあたり、ヘキサゴナルアーキテクチャの中心に置くドメインの分割単位を決める必要がある。関心事は大きく「ユーザーが書く定義の解析・検証」「タスク帳簿の状態と遷移」「実行の観測・分類・判定」の3系統があり、これを1ドメインに混ぜるか、どの粒度で分けるかは非自明である。

## 前提

- ドメイン層は外部クレート・I/Oに依存せず、判断(純粋関数)と副作用の実行を分離する(CLAUDE.md)
- tick は永続化された事実から常に同じ判断を再導出できる(冪等性)
- ワークフロー定義はタスク登録時にスナップショットされ、タスクの一部になる(requirements §7.1、ADR-015)

## 決定

ドメインを次の3つに分割する。依存方向は task → definition、execution → task / definition の一方向のみとする。

- **definition**: ユーザーが記述する定義(グローバル設定・ワークフロー定義)の構造・検証・コマンドテンプレート展開。値オブジェクト中心のドメインで、可変状態を持たない
- **task**: タスク集約。タスクステータス・実行状態・カウンタ・スナップショットからなる帳簿と、その遷移ロジック(純粋関数)。システムで唯一の永続化される可変状態
- **execution**: 実行の観測と判断。runディレクトリの語彙、launching / running の分類、判定プロトコル、gcの保護規則。観測された事実を入力に取り決定を返す純粋なサービス群と、外界(プロセス・worktree・コマンド実行)のポート

分割の根拠:

- 変更理由が異なる: definition はYAMLスキーマの拡張で、task は状態機械の変更で、execution は観測・分類規則の変更で変わる
- ライフサイクルが異なる: definition の値は登録時に一度だけ検証されて不変になる。task は tick / CLI のたびに遷移する。execution は状態を持たず毎tick再導出される
- テスト境界が明確になる: 遷移ロジック(task)と分類ロジック(execution)は、ファイルシステム・プロセスなしの純粋なユニットテストで網羅できる

## 検討した代替案

- 単一ドメイン(scheduling) — 型は少ないが、YAMLパースの語彙と状態機械の語彙と観測の語彙が1ファイルに混ざり、変更理由の異なるものが同居する。想定規模でも定義・遷移・観測はそれぞれ十分な厚みがあるため不採用
- definition をさらに config / workflow に分割 — ワークフロー検証は「定義とグローバル設定の突き合わせ」(参照エージェントの存在・skill_input・プレースホルダ値の供給)であり、両者は登録時検証で常に一緒に使われる。分けると相互参照だけのドメイン境界になるため不採用
- execution を task に併合 — 分類(観測事実 → 判断)と遷移(判断 → 新しい状態)は入力が異なる別の純粋関数群であり、併合すると task がプロセス観測の語彙(pid・starttime・猶予時間)を抱え込む。ポートの大半(プロセス・worktree・コマンド実行)が execution 側の関心であることからも分離が自然なため不採用

## 影響

- ポートの帰属が決まる: definition = ConfigStore / WorkflowStore、task = TaskRepository / TaskIdGenerator / Clock、execution = RunStore / ProcessController / WorktreeManager / CommandRunner / ExclusiveLock
- アプリケーション層(tick・CLIユースケース)は「execution で分類 → task で遷移 → ポートで実行」の一方向の流れとして書ける
- ドメイン間に循環はなく、definition は他ドメインを知らない
