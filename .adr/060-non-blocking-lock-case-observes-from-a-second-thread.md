# 060: 「待たずに返る」ロックのケースは別スレッドで試み、そのケースだけ `Lock: Sync` を要求する

## ステータス

承認済み

## コンテキスト

TC-port-exclusive-lock-003 は「別プロセスが保持している間の `try_acquire` が、解放を待たずに返る」ことを主張する。経過時間の判定を取得と同じスレッドで行うと、解放を待つ実装では `try_acquire` が返るまで判定に到達しない。保持の解放はさらに後にあるため、両者が互いを待ってケースはハングする — 宣言したアサーションでは、ケースが名指しする失敗モードを検出できない。

取得を別スレッドに置くには、ロックへの共有参照をスレッドへ渡すため `Lock: Sync` が要る。ADR-027 は TC-port-task-repository-042 / 044 で同じ制約に当たったとき、スキップ可能なフック（`concurrent_repo`）に `Sync` を隔離した。

## 決定

TC-003 は取得の試行を `thread::scope` の子スレッドで走らせ、親が期限まで完了を監視する。期限を超えたら**先に `release_holder` して試行を返らせ**、「待った」ことを失敗として報告する。

`Sync` の要求はこのケース関数の `where` 境界（`Harness::Lock: Sync`）に閉じ、ハーネストレイトには課さない。ガードは子スレッドの中で落とし、結果だけを値としてスレッド境界を越えさせる（`LockGuard` は `Send` を要求しない）。

TC-042 / TC-044 と違い、スキップ可能なフックにはしない。フックにすると、この行は「待つ実装」に対して失敗ではなくスキップになり、検出したい失敗モードがそのまま素通りする。

## 検討した代替案

- 保持の解放を別スレッドに置き、取得は本体スレッドで測る — ハーネスと保持ハンドルの双方に `Send` / `Sync` が要り、要求が広がる
- `hold_from_other_process` と対で `concurrent_lock` フックを足す — 待つ実装でケースがスキップに落ち、この行の存在意義が消える

## 影響

- 待つ実装に対してケースがハングではなく失敗として現れる。期限超過時も保持を解放してから合流するため、テスト実行が止まらない
- トレードオフ: ExclusiveLock の適合スイートを適用する実装には `Sync` が要る。満たさない実装は境界エラーとして即座に分かる（黙ってスキップにはならない）
