# ADR: 内容へ到達できないエントリは検索でも破損として扱い、作成では使用済みとみなす

## ステータス

承認済み

## コンテキスト

タスクファイルの読み取りで `fs::read` が `NotFound` を返す状況は2つある。「その領域にもうエントリが無い」（`archive` による移動を含む）と、「エントリは残っているのに内容へ到達できない」（実体を失ったシンボリックリンク、手動修復の中途など）である。

走査（`list_active` / `list_archived`）は `symlink_metadata` で両者を分け、後者を `TaskEntry::Corrupt` として報告する。一方 `find` は `fs::read` の `NotFound` だけを見て `TaskLookup::NotFound` に写していたため、同じ1つのファイルを `ls` は「読めない」と報告し `show` / `abort` / `retry` は「存在しない」と答える状態になっていた。

`create` の存在確認も `try_exists`（リンクを辿る）だったため、同じエントリを「使われていない ID」とみなして上書きしうる。上書きは修復材料を消す。

spec/domains/task.md は `TaskLookup::Corrupt` を「ファイル全体が読めない」と定義し、spec/testcases/ports/task-repository.md の `list_active` 行は「`find` と同じ区分で列挙される」と定める。

## 決定

「エントリの有無」を消失と到達不能を分ける唯一の述語とし、`find` と走査の双方が同じ判定を通る。

- 内容へ到達できないエントリは `find` では `TaskLookup::Corrupt { path, message }`、走査では `TaskEntry::Corrupt { path, message }`。区分は問い合わせ方によって変わらない
- `create` の存在確認はリンクを辿らず、エントリが残っていれば `Conflict` を返す。デコードの可否も到達の可否も問わないのは、読めないファイルも「その ID は使われている」ことの証拠だから
- 領域にエントリが無い場合だけ「無い」と答える（`find` は `NotFound`、走査は結果から落とす）。`archive` の中間状態を失敗として観測させない契約はこの枝が担う
- 書き込み系（`save` / `archive`）の存在確認はリンクを辿る判定のままとし、到達できないエントリを `NotFound` として拒む。破損への書き込みは呼び出し側が禁じられている操作であり、リンクの先を書き換えないことを優先する

## 検討した代替案

- **走査を `find` に合わせる**（到達できないエントリを黙って落とす） — 修復の入口が消える。`ls` に現れないファイルは利用者から見て存在しないのと同じで、requirements §9 が前提とする手動修復に辿り着けない
- **専用の区分を足す**（`Unreachable` 等） — `TaskLookup` / `TaskEntry` は spec が値を列挙しており、増やすとポート表との1対1が崩れる。「ファイル全体が読めない」の定義がこの状況をすでに含む

## 影響

- `find` / 走査 / `create` の3経路が同じ述語を共有し、後続スライスの `ls` / `show` / `abort` / `retry` が同じ ID について食い違う答えを返さない
- トレードオフ: 到達できないエントリが残っている限り、その ID での `create` は `Conflict` を返し続ける。ID は再発行できるため実害は無く、黙って上書きするより修復可能性を優先する
- 適合スイートのフック集合では到達できないエントリを作れない（フックは内容の文字列を受け取る形）。この状況の固定はアダプター側のユニットテスト（unix 限定）が受け持ち、適合スイートは TC-port-task-repository-029 で「`find` と走査は同じ区分」という一般の契約を見る
