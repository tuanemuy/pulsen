# ADR: テンプレート展開失敗は launching 記録前の同期spawn失敗として処理する

## ステータス

承認済み

## コンテキスト

登録後の config.yaml 編集で混入したテンプレート不備(エージェント名の解決失敗・未知プレースホルダ・`skill_input` 欠落・`{model}` への値なし等)は、tick が起動時に同期検出し spawn失敗として分類する契約(requirements §10)が確定済みだった。しかし手続きの詳細 — spawn_fail_count の加算、失敗要因の記録、無効化マーカーの要否、§4.1 の猶予時間経路との関係 — が未確定だった。猶予経路への委譲では、観測する側のtickが展開エラーの内容を知らず失敗要因を記録できない。

## 前提

- テンプレート展開はデタッチ起動の前提であり、tick 自身が同期的に行う(ラッパーに渡すコマンドラインを構成するため)
- attempt番号は launching 記録のたびに採番され、runディレクトリのパスに含まれる(requirements §4.1)
- 無効化マーカーは「spawn した(かもしれない)ラッパーの遅延起動を排除する」ための機構である

## 決定

tick は pending / failed のタスクを起動する際、**launching 記録の前に**テンプレート展開(エージェント定義の解決とプレースホルダ展開)を行う。展開に失敗した場合は次の同期手続きで処理し、§4.1 の猶予時間経路と並ぶ**同期spawn失敗経路**とする。

1. spawn_fail_count を加算する
2. 直近の失敗要因(requirements §9)に展開エラーの内容を記録する
3. 実行状態は変更しない(pending のまま / failed なら failed のまま。launching 記録を行わないため、attempt番号の採番・runディレクトリの作成も起きない)
4. 加算後に上限(グローバル設定、デフォルト3)を超過していれば stopped とする(確定時に通知する)

無効化マーカーは不要である(何も spawn しておらず、排除すべき遅延起動が存在しない)。attempt_count は消費しない(spawn失敗系の失敗であり、猶予経路と同じく spawn_fail_count のみが数える)。

worktree が未作成の場合の順序は「worktree作成 → テンプレート展開 → launching 記録 → spawn」とする({workspace} の展開に worktree パスが要るため)。worktree作成の成功後に展開が失敗した場合、worktree は作成済みのまま残り、次のtickは作成をスキップして展開から再試行する。

## 検討した代替案

- launching を記録してから失敗させ、猶予時間経路に合流させる — 観測する側のtick(30秒後)は展開エラーの内容を知らないため失敗要因を記録できず、原因調査(monitoring.md)が「pid が現れなかった」以上の情報を失う。また何も spawn していないのに猶予時間ぶん検出が遅れるため不採用
- 展開失敗を failed(attempt_count 消費)として分類する — 設定起因の失敗はエージェントの再実行で解決せず、spawn失敗の恒久化として spawn_fail_count で数える既存の分類(requirements §4.1・task-execution.md)と矛盾するため不採用

## 影響

- 同期経路で凍結したタスクは、runディレクトリに痕跡がない(attempt が採番されない)。原因は `show` の直近の失敗要因で確認する(猶予経路との判別材料にもなる)
- spawn_fail_count は「同期検出(展開失敗)」と「非同期検出(猶予時間超過)」の2経路から加算され、起動確認(running への遷移)でリセットされる
- 展開は起動のたびに行われるため、config.yaml の修正は次のtickから即座に反映される(グローバル設定はスナップショットされない原則と一致)
