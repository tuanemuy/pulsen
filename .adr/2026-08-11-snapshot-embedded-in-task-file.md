# ADR: ワークフロー定義のスナップショットはタスクファイルに埋め込む

## ステータス

承認済み

## コンテキスト

タスク登録時のワークフロー定義スナップショット(requirements §7.1)の保存形態として、タスクファイルへの埋め込みと `state/tasks/` 配下の隣接ファイルの2案があり、確定がドメイン設計に委ねられていた。隣接ファイル案を採る場合は、アーカイブ移動のアトミック性(cleanup.md「中途半端な状態が観測されない」)を複数ファイルの移動でどう成立させるかを併せて解く必要があった。

## 前提

- タスクファイルの更新とアーカイブ移動はアトミック置換・アトミックな移動で行い、中途半端な状態が観測されてはならない(requirements §9・cleanup.md)
- スナップショットはタスクファイルと同じ寿命を持ち、アーカイブ時はともに `state/archive/` へ移動する(requirements §7.1)
- タスクファイルは人間可読で、直接の閲覧・修復が可能(requirements §9)

## 決定

スナップショットは**タスクファイル(`state/tasks/<task-id>.json`)の1フィールドとして埋め込む**。保存するのは元YAMLの生テキストではなく、登録時検証を通過した後の**正規化された構造**(デフォルト適用前の、検証済み定義の構造化表現)とする。

- アーカイブ移動は単一ファイルの rename に帰着し、アトミック性が自明に成立する
- 「タスクとその定義」が常に1ファイルで完結し、寿命の一致が構造的に保証される
- `show` が表示する「スナップショットの保存先パス」はタスクファイル自体のパスとなる

## 検討した代替案

- 隣接ファイル(`state/tasks/<task-id>.workflow.yaml` 等) — アーカイブ移動が2ファイルになり、順序付け・途中クラッシュ時の中間状態(片方だけ移動済み)の扱い・冪等な再開手順という追加の設計が必要になる。タスクファイルを開けば定義も見える埋め込みに対し、可読性の利点も薄いため不採用
- 元YAMLテキストのまま埋め込み — 実行時に再パースが必要になり、「登録時に一度だけ検証する」(parse, don't validate)が壊れる。スナップショット済みタスクが実行時にパースエラーを起こす経路を作らないため不採用

## 影響

- タスクファイルの読み込みだけで tick の判断に必要な定義が揃い、実行時のファイル解決が発生しない
- タスクファイルはワークフロー定義の分だけ大きくなるが、更新はアトミック置換で全体を書き直すため処理は変わらない
- pages の縮退状態「スナップショット不在・パース不能」は、埋め込みフィールドの欠落・不正(手動修復の失敗等)として引き続き成立する(タスクファイル自体は読めるがスナップショットフィールドが壊れているケース)
