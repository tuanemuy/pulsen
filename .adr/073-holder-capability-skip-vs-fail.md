# 073: ロック保持フィクスチャの能力は probe で1度だけ判定し、スキップの宣言だけで次の一手が定まるものだけを許容集合に入れる

## ステータス

承認済み

## コンテキスト

適合スイートを適用するテストファイルは、スキップを許容するケースの集合を環境の能力から実行時に宣言する(ADR-055)。ロックの排他を検証するケース(適合4件と受け入れ1件)は、別プロセスに実際にロックを保持させるフィクスチャ(ADR-032)に依存し、その起動関数が `None` を返したときにスキップへ落ちる。

その `None` には性質の違うものが潰れていた。「保持プロセスの実行ファイルが無い」と「起動した保持プロセスの合図が期限内に返らない」が同じ値になり、許容集合は前者だけを見ていた。結果として向きが両方とも逆になる。

- **環境の遅さが実装の失敗として現れる。** 合図が期限内に返らない環境では、宣言の外のスキップとして `SkipBudget` が5件を落とす
- **ビルド構成の誤りが静かな緑になる。** 単一のテストターゲットを指定した実行では example がビルドされず、実行ファイルの不在が宣言済みのスキップとして通る

期限を延ばす対処はこの2つを区別しない。`cfg(windows)` の決め打ちは、成立するかどうかが環境の能力の問題であって OS の問題ではないという理由で ADR-071 が既に却下している。

区別を作ると、能力は4つに分かれる — 起動して合図が返る / 起動はできるが合図が期限内に返らない / 実行ファイルが無い / 実行ファイルはあるが起動できない。このうち最後の1つ(ウイルス対策による隔離・`noexec` マウント・実行形式の不一致)は「ビルド構成の誤りだから失敗」という理由では振り分けられない。実行の仕方の誤りではなく、テスト側では手の打ちようがない環境の性質であり、その点で合図のタイムアウトと同じ顔をしている。どちらへ倒すかを決められる基準そのものが要る。

## 決定

**能力側と失敗側を分ける基準 — 許容集合に入れてよいのは、スキップにしたときに「なぜ走らなかったか」と「次に何をすればよいか」がその宣言だけから定まる能力に限る。** 定まらないものは静かな緑にせず、失敗にして材料を人の目の前に出す。4つの区別はこの基準で次のように分かれる。

- **合図が期限内に返らない(`SignalTimedOut`) → 能力側。** 観測が「合図が期限内に返らなかった」に閉じており、環境の遅さという説明と、負荷の低い環境なら成立するという見通しが宣言から読める。この観測が原因を1つに定めるわけではない(「影響」のトレードオフ)
- **実行ファイルが無い(`ProgramMissing`) → 失敗側。** 原因も回避方法も一意(example をビルドする形で実行する)。緑にすると、フィクスチャの作り忘れとビルド構成の誤りをそのまま隠す
- **実行ファイルはあるが起動できない(`ProgramUnusable`) → 失敗側。** 理由は起動が返した `io::Error` にしか無く、それが恒久的な環境の性質なのか一度きりの事故なのかを probe は判別できない。スキップに逃がすと、次に何をすればよいか誰にも分からない緑が残る。失敗にすればエラーが案内に載り、その環境で何が起きているかを人が判断できる
- **起動して合図が返る(`Available`) → 該当なし**(ケースが走る)

失敗側の2つは、失敗メッセージに次の一手の材料を載せる。実行ファイルの不在は原因と回避方法を、起動の失敗は `io::Error` の内容を述べる。エラーを早すぎる段階で文字列に畳まないのは、後から「この `ErrorKind` は能力側へ倒す」という述語を書く材料を残すため。

宣言側の網羅は `match` のワイルドカードで畳まない。新しい区別が増えたときに、能力側と失敗側のどちらへ倒すかをコンパイラが問う形を、宣言を持つすべての適用先で保つ。

**能力は probe で1度だけ判定し、宣言と挙動の双方がその1点を見る。** 判定は、実際に1回だけ保持プロセスを起動して合図を待つ probe に集約する。スキップの宣言も、ケースが呼ぶ起動関数も、この1点だけを見る。

probe が「実際に1回保持させてみる」形を取るのは、それがフィクスチャの本番の手順そのものだからである。ADR-055 の権限制限の probe が「フックが掛ける制限と同じ手順で判定する」ことで判定と実際のスキップの食い違いを消したのと同じ性質を、ロック側にも与える。

観測から宣言へ書き写す順序は取らない。宣言は最初のスキップ記録の時点で確定するため、対象のケースが並列に走る以上、2件目以降の観測は評価済みの集合に間に合わない。前提を直接見る形を保つのは ADR-068 と同じ理由である。

**probe の判定基準は「合図が期限内に返ったか」だけに限る。** 誰も保持していないパスでロックを取得できたかも、合図を読み取れたかも、判定には入れない。どちらも環境の能力ではなく異常なので、ケース側の失敗として現れるべきものである。読み取りが結果を返さずに終わった場合(読み取り側が結果を送らないまま消え、子の応答そのものを観測できていない場合)も同じ扱いにする。起動して合図待ちに入った子については、能力側へ倒すのは期限の超過を実際に観測したときだけで、それ以外は能力ありとして扱い、異常は後続のケースの失敗に出す(起動そのものが成立しなかった場合の振り分けは上の4区分による) — 判定に入れる観測を1つに保つ代わりに、`Available` を名乗る根拠は経路によって「合図が期限内に返った」と「期限の超過を観測しなかった」の2つに分かれる。

**probe が成立したあとのタイムアウトは失敗にする。** probe が通った以上、この期限超過は環境の能力の宣言としては読めない — 同じ手順が一度は期限内に返っている。probe が測るのは1プロセスの単発の起動で、本番の負荷そのものは測定条件に入っていない(後述のトレードオフ)ため、一度きりの期限超過が異常だと言い切れるわけでもない。繰り返し起きるなら閾値の見直しとして扱う。それは ADR-071 の停止規則で適用側のテストに収まる範囲であり、そのときは区別が付いているので閾値を動かす判断を正当に行える。ここを再びスキップへ逃がすと、区別を作った意味が消える。

**期限の無い待ちは、正常に保持できたと分かっている相手にだけ許す。** この基準が掛かるのは probe と、`crates/pulsen/tests/common/lock.rs` の失敗経路 — すなわち能力の判定と、判定のあとにフィクスチャが前提の破れを見つけた経路 — の2つである。どちらも保持プロセスが想定どおりに振る舞っていないと判断した直後なので、そこから相手の正常終了を期限なしに待つ理由が無い。いずれも `kill` してから終了を回収する形に揃える。

probe についてはもう1つ理由がある。probe は正常終了できるかを測っておらず、しかも1度きりの初期化の中にあるため、そこで止まれば能力を問うすべてのスレッドが止まる。ADR-060 が「フィクスチャのハングはテストの失敗より診断が難しい」として期限を置いた対象を、probe で期限の無い待ちに戻さない。

**この基準が実際に期限の無い待ちを消すのは、`kill` が届く限りにおいてである。** 終了の回収そのものには期限が無いので、`kill` を受けても即座には終われない相手に当たれば、揃えたあとの形もそこで止まる — probe についての上の理由も、その範囲までしか効かない。この状況は抽象的ではない。合図が返らない原因がロック取得の syscall で刺さっていること(ネットワークファイルシステム上の排他)なら、「合図が返らない」と「強制終了が即座には効かない」は相関する。この残りをどう畳むかは、下の「射程」と同じ手当ての問題である。

**射程はこの2つに限る。** 保持に成功したプロセスを標準入力の EOF で畳む解放の手順は射程の外にあり、取得できなかったプロセスに対してその手順を使う適合ハーネスの経路(`try_acquire_from_other_process`)も現状のままとする。取得に失敗した保持プロセスは即座に終了するので待ちは返る。この経路にも期限を掛けるには、子の終了を期限つきで待つ汎用の手当てと3 OS での検証が要る — 射程を広げるのはその手当てと同時にする。`kill` のあとの回収も同じ手当てが要る側にあり、期限を掛けるならまとめて掛ける。

**probe の置き場所の基準 — スイート側だけで判定できる能力はスイートに、適用側の具体的なフィクスチャに依存する能力は適用側に置く。** 保持プロセスのパスは適用側のテストターゲットからしか解決できず(ADR-032)、保持プロセスという具体のフィクスチャが存在することは適用側の知識である。スイートを別の実装へ適用する後続の適用先が、その知識を背負う筋合いは無い。ハーネスの trait 定義もフックのシグネチャも変えない。

同じ立場をスイートの正本(HOOKS.md)の表にも掛ける。判定列と「前提を作れない環境」列の主語はフック水準に保ち、適用側にしか存在しない関数名・定数名を書かない。書けば適用側の改名だけで正本が古くなる。この適用先での実態は括弧の補足として書く。

## 検討した代替案

- **起動結果の型で区別し、タイムアウトの事実を実行時に許容集合へ反映する** — 観測してから宣言へ書き写す構造になり、宣言が確定したあとの観測が間に合わないので、非決定的な赤が別の形で残る
- **合図の期限を延ばす** — 閾値をどこに置いても、実行ファイルの不在と環境の遅さの区別は付かない
- **`cfg(windows)` で決め打つ** — ADR-071。成立するかは環境の能力の問題であって OS の問題ではない
- **実行ファイルの不在も許容集合に入れる(従来の形)** — フィクスチャの作り忘れとビルド構成の誤りが静かな緑になる。ADR-068 が「`--workspace` を選ぶこと自体がこの経路の構造的な回避であり、許容集合には入れない」とした方針とも食い違う
- **起動できない場合(`ProgramUnusable`)を能力側へ倒す** — 上の基準で落ちる。理由が起動時のエラーにしか無いので、スキップの宣言だけからは次の一手が定まらない
- **probe を能力側に倒すときだけ再試行し、偽陽性の確率を下げる** — 再試行は偽陽性を消さず確率を下げるだけで、代償として「遅い」と判定済みの環境の待ちが倍になる。待ちの上限が固定であること(判定は1回きり)を保つほうを採る。偽陽性で許容集合が広がった場合はスキップの一覧に現れる
- **宣言の述語を1本に畳み、複数の適用先で共有する** — 観測を共有しているのは probe で足りており、述語まで畳むと、新しい区別が増えたときに各適用先の宣言でコンパイラが判断を迫る形が消える

## 影響

- 評価の順序や並列実行に関わらず、スキップの宣言と実態が一致する。吸収の形が ADR-071 の「probe + 許容集合」に乗るため、新しい原則を足さずに済む
- **ADR-068 が「決定」で挙げた帰結が本決定で改まる。** 068 は「単一テストターゲット指定では example がビルドされず、ロック保持のフィクスチャが消えてロック系のケースが『宣言済みスキップ』に化ける」と述べているが、実行ファイルの不在を失敗側へ置いたことで、その実行の仕方では適合4件と受け入れ1件が**失敗する**(メッセージが不在と回避方法を述べる)。ただし単一ターゲットの指定は example をビルドしないだけで既存の成果物を消しはしないため、失敗するのは `target/` にその成果物が残っていない場合である。`--workspace` を選ぶこと自体がこの経路の構造的な回避であるという 068 の方針は変わらない。ADR-068 の本文は判断が下された時点の記録として書き換えない
- 能力側と判定された環境では、以後のケースが起動を試みずにスキップへ落ちるので、期限ぶんの待ちは probe の1回に限られる
- 振り分けが基準で決まるので、後から区別が増えたときも同じ問い(スキップの宣言だけで次の一手が定まるか)で判断できる
- トレードオフ: **probe は無負荷の測定ではない。** 判定は遅延評価で、最初にロックの能力を必要としたテストスレッドの中で走る。そのとき同じテストバイナリの他のケースは並列に走っている最中であり、測定条件はそのバイナリの混雑した瞬間に近い。誤差は安全側に効かない — 偽陽性で能力側に倒れると許容集合が黙って広がり、ケースが走らなくても緑になる。この退行に機械的な歯止めが無いことは ADR-068 が記録済みで、スキップの一覧には現れる
- トレードオフ: probe が本番のケースと同じ資源(プロセス起動)を1つ使う。Windows の初回起動のスキャンを先払いする副次効果は見込めるが、それで相殺できるのは cold-start 由来の遅さだけで、負荷由来の遅さは probe の測定条件に入っていない
- トレードオフ: probe は本番の手順を合図までしか再現せず、ロックが実際に効くかまでは確かめない。その差は最初のケースで失敗として現れるので、静かな緑にはならない
- トレードオフ: `SignalTimedOut` の腕に入るのは環境の遅さだけではない。**保持プロセス側が合図を返さなくなった退行 — 実行ファイルはあり起動もできるが合図を書かない状態 — も同じ腕に入り、期限を変えないままスキップとして緑で通る。** probe が本番と同じ手順を踏む以上、フィクスチャ側に両者を区別する材料は無い。実行ファイルの不在は失敗側へ移したが、実行ファイルが壊れている場合は能力側に残っている。`SKIP` の一覧に5件が並んだときは、環境の遅さと同じだけフィクスチャの退行も疑う
- トレードオフ: 単一のテストターゲットを指定した実行が、これまでの緑から5件の失敗に変わる(成立条件は上と同じで、`target/` に example の成果物が残っていれば緑のまま通る)。失敗メッセージが原因と回避方法を持つ以上、緑に見える状態より危険度は低い。CI は `--workspace` で回すので影響を受けない
- トレードオフ: 保持プロセスを一切起動できない環境では、5件が失敗のまま残る。その環境を許容集合へ入れるかどうかは、案内に出た `io::Error` を根拠に改めて下す判断であり、材料の無いまま宣言を広げる形は取らない
