# ADR: ポートをまたぐ順序は、ダブル共通の採番で主張する

## ステータス

承認済み

## コンテキスト

通知の共通手続きの順序(凍結を書く → notify_cmd を実行する → `notified_at` を追記する)は、逆にすると失敗した通知が永久に再送されない — at-least-once を支える契約そのものである。

この順序は `TaskRepository` と `CommandRunner` の2ポートにまたがる。ダブルはそれぞれ独立した列に記録するため、`saved()` と `calls()` を別々に見るテストが主張できるのは同じポート内の順序だけになる。通知を先に起動して、成功したら stopped と `notified_at` を一度に書く実装でも、`saved` の列も `calls` の列もそれぞれの中では期待どおりに見えるので緑で通る。

## 前提

- ポートの契約には、単一ポート内では表現できない順序が含まれる
- 適合スイートのダブルは、対象のバックエンドを知らない形で書かれる(ADR-027)

## 決定

**`pulsen-conformance` のダブルに `RecordSeq` を持たせ、記録に添える。** 採番はプロセス内の1つの単調増加カウンタ(`static AtomicU64`)から採る。テストは複数ダブルの `*_in_order()` をマージし、採番で並べ直して1本の列として主張する。

**採番を掛けるのは、順序の契約がポートをまたぐメソッドだけにする。** 現時点では4つ — `TaskRepository::save` / `TaskRepository::save_degraded` / `CommandRunner::run` / `ProcessController::try_kill_remnants`。

- `save` と `run` は通知の順序そのもの(凍結を書く → notify_cmd を実行する → `notified_at` を追記する)を担う
- `save_degraded` を含めるのは、通知の順序が書き戻し先の型で変わらないためである。`Task` 経路だけを1本の列に並べても、縮退タスクの再通知は「`mark_notified` を先に保存する」実装を素通しにする。テスト側は保存先(`save` / `save_degraded`)と起動したコマンド(通知 / 判定)を区別したまま1本の列へ並べる — 契約は経路ごとに同じ順序を求めるので、取り違えを列の形として見せる。なお縮退タスクは tick 内で凍結する経路を持たない(定義依存の判断をすべてスキップする)ため、この経路で主張できるのは「通知 → `notified_at` の追記」の2ステップである
- `try_kill_remnants` を含めるのは、手続きD が `DiedWithoutExit` に対して `try_kill_remnants` → `fail_run` → `save` を契約として定めており、順序が `ProcessController` と `TaskRepository` をまたぐためである。`save` を先に置く実装は、それぞれのポートの列だけを見るかぎり期待どおりに見える

`starttime_of` / `kill` には掛けない。この2つに主張するのは「呼ばれない」「失敗しても書かない」だけで、またぐ順序の契約を持たない。

既存アクセサ(`saved()` / `saved_degraded()` / `calls()`)は採番を落とした形で維持する — 順序を要さないテストを書き換えない。`ScriptedProcessController` は呼び出しの記録を1本の列に持ち、採番は `Option<RecordSeq>` として `try_kill_remnants` にだけ載せる。`calls()` は採番を落として全呼び出しを返し、`calls_in_order()` は採番のある呼び出しだけを返す — 順序の契約を持たない呼び出しが並べ直しの列に混ざらないことを、アクセサの戻り値の形で示す。

## 検討した代替案

- **`Rc<Cell<u64>>` をハーネスが明示的に共有する** — 共有し忘れたダブルどうしでも比較がコンパイルを通り、無意味な順序を静かに主張できる。採番元がプロセスに1つなら、その失敗のしかたが存在しない
- **すべてのメソッドに採番を掛ける** — 順序の契約を持たない呼び出しが並べ直しの列に混ざり、テストが契約の無い順序を主張できてしまう
- **単一ポートの列だけで主張する(従来の形)** — 通知を先に起動して成功後に一度に書く実装が、どちらの列から見ても期待どおりに見えて緑で通る

## 影響

- ポートをまたぐ順序の契約を値として主張でき、通知を先に起動する実装が赤になる
- `RecordSeq` は比較だけができる不透明な値で、テストが具体的な番号に依存しない
- トレードオフ: 並行して走る別テストの記録が番号を飛ばす。主張に使えるのは前後関係だけで、差や連続性は使えない
- トレードオフ: 採番を要するポートごとにアクセサが2本になる。付けるのは上の4メソッドに限り、順序の契約が無いメソッドには付けない
