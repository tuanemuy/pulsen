# ADR: `exit` の読み取り結果は run ディレクトリの有無に入れ子で持つ

## ステータス

承認済み

## コンテキスト

`ShowTask` は `RunStore::attempt_exists` で run ディレクトリの有無を確かめ、**存在すれば** `read_exit` で exit を補う(`spec/usecases/task.md#showtaskshow` の処理フロー3)。存在確認は3値(在る / 無い / 確認できなかった)になるため、`read_exit` を呼ばない経路が2つ生まれる。

出力DTOで `exit` を有無と**並べて**持つと、この2経路の扱いが問題になる。「記録あり / 記録なし / 読めなかった」の3値にすればどちらも「記録なし」に落ちるが、ディレクトリごと無い場合はそれが真である一方、**存在を確かめられなかった**場合は記録の不在も主張できない — 表示が「記録なし」と言い切ると、観測できなかったことが観測結果として読める。かといって「読んでいない」を4つ目の変種として並べれば、有無と exit が独立な2軸になり、`(不在, 記録あり)` や `(在る, 読んでいない)` のような成立しない組み合わせが型で書けてしまう。

同じ問いは `snapshot` や `limits.retry` にも現れる。出力DTOのフィールドを「畳む / 並べる」で決める基準が無いと、項目ごとに場当たりで決まる。

## 前提

- ポートの存在確認が3値であること。確認そのものが失敗しうる限り、「有無を確かめられなかった」は消えない
- 表示項目の構成は spec が決めること(`spec/pages/index.md` の縮退表と AC-4 は run ディレクトリと exit を独立した項目として求める)。DTO の形が表示の項目構成を決める順序にはしない

## 決定

**`exit` は `RunDirPresence::Present { exit: ExitOutcome }` として run ディレクトリの有無に入れ子で持つ。** `ExitOutcome` は `Recorded` / `Absent` / `Unreadable` の3値で、`Present` のときにしか存在しない。`Absent`(ディレクトリが無い)と `Unknown`(有無を確かめられなかった)は exit を持たない — 前者は記録が無いことが事実として導け、後者は記録について何も主張できないため、どちらも別の値を添える余地がない。

`AttemptSummary` が run ディレクトリについて持つのは `run_dir_presence` の1つだけで、`read_exit` を呼ぶのは存在確認が `Ok(true)` を返した枝に限られる。表示は run ディレクトリの行と exit の行を**別々の項目**として出し、同じ値を2度 `match` して言葉を当てる — 不在は「(記録なし)」、確認できなかった場合は「(runディレクトリの有無を確認できないため読んでいません)」で、観測の失敗が観測結果として読めないことは変わらない。

**畳む / 畳まない基準は軸の従属性で決める。片方が他方を決める従属軸は入れ子にし、真に独立な軸だけを並べる。** `snapshot`(定義済みステータス一覧と、読めない理由)は両方が立つ状態もどちらも立たない状態も無い1軸なので `SnapshotInfo` に畳む。`exit` は run ディレクトリの有無が「読めるか / 何を主張できるか」を決める従属軸なので `RunDirPresence` に入れ子にする。

従属軸というだけでは畳む先が尽きるまで畳み続けられるため、**打ち止めの条件を基準に含める。畳むのは、(1) 従属関係が下位層(ドメインの直和型・ポートの呼び出し可能性)に既にある、かつ (2) 畳んだ後も各表示項目が自分の正本フィールドを持ち続ける、の両方を満たすときに限る。** 片方でも欠けるなら畳まず、従属である事実と畳まない理由を型の doc に残す — 従属を見落としたのか、見たうえで並べたのかを、次に同じ箇所を読む者が型だけで判別できるようにする。

適用結果は2件。

- `execution_state` + `stop_info` → `execution`(`ExecutionState`)。(1)(2) をともに満たす — 従属関係はドメインが `ExecutionState` として既に閉じており(凍結要因と通知は `Stopped` の付随データ)、実行状態の行は畳んだ後も `execution` 自身を正本に持つ。
- `limits.retry` は畳まない。(1) は満たす(`RetryLimitInfo::Unknown` は `SnapshotInfo::Unreadable` と共変する)が、(2) を欠く — 畳むとカウンタ行(attempt_count)の併記の正本がスナップショット項目の内側へ移り、表示が別の項目の内部形を読むことになる。加えて `RetryLimitInfo` の3値は `spec/usecases/task.md` の `limits.retry` と TC-task-show-task-029 が名前付きで定めた契約で、「併記なし」と「導出不能」の区別はその名前に結び付いている。

## 検討した代替案

- **`exit` を有無と並べ、「記録あり / 記録なし / 読めなかった」の3値で持つ** — 有無を確かめられなかった経路も「記録なし」に落ち、観測できなかったことが観測結果として表示される
- **「読んでいない」を4つ目の変種として並べる** — 有無と exit が独立な2軸になり、`(不在, 記録あり)` のような成立しない組み合わせが型で書ける
- **従属軸をすべて畳む** — 打ち止めの条件が無いと畳む先が尽きるまで畳み続けることになり、`limits.retry` のように表示項目が別の項目の内部形を読む形が生まれる
- **ドメイン側の形の変更を伴う畳み込み(`AttemptRef::process` を実行状態へ入れ子にする、など)** — 出力DTOの整形がドメインの形を決める順序になり、表示の都合が中心へ流れ込む

## 影響

- 成立しない組み合わせが型で表現できない。「有無を確かめられていないので読んでいない」は `Unknown` が exit を持たないことから構造的に従い、同じ事実を2つのフィールドで二重に表さない
- `read_exit` を呼ぶ条件が型の形と一致する。`ExitOutcome` を作れる場所が `Present` の構築点1つに限られるため、呼ばない経路が増えても値の埋め方を選び直す余地が生まれない
- 読み取りが失敗した場合(`ExitOutcome::Unreadable`)は、原因をポートの分類の**構造のまま**持つ — `RunFileError` の `Corrupt { path, message }` と `Io { message }` の区別を残す。文字列に潰すと、表示層がパスを出すべきかどうかを判定できなくなる
- パスを文字列に入れる層が決まる。アダプターの `Io` 系メッセージは既に対象を含むため、表示層はパスを前置しない。`Corrupt` は構造化された `path` を持つので、表示層がそれを1度だけ出す。`RunDirPresence::Unknown` も `Io` と同じ扱いにする
- トレードオフ: 表示層が同じ値を2度 `match` する。1つの項目にまとめれば1度で済むが、`spec/pages/index.md` の縮退表(run ディレクトリ・中身の不在は注記して 0)と AC-4(exit のパスと値を示す)はどちらも独立した項目として求めており、DTO の形に合わせて表示の項目構成は変えない
- `SnapshotInfo` / `RunDirPresence` / `execution` は、`spec/usecases/task.md` の ShowTask 出力DTO(`defined_statuses` / `snapshot_error`、`exit` / `run_dir_exists`、`execution_state` / `stop_info` をそれぞれ並べたフィールド)とフィールドの持ち方が離れる。spec 側の追従が要る
