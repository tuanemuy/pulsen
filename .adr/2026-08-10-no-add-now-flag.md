# ADR: add に --now フラグを設けない

## ステータス

承認済み

## コンテキスト

Phase 0 では、旧 `run` コマンドの廃止に伴い、登録後に1回のtickパスを実行する `add --now` を提供する決定だった(`add && tick` のショートカット、専用実行パスなし)。Phase 2 完了後のレビューでこのフラグの必要性を再検討した。

## 前提

- tick は冪等で、排他ロックにより多重実行が防がれる。tick 単体もロック競合時は状態を変更せずスキップして 0 で終了する
- 想定するtick間隔は1分程度であり、tick頻度はエージェント実行の回数(実行コスト)に影響しない

## 決定

`--now` フラグを設けず、`add` は登録のみとする。次回の定期tickを待たず即座に開始したい場合は、シェル合成 `add && tick` で行う。

`add --now` は exit code の挙動(ロック競合時の 0 スキップ)まで含めて `add && tick` と完全に等価であり、等価な合成が既に存在する機能のために、専用シナリオ・縮退規則(登録成功のままtickパスのみスキップ)・テストを維持する価値がない。定期性・合成をツールの外部(スケジューラー・シェル)に委ねる設計思想とも整合する。

## 検討した代替案

- `--now` を維持する — 害はないが、`add && tick` との等価性の説明を spec・ヘルプ・テストで維持し続けるコストだけが残るため不採用
- `add` が常にtickパスを実行する — tick は当該タスク専用でないフルパスであり、他タスクの kill・クリーンアップ・判定コマンド実行(timeout デフォルト60秒)を登録コマンドに巻き込む。add の契約(検証して永続化するのみ)も濁るため不採用

## 影響

- 「登録と同時に即実行する(add --now)」シナリオと、pages の `--now` に関する記述(フラグ定義・ロック競合の縮退規則)を削除した
- 即実行の案内は「登録に続けて手動で `tick` を実行する」に統一する(setup.md のワークフロー試行シナリオを含む)
