# ADR: スキップの合否判定は `SkipBudget` に一本化し、CI は環境前提の直接アサートと可視化だけを持つ

## ステータス

承認済み

## コンテキスト

`.adr/1-conformance-skip-budget.md` は「スイートを適用するテストファイルが、スキップを許容するケースの集合を環境の能力から実行時に宣言する」と決めた。`SkipBudget::record` は `SKIP` 行を出した直後に `assert!(self.allows(case))` を通すので、宣言集合の外のスキップは**そのケースの失敗**として現れる。libtest は成功したテストの stdout を握り潰すため、`--nocapture` が無いと `SKIP` 行そのものがログに出ない。CI がスキップをどう扱うかを決める必要がある。

「非 root unix なら許容集合はすべて空になる」という見立ては実測と合わない。macOS(非 root)で `cargo test --workspace --locked -- --nocapture` に掛けると、**全件 PASS・exit 0 でありながら `^SKIP ` 行が4件出る**。

- `tc_port_clock_005`(適合スイート) — `conformance_time_id.rs` の `allowed_clock_skips()` は環境を一切見ず定数を返す。`SystemClockHarness` が `rewind` を提供しないのは実時計というアダプターの性質であって環境の欠落ではないので、**どの OS でも恒久的にスキップされる**。HOOKS.md も TC-port-clock-005 の判定を「ハーネスが `rewind` を提供するか」としており、プラットフォームでも権限でもない
- `pulsen-conformance` の lib ユニットテスト3件 — `SkipBudget` の仕様自体を検証するテストが `record` を直接呼ぶ(うち2件は `#[should_panic]`)。ケース名は架空のもので、実在の適合ケースと形が区別できない

したがって「SKIP 行が 0 件」を CI が要求すると、非 root unix でも初回から確実に赤になる。赤の原因は `.adr/1-conformance-skip-budget.md` が正しく設計した振る舞いなので、環境を整える手当てでは解消できない。

CI 側の扱いの選択肢:

1. 何もしない — Windows で権限系のケースが走っていないことが誰にも見えない
2. 期待するスキップ集合を CI にハードコードして照合する — `SkipBudget` が持つ知識を CI に複製し、区分 C の行が増えるたびに2箇所を直す。`.adr/1-conformance-skip-budget.md` が「件数ではなく集合で宣言する」とした理由(宣言と実態のズレが集計で相殺されない)を CI 側で崩す
3. 恒久スキップを除外リストに書いたうえで、unix ジョブに限り「フィルタ後の SKIP 集合が除外リストと一致しなければ失敗」を要求する。除外リストに入るのは環境非依存の恒久スキップだけで、非 root unix では架空ケースを除いたあとに残る SKIP はちょうど1件(`tc_port_clock_005`)。区分 C の行は非 root unix では**走る**ので SKIP 行を出さず、区分 C が増えても除外リストは動かない。腐るのは恒久スキップを足したときだけで、それは意図的でレビュー可能な事象。**環境由来の判断を複製しない安価な歯止めとして成立する。** 採らない理由は「腐るから」ではなく、恒久スキップの宣言先が `allowed_clock_skips()` とワークフローの2箇所になり、両者を結ぶものがコンパイラにもテストにも無いこと、そして宣言集合が最も大きい Windows には適用できないこと
4. **スキップの正しさは `SkipBudget` に委ね、CI は「宣言集合が痩せる環境で回っていないこと」という前提そのものを検査する。** SKIP 行は可視化するが合否には使わない

スキップ件数は「宣言が正しいか」の proxy にすぎず、観測結果を期待値に写す構造になりやすい。4 は前提(非 root であること)を直接見るので循環しない。「root コンテナで回すなら宣言値の見直しが要る」という懸念への直接の答えでもある。

`--nocapture` は SKIP 行を取り出すために要るが、副作用として `pulsen-conformance` の `#[should_panic]` 2件が出す「宣言外スキップ」のパニックメッセージもログへ素通しになる。ここに `RUST_BACKTRACE: 1` を全ジョブへ掛けると `SkipBudget::record` → `CaseOutcome::report` のスタックトレースまで付き、**緑の実行のログに本物と見分けのつかない失敗が2件常駐する**。赤のときに人が読むのはサマリーではなくログのほうなので、ここを汚すのは架空ケースをサマリーから除いたのと同じ理由で避けたい。

## 決定

- テストは `cargo test --workspace --locked -- --nocapture` で回し、出力を `test.log` に残す(`--nocapture` が無いと `SKIP` 行が握り潰される)
- **スキップの合否判定を CI は持たない。** 宣言集合の外のスキップは `SkipBudget` がそのケースの失敗として落とす。CI が proxy で二重化しない
- **CI が独自に守るのは環境前提のほう。** unix ランナーでは実行ユーザーが root でないこと(`id -u` が 0 でない)を各 stable ジョブの先頭で直接アサートし、成立しなければ即座に失敗させる。ジョブのコンテナ指定は使わない(コンテナのランナーは root で走る)
- **その唯一の判定を fail-open にしない。** `id -u` の出力は代入で受けてから検査する。`if [ "$(id -u)" -eq 0 ]` の形だと、`id` 自体が失敗しても `-e` が効かない位置なので `[` が「整数でない」で偽になるだけで、検査が空振りしたままステップが成功する。代入形なら `id` の失敗がその場で落ち、`0` でも数値でもない出力も失敗として扱える。判定できなかったときに通す側へ倒すと、守っているのは前提ではなく「前提を読めたときだけの前提」になる
- **可視化は失敗させずに行う。** 全 OS で `test.log` の `SKIP ` 行をジョブサマリーに列挙する。ただし `pulsen-conformance` の lib ユニットテストの区間は除外する — 架空のケース名が実在の行と混ざると、サマリーを読む人間が「走らなかった適合ケース」を誤って数える
- **除外した件数もサマリーに出す。** 除外の単位はケース名ではなくテストバイナリの区間なので、将来そのバイナリが実在ケースのスキップを出せば、それはサマリーから黙って消える。可視化しか役割を持たない機構なので、消えたことを合否判定で捕まえる経路が無い。件数が 3 から動くことが唯一の合図になる。区間で判定すること自体は、ケース名を列挙するより腐りにくいので変えない
- **ログの色は保ったまま、抽出側で ANSI を落とす。** `CARGO_TERM_COLOR: always` を付けると cargo の `Running` 行は `\033[1m\033[92m     Running\033[0m …` になり、行頭が空白ではなく ESC で始まる(実測)。ANSI を残したまま区間を判定すると除外が丸ごと効かず、色なしなら1件のサマリーが色ありでは4件になる。色を捨てて `CARGO_TERM_COLOR` を外す手もあるが、**赤を読むのはサマリーではなくログのほう**で、`error:` が着色されているかどうかは Actions の UI で読む速さに直に効く。色は Actions の UI 向け、抽出は機械向けと役割が違うだけなので、両立できる形 — 抽出の照合用に ANSI を落とした行を作ってから判定する — を採る。`SKIP ` 行と `test result:` 行は libtest の出力でパイプ越しには色が付かない(実測)ため、ANSI が影響するのは `Running` 行の判定だけである
- **行頭に錨を打たない。** ANSI を落としても行頭一致では足りない理由がもう1つある。`--nocapture` 下の libtest は改行を伴わない進捗行 `test <名前> ... ` を先に書き、その改行待ちの行末に別スレッドのテストの stdout が載る。`SKIP ` 行・`Running` 行・`test result:` 行はいずれも進捗行に連結した姿で現れうる(Windows で実測)。連結の位置は「`... `」の直後に限らない — 判定の綴りに直付いた `okSKIP tc_port_clock_004_…` の形が実在する。**位置を列挙しても網羅にならないので、3種類とも行のどこに現れても拾う。** `SKIP` は見つけた位置から行末までを1件の同一性に使う。区間は `Running` に加えて `Doc-tests` でも切り替え、`test result:` で閉じる — 開いたままにすると最後の `Running` 以降の SKIP がすべて除外側へ回る
- **偽陽性と偽陰性を対称に扱わない。** この機構は可視化しか役割を持たないので、誤って1行余分に出すことと、黙って1行消すことは重さが違う。後者は他に検出経路がない。入口も区間の判定も、迷ったら「拾う・開く(＝列挙される)」側にしか倒れない形にする
- **「SKIP 0 件」と「テストが走っていない」を同じ表示にしない。** 報告は `if: always()` で走るため、build が落ちた実行でも表示が出る。テスト結果行(`test result:`)の有無で「到達していない」「走っていない」「走ったが 0 件」を区別する。可視化が目的である以上、最も紛らわしい局面(OS 差の赤を吸収している最中)で嘘の「なし」を出すなら可視化になっていない
- **`RUST_BACKTRACE` は設定しない。** 上記の意図的なパニック2件にスタックトレースが付くのを避ける。テストの失敗は libtest がメッセージとソース位置を出すので、バックトレースが要るのは依存クレート内部でパニックしたときに限られ、そのときは手元で `RUST_BACKTRACE=1` を付けて再現する。あわせて、この2件が緑でも出ることをワークフローの why コメントに残す
- **新しい環境で走らせるときは、期待するスキップ集合を実行前に HOOKS.md から予測し、実行後に観測と突き合わせる。** 観測値を期待値へ書き写す順序は取らない。差分が出たら予測が誤っていた理由を先に特定し、それから期待値を更新する
- `cargo test --test <名前>` を使わず `--workspace` のままにする。単一テストターゲット指定では example がビルドされず、ロック保持のフィクスチャが消えてロック系のケースが「宣言済みスキップ」に化ける。`--workspace` を選ぶこと自体がこの経路の構造的な回避であり、`SkipBudget` の許容集合には入れない(HOOKS.md の方針)
- これらの理由をワークフローの why コメントとして残す

## 影響

- 判断主体が `SkipBudget` の1箇所に保たれ、CI に知識が複製されない。恒久スキップが増えても CI 側の手当てが要らない
- 「静かな緑」を作る条件(root 実行・単一テストターゲット指定)が、やらない理由つきでワークフローに記録される。前提の検査は観測結果と独立なので、何件スキップしても判定が循環しない
- トレードオフ: 宣言集合そのものが不当に広げられた場合(`allowed_skips()` が環境を見ずに大きな集合を返すよう書き換えられる等)、CI は気づかない。これはテストコードのレビューで見る範囲とし、CI の役割にはしない
- トレードオフ: **マージ後の環境退行に機械的な歯止めが無い。** 非 root アサートが塞ぐのは権限系の述語だけで、`tmpdir_outside_repository()`(ランナーの一時ディレクトリがリポジトリ配下へ移る)や `holder_program()` 経由の合図タイムアウトが false へ倒れれば、許容集合が黙って広がって CI は緑のまま進む。守れるのは PR の初回実行を人が読む範囲まで。サマリーの SKIP 一覧には現れるので、実際に退行を踏んだ時点で unix 限定の集合一致判定(選択肢3)を足す判断をそのとき行う
- トレードオフ: `--nocapture` によりテストの標準出力がすべてログに出る。既存のテストで `println!` するのは `SkipBudget::record` だけなので実害は小さい
- トレードオフ: `RUST_BACKTRACE` を設定しないので、依存クレート内部でパニックした場合は手元で再現するまでスタックが見えない。緑のログに常駐する偽の失敗を消すほうを採った
- トレードオフ: サマリーからの除外を cargo が出す `Running unittests src/lib.rs (…pulsen_conformance-…)` の区間で行うため、cargo の出力形式に依存する。形式が変わっても混ざるのは架空の3件だけで、合否には影響しない
- トレードオフ: `--nocapture` 下の libtest は進捗行とテストの stdout を同じストリームへ並行に書くため、**行の切れ目が保証されない**。行のどこでも拾う形にしたのはこれに対する対処だが、代償として本文に綴りを含むメッセージを誤って拾いうる。`SkipBudget` のパニックメッセージの文言が変われば起きる。可視化にしか使わない機構なので、その場合の被害はサマリーに1行余分に出ることに留まる。件数が3から動いたときに読み手が見るのは、実在ケースの巻き込みと、この誤検出の両方である
- トレードオフ: 区間で除外する以上、そのバイナリが実在ケースのスキップを出すようになれば一緒に落ちる。除外件数をサマリーに出すので、除外が広がったことは件数の変化として見える。読む人がいて初めて効く歯止めであり、機械的な検出ではない
