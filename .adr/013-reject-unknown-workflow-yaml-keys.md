# 013: ワークフローYAML・グローバル設定の余剰キーは読み込み時エラーとする

## ステータス

承認済み

## コンテキスト

ワークフローYAMLに、動作種別に無関係なキー(「何もしない」ステータスへの `judge` 等)や、スキーマに存在しないキーが書かれていた場合の扱い(登録時エラーか無視か)が未確定だった。同じ問いは config.yaml にもある(`run_retention` の typo が無視されると gc が無効なまま気づけない)。

## 前提

- 検証は境界で一度だけ行う(parse, don't validate。CLAUDE.md)方針であり、登録時検証(`add`)が定義の受理を確定する(ADR-003)
- 定義は登録時にスナップショットされ、以降の修正は既存タスクに反映されない(requirements §7.1)。受理された定義の誤りは実行時まで顕在化しない

## 決定

ワークフローYAMLのパースは**厳格スキーマ**で行い、次をすべて登録時(読み込み時)エラーとしてタスクを作らない。

- スキーマに存在しない未知キー(トップレベル・ステータス内とも)
- 動作種別に無関係なキー: エージェント実行に属するキー(`agent` / `model` / `timeout` / `retries` / `judge` / `next`)を `run: wait` / `run: cleanup` のステータスに書いた場合
- 各レベルで許されるキーの集合:
  - トップレベル: `workflow` / `agent` / `model` / `initial` / `statuses`
  - エージェント実行ステータス: `prompt` または `skill`(どちらか1つ)+ `agent` / `model` / `timeout` / `retries` / `judge` / `next`(`next` は必須)
  - `run` ステータス(`wait` / `cleanup`): `run` のみ

**config.yaml にも同じ規則を適用する**: スキーマ(`agents` / `notify_cmd` / `judge_attempt_limit` / `judge_timeout` / `spawn_fail_limit` / `run_retention`)に存在しないキーは読み込み時の構造エラーとする。これは pages の「内容の検証は参照時に行う」と矛盾しない — 検証は二層であり、**構造**(YAML構文・キーの正当性・型・期間の形式)は読み込み時に、**内容**(コマンドテンプレートのプレースホルダの正当性等)は参照時(add の登録時検証・tick の展開時)に行う。壊れたテンプレートを含む config でも、それを参照しないタスク・コマンドは動作する。

## 検討した代替案

- 未知キーの無視(寛容パース) — typo(`prmopt`、`nxet` 等)や意味のない指定(wait への `judge`)が無言で捨てられ、スナップショット後に「書いたはずの設定が効いていない」形で顕在化する。登録の成功 = 定義の受理確認(setup.md シナリオ2)という体験が壊れるため不採用
- 警告付きで受理 — 警告は無人運用(cron からの add)で読まれない。エラーとの中間状態を設ける価値がないため不採用

## 影響

- 定義スキーマへの将来のキー追加は、旧バージョンで登録済みのスナップショットに影響しない(スナップショットは検証済みの正規化構造で保存されるため)
- クリーンアップステータスはリトライ上限の上書きキーを持てないことが確定する(上限の出所は ADR-014)
- 実装ではデシリアライズを deny-unknown-fields 相当の厳格モードで行い、動作種別との整合はパース後の検証で確認する
