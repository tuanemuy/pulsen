# ADR: OS 差の吸収は probe と許容集合で表し、層を越える場合は別 Issue へ切り出す

## ステータス

承認済み

## コンテキスト

CI を新しい OS へ広げる作業は「回して落ちたら吸収する」という条件付きの部分を含む。何が落ちるかは実行するまで確定しないため、完了条件が「CI が緑になるまで」という形になる。この書き方には上限が無く、2つの形で膨らみうる。

- **層を越える膨張**: Windows の `NamedTempFile::persist` が共有違反を返す場合、短い再試行で収まらなければ `write_atomic` の置換方式そのもの、ひいては永続化ポートの契約に踏み込む。そこまで行くと「CI の導入」が別テーマの設計変更を巻き込み、PR の読み手にスコープが見えなくなる
- **無期限化**: 「Windows では契約自体が成立しない」という結論に至ったとき、「3 OS とも緑」を満たす方法が無くなり、Issue が開いたまま残る

停止規則を「振る舞いを変えるかどうか」で書くと境界が定まらない。`write_atomic` の中に `persist` の再試行を足すのは、`util/atomic.rs` の振る舞いを変えることでもあるし、置換の**方式**は変えないことでもある。どちらとも読めるので、境界は「変えるか」ではなく**何を変えるか**で引く必要がある。判定者と判定タイミングも決めないと、条件付きの作業は「緑になるまで」を無期限に回せてしまう。

吸収の表し方にも選択肢がある。

1. `cfg(windows)` で決め打ちに分岐する — 「その環境では成立しない」を静的に宣言することになるが、実際に成立するかは環境の能力の問題であって OS の問題ではない。`.adr/1-conformance-skip-budget.md` が「環境の能力から実行時に決める」とした理由をそのまま崩す
2. **probe を足して `SkipBudget` の許容集合に入れる** — 既に ` .yaml` フィクスチャに対して採っている手。同じ形が他のケースにも一般解として使える
3. `continue-on-error: true` で Windows ジョブを緑に見せる — 「スキップを緑と誤認しない」という CI 導入の趣旨に真っ向から反する。ジョブ単位で同じ誤認を作る

## 決定

- **吸収は probe + 許容集合で表す。** 実測の結果ある環境で前提を作れないと判明した場合、`cfg(windows)` の決め打ちではなく「その能力があるか」を実際に試す probe を足し、その結果で `SkipBudget` の許容集合に加え、HOOKS.md に行を足す。これを OS 差の吸収全体に掛かる原則とする
- **停止規則が掛かる範囲**: **OS 差に由来する赤だけ。** MSRV ジョブの赤と、現行 stable の clippy / rustfmt との差による赤(`.adr/10-stable-toolchain-tracks-the-current-release.md`)は別の軸で、この規則の対象外とする。前者は「特定の環境で契約が成立するか」という設計の問題だから射程を絞る必要があるが、後者2つは対象ファイルが原因側で決まる(MSRV 非対応の API を使っている箇所・lint が指摘した箇所・rustfmt が整形し直す全域)ので、層で線を引く意味がない。MSRV の赤は `crates/pulsen/src/cli/` や `crates/pulsen/src/application/` を、`rust-version` を上げるなら `Cargo.toml` と `.adr/1-std-file-lock-and-lockguard-marker-trait.md` / `.adr/1-dependency-selection.md` を、`cargo fmt --all` は `crates/pulsen-domain/` を含むソースツリー全域を正当に触る。これらを層の逸脱と読まない
- **停止規則の判定者とタイミング**: **OS 差由来の CI が赤になった時点で、その赤を消す作業を行う実装者が判定する。** 判定するのは「その赤を消す修正が `crates/pulsen/src/util/` / `crates/pulsen/src/adapter/` / `crates/pulsen/tests/`(フィクスチャ)/ `crates/pulsen-conformance/src/` に収まるか」。収まると判定したらそのまま直す。収まらないと判定したら**その場では直さず**、別 Issue を起票して当該 OS を下の撤退条件に載せる。判定の結果(どちらに倒したか、その理由)は PR 本文に残す。迷う場合は切り出す側に倒す — CI 作業の目的は CI を回すことであって、置換戦略を設計し直すことではない
- **境界を具体で引く。** 上記の「収まるか」は次のように読む(OS 差由来の赤に限る)
  - **その場で扱う**: `persist` を使う置換手順を保ったまま、失敗時の再試行やエラー分類をその手順の中に足す。フィクスチャの待ち時間・環境変数の渡し方を変える。probe を足して `SkipBudget` の許容集合と HOOKS.md に反映する
  - **切り出す**: `persist` を使わない置換方式への変更。`write_atomic` / `rename_atomic` のシグネチャや契約(失敗時に一時ファイルを残さない・対象が変わらない・読み手はロックなしで常に一貫した内容を見る)の変更。ポート trait の定義変更。`crates/pulsen-domain/` の変更
- **撤退条件**: probe + 許容集合でも表せず、別 Issue へ切り出した結果ジョブが赤のまま残る場合、`continue-on-error` で緑に見せることはしない。**赤のまま残るジョブだけ**をマトリクスから外し、外した理由と切り出した Issue 番号をワークフローの why コメント・PR・元の Issue のコメントに残したうえで、その Issue を閉じる
  - 外す単位はジョブであってプラットフォームではない。stable の Windows が緑にならない場合に外すのは **stable の Windows だけ**で、MSRV の Windows は残す — MSRV ジョブは `cargo build --all-targets` だけでテストを実行しないので、テスト・フィクスチャ由来の赤を持たない。MSRV の Windows がコンパイルできない場合は MSRV の軸の話で、そこでも解消できないときに初めて MSRV の Windows も外す
  - 撤退後のジョブ数は、stable の Windows だけを外したなら6、MSRV の Windows も外したなら5になる(`.adr/10-job-split-fmt-and-two-os-matrices.md` の7から読み替える)
- どの出口を採る場合も、テストを緩めること(アサーションの削除・`#[ignore]`・期待値の弱化)は取らない

## 影響

- 条件付き作業の射程が明示され、「緑になるまで」が無限の作業を意味しなくなる。判定の起点(CI が赤になった時点)が決まっているので、判断を先送りしたまま試行を繰り返す形にならない。Issue が閉じられる状態が常に存在する
- 吸収の形が `.adr/1-conformance-skip-budget.md` と揃うため、`cfg` 分岐が増える圧力を受け止める先が1つに定まる
- 停止規則が「変えるか」ではなく「何を変えるか」で書かれているので、`write_atomic` への再試行追加(`.adr/10-atomic-replace-move-read-retry-on-transient-denial.md`)が規則に抵触するかを読む人ごとに判断しなくてよい
- トレードオフ: 撤退した場合、検証範囲が当初の狙いより狭くなる。ただしマトリクスから外した事実と理由がワークフロー・PR・Issue に残るので、「検証済み」と誤読される形にはならない
- トレードオフ: 境界の列挙は現時点で想定できる失敗に基づくもので、想定外の失敗には当てはまらない。その場合は「迷ったら切り出す」に倒す
