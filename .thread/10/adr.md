## ADR-001: CI は GitHub Actions に置き、toolchain はランナー同梱の rustup から取る

### Status

Proposed

### Context

CLAUDE.md は「安定版ツールチェーンを前提とし、`cargo fmt` / `cargo clippy` を通る状態を保つ」「特定の OS に依存しない(Linux / macOS / Windows)」と定めるが、検証環境は Nix flake の devShell 1つだけで、rustc は nixpkgs-unstable の 1.97.1、実機は macOS のみ。Windows を含む3 OS を回せる CI が要る。

CI プロバイダの選択肢:

1. **GitHub Actions** — リポジトリは GitHub の public(`tuanemuy/pulsen`)。3 OS のホストランナーが無料で使え、PR のチェック統合が標準。
2. GitLab CI / Circle CI 等の外部サービス — リポジトリのホストと分離し、アカウントと連携の管理が増える。Windows ランナーは有料か自前。
3. self-hosted ランナー — Windows 実機を自前で用意する必要がある。Issue の「Windows 実機での挙動は未検証」を解消するには最も遠回り。

toolchain の入手手段:

1. **rustup**(3ランナーとも同梱) — Windows を含む3 OS で同じ手順が通る。MSRV 用の別バージョン導入も `rustup toolchain install` の1行。
2. Nix(`nix develop -c ...`) — 開発環境と完全に一致するが、**Windows で成立しない**。Linux / macOS だけ Nix、Windows だけ rustup にすると、CI の中に2種類の toolchain 供給経路が生まれ、赤の原因を切り分けにくくなる。また nixpkgs は「宣言した MSRV の版」を狙って入れる手段としては不向き。
3. `dtolnay/rust-toolchain` 等の第三者製 Action — 広く使われているが、public リポジトリに第三者製 Action を入れるとサプライチェーンの面が増える。ADR-023 は依存の選定を「用途が1〜2モジュールに閉じ、std で足りるものは足さない」という基準で行っており、CI でも同じ基準を当てるなら、`rustup` の3行で済むものに Action を足す理由がない。

### Decision

GitHub Actions を使う。toolchain はランナー同梱の `rustup` を直接叩いて用意し、CI が使う Action は GitHub 公式の `actions/checkout` **だけ**にする。

- stable ジョブ: `rustup update stable --no-self-update` → `rustup default stable` → `rustup component add clippy`
- fmt ジョブも同じ手順を踏む(ADR-004 の「常に現行 stable」は整形にも掛かる)。導入する component が `rustfmt` である点だけが違う。
- MSRV ジョブ: `rustup toolchain install <版数> --profile minimal --no-self-update` → `cargo +<版数> ...`
- Nix devShell は開発環境として残し、CI では使わない。CI と devShell で rustc の版が違うことは受け入れる — むしろ「1つの版でしか通らない」状態から抜けることが本 Issue の目的である。

`actions/checkout` は**唯一の例外として残す Action** なので、固定方法も同じサプライチェーン基準で決める。**現行のメジャータグ(`actions/checkout@v7`)で固定する。** 固定するのはメジャーだが、**古いメジャーに留まり続けることは固定ではなく放置である** — `actions/checkout` の旧メジャーは Node ランタイムの世代とともに非推奨になり、いずれ警告付きで動く状態になる。導入時点の現行メジャーを採り、以後はその非推奨の警告を更新の合図とする。SHA ピンは改竄への耐性が一段上だが、更新のたびに SHA を手で追う運用が要る。GitHub 公式 org のリポジトリはアカウント侵害の面が第三者製より小さく、他に Action を持たない構成では守るべき面が1つしかないので、メジャータグの安定性と読みやすさを採る。ブランチ参照(`@main`)や暗黙の最新は取らない。

ランナー同梱の前提は、各ジョブの先頭で**その場で落ちる**形に検査する。対象は「ワークフローがそのジョブで実際に使う道具」に揃える — `rustup`(全ジョブ)、`cargo` / `jq` / `grep`(MSRV ジョブ)、`awk` / `cat` / `grep` / `tee`(stable ジョブのスキップ報告)、`id`(stable ジョブの非 root アサート)。`id` を落とさないのは、それが CI の独自の合否判定(ADR-005)が乗る唯一の道具だからである。記録にしか使わない道具を検査して、判定に使う道具を検査しない理由がない。前提が崩れたときに `cargo` の不可解な失敗として現れるより、崩れた前提そのものが失敗として現れるほうが切り分けが早い。前提が実際に崩れた場合の第2手は、第三者製 Action を足すことではなく `curl https://sh.rustup.rs -sSf | sh` を自前で叩くこと。

`cargo` を MSRV ジョブにだけ入れるのは、そのジョブだけが**自分で toolchain を用意する前に** cargo を使うからである。fmt / stable ジョブは `rustup default stable` を踏んでから cargo を叩くので存在が保証されるが、MSRV ジョブは `rustup default` を一度も呼ばず、ランナーに既定 toolchain が設定済みであることに暗黙に依存して `cargo metadata` で版数を読み出す。既定が無ければ rustup のシムがそこで落ち、それが「版数の読み出しの失敗」に化ける。

検査の形は道具によって分ける。`rustup` / `cargo` / `jq` は `--version` で版まで表示する(版がログに残る利点がある)。`awk` / `cat` / `grep` / `id` / `tee` は `command -v` で存在と解決先パスだけを見る — **`--version` は移植性が無く**、macOS の BSD `tee` は `illegal option -- -` で落ちる(実測)。解決先パスを出すのは、Windows で Git for Windows の `/usr/bin/<tool>` ではなく `C:\Windows\System32\` 側の同名プログラムを掴んでいないかがログから分かるため。

**`sort` はどのジョブでも使わない。** `command -v` は存在すれば成功するので、間違ったプログラムを掴んでいても前提検査は通ってしまう。Windows の PATH 解決が `C:\Windows\System32\sort.exe` に当たった場合、それは `-u` を受け付けずに非ゼロで終わる。スキップ報告の抽出は `-e` の下で落ちないよう終了コードを切り離してあるので、**パイプライン全体が空になり「なし」という嘘のサマリーが出る** — 11件スキップしている Windows で「走らなかったケースは無い」と表示されるのは、可視化としては失敗そのものである。重複除去は区間判定で既に使っている awk に寄せ(`!seen[$0]++`)、`sort` への依存自体を持たない。道具を1つ減らすことが、掴み違いを検査で捕まえるより確実で安い。

### Consequences

- 良い点: 3 OS が同一の手順で回る。第三者製 Action がゼロなので、ワークフローの信頼境界が GitHub 本体だけに閉じる。MSRV の toolchain 切り替えが1行で済む。
- 良い点: ランナー前提の崩れが fail-fast で見える。AC-7 を守ったまま逃げ道(rustup 自前導入)が用意されている。
- トレードオフ: CI の toolchain と devShell の toolchain が一致しない。ローカルで緑でも CI で clippy が落ちる(またはその逆)ことが起きうる。これは検出したい種類のズレなので、一致させる方向には倒さない。
- トレードオフ: `actions/cache` や `Swatinem/rust-cache` が提供する高速化を捨てる(ADR-006 参照)。
- トレードオフ: メジャータグ固定なので `v7` の内部が動いたことは検知できない。SHA ピンへ上げる判断は、第三者製 Action を足すことになったときに全体でまとめて行う。

## ADR-002: MSRV は `Cargo.toml` の `rust-version` を読み出して固定し、3 OS すべてで検証する

### Status

Proposed

### Context

`rust-version = "1.89"` は ADR-022(`std::fs::File::try_lock` の安定化)を根拠に宣言されているが、その版で一度もビルドされていない。MSRV ジョブでどう版を決めるかに選択肢がある。

1. ワークフローに `1.89` を直接書く — 単純だが、`Cargo.toml` を上げたときにワークフローの更新を忘れると、CI は古い版を検証し続ける。宣言と検証対象が黙ってズレる。
2. **`Cargo.toml` から読み出す** — `cargo metadata --format-version 1 --no-deps` の `rust_version` を `jq` で取り出す。`jq` は3ランナーとも同梱。ズレようがない。
3. `rust-toolchain.toml` を置いて rustup に解決させる — MSRV とは別に「既定の toolchain」を宣言するファイルであり、意味が混ざる。加えて Nix devShell(rustup 無し)からは無視されるため、ツールチェーン指定の出典が2つに割れる。

読み出す対象にも選択肢がある。3クレートはいずれも `rust-version.workspace = true` で、`workspace.package.rust-version = "1.89"` が唯一の宣言である。`cargo metadata` は継承を解決したうえで3パッケージすべてに `rust_version` を載せるので、`select(.name == "pulsen")` で1パッケージだけを見ても現時点では同じ値が取れる。ただしそれは継承が全員に効いている結果にすぎず、将来どれかが個別に `rust-version` を持てば、CI が検証するのは `pulsen` の値だけになり、他クレートの宣言は一度も実測されない。基準が言う「唯一の出典」と実装が指すものが割れる。

検証コマンドの範囲: `cargo check --workspace --all-targets`(型検査まで)/ **`cargo build --workspace --all-targets`**(コード生成・リンクまで)/ `cargo test`(実行まで)。Issue は「`rust-version` に固定した toolchain での**ビルド**」と書いている。`check` はリンク段階でしか出ない失敗(リンカの差、単相化後にのみ現れるエラー)を取りこぼし、それが最も起きやすいのは一度もリンクされたことのない Windows 側コードである。stable ジョブが見ているのは stable でのリンクであって MSRV でのリンクではない。依存45クレート・クリーンビルド55秒という規模なら、`check` から `build` へ上げる追加コストは1ジョブあたり数十秒に収まる。

### Decision

- 版数はワークフローに書かず、`cargo metadata --format-version 1 --no-deps` の**全メンバーの `rust_version`** を読み出す。`null` を除いた値が空なら失敗させ、値が複数種類に割れていても失敗させる(どの版で検証すべきかが一意に決まらない状態を黙って通さない)。一意に定まった値を `rustup toolchain install` と `cargo +<版数>` に渡す。
- MSRV ジョブは stable と同じ3 OS のマトリクスで回す。MSRV は言語と std の API 表面の話なので1 OS で足りるという考え方が一般的だが、このプロジェクトには `#[cfg(unix)]` / `#[cfg(not(unix))]` で分岐するコードが5ファイルある。ubuntu だけで検証すると **Windows でしかコンパイルされないコードの API 要求は一度も検査されない**。ローカルの clippy が `incompatible_msrv` を出さないことも、同じ理由で unix 側のコードについてしか保証していない。
- コマンドは `cargo build --workspace --all-targets --locked`。`--all-targets` にするのは、テストと example もその版でコンパイル・リンクできることを宣言の意味に含めるため。テストの**実行**までは stable ジョブが見ているので MSRV では重ねない。

### Consequences

- 良い点: `Cargo.toml` を1箇所直せば CI の検証対象が自動的に追随する。ステップ 9(MSRV 引き上げ)がワークフローの変更を伴わない。1クレートだけ MSRV を上げた場合も、割れが失敗として現れるので気づける。
- 良い点: cfg で分岐するコードの MSRV が OS ごとに、しかもリンクまで検査される。`check` では見えない Windows 固有のリンク失敗が MSRV でも捕まる。
- トレードオフ: ジョブが3つ増える(合計7ジョブ)。public リポジトリなので課金は無いが、実行時間とログの量は増える。`build` にしたぶん `check` より1ジョブあたり数十秒重い。
- トレードオフ: MSRV の意味を「コンパイル可能性」ではなく「リンクまで通る」と定義することになる。Issue の文言に忠実で、かつ実際に踏む失敗を捕まえられる側に倒した。
- トレードオフ: `cargo metadata` の実行にランナー同梱の stable cargo を使うため、MSRV ジョブが2つの toolchain を触る。読み出しに失敗したら明示的に落ちるようにして、黙って空文字で進まないようにする。

## ADR-003: `rust-toolchain.toml` は置かない

### Status

Proposed

### Context

CI で toolchain を明示するなら、リポジトリに `rust-toolchain.toml` を置いて rustup に解決させる手もある。ローカルでも同じ版が使われるという利点がある。

しかしこのプロジェクトの開発環境は Nix flake の devShell で、rustup は入っていない(`which rustup` → not found)。`rust-toolchain.toml` は rustup のシムが読むファイルなので、devShell の中では完全に無視される。置いた場合、「ローカルでは nixpkgs の 1.97.1、CI では `rust-toolchain.toml` の版」という二重の出典になり、どちらが正かがファイルからは読み取れない。

### Decision

`rust-toolchain.toml` を置かない。CI のワークフローが `rustup default stable`(stable ジョブ)と `cargo +<rust-version>`(MSRV ジョブ)で明示する。ローカルは `flake.nix` が唯一の出典であり続ける。

### Consequences

- 良い点: 「ローカルは flake.nix、CI はワークフロー」と出典が1対1で対応する。無視されるファイルを置かずに済む。
- トレードオフ: rustup を使う開発者(Nix を使わない人)がリポジトリを clone しても、toolchain の指定を受け取れない。現状そういう開発者はいないため受け入れる。

## ADR-004: 安定版のツールチェーンは固定せず、常に現行の stable を使う

### Status

Proposed

### Context

CI で stable をどう指すかに選択肢がある。

1. ランナーイメージ同梱の stable をそのまま使う — イメージの更新タイミングで版が動く。どの版だったかがログを見ないと分からない。
2. **`rustup update stable` で現行の stable にする** — 常に最新の安定版で検証する。新しい clippy lint が追加された日に、コードを1行も変えていないのに CI が赤くなりうる。
3. `1.97.0` のように固定する — 再現性は最高だが、CLAUDE.md の「安定版ツールチェーンを前提とし、`cargo clippy` を通る状態を保つ」が意味するのは「現行の安定版」であり、固定すると新しい lint に追随しない状態が静かに続く。それは本 Issue が壊しにいった「1環境でしか回っていない」構造の再生産でもある。

### Decision

`rustup update stable --no-self-update` で現行の stable に上げてから回す。版は固定しない。新しい lint で赤くなったら lint を直す(steps.md ステップ 10)。`allow` での握り潰しやツールチェーンの固定は取らない。

この決定は **fmt ジョブにも等しく掛かる**。rustfmt は版によって整形結果が変わるため、clippy が新 stable・rustfmt がイメージ同梱の旧 stable という状態だと、「CI は緑だが開発者が新 stable で `cargo fmt` すると差分が出る」というズレが CI に映らない。fmt ジョブも `rustup update stable` を踏み、使った版(`rustc --version` / `cargo fmt --version`)をログに残す。この構成では **fmt ジョブが版差で赤になることが起こりうる**(ローカルは nixpkgs の 1.97.1)。その場合の解消は clippy と同じく「現行 stable に合わせる」で、CI と同じ版の rustfmt で `cargo fmt --all` を掛け直して差分をコミットする(steps.md ステップ10)。`rustfmt.toml` に整形を抑止する設定を足すことも、rustfmt の版を固定することもしない。

### Consequences

- 良い点: 「安定版で通る」という宣言が、宣言した時点の版ではなく常に現時点の版について成り立つ。整形についても同じ版で成り立つ。
- トレードオフ: 無関係な PR が新 stable のリリース直後に赤くなることがある。原因が自分の変更でないと分かる形(clippy の lint 名がログに出る)なので、切り分けのコストは低い。
- トレードオフ: 過去の実行を厳密に再現できない。再現が必要になる場面(退行の二分探索など)では、そのとき明示的に版を指定して手元で回す。

## ADR-005: スキップの合否判定は `SkipBudget` に一本化し、CI は環境前提の直接アサートと可視化だけを持つ

### Status

Proposed

### Context

ADR-055 は「スイートを適用するテストファイルが、スキップを許容するケースの集合を環境の能力から実行時に宣言する」と決めた。`SkipBudget::record` は `SKIP` 行を出した直後に `assert!(self.allows(case))` を通すので、宣言集合の外のスキップは**そのケースの失敗**として現れる。libtest は成功したテストの stdout を握り潰すため、`--nocapture` が無いと `SKIP` 行そのものがログに出ない。Issue はこの点を懸念事項として挙げている。

「非 root unix なら許容集合はすべて空になる」という見立ては実測と合わない。`origin/main` を macOS(非 root)で `cargo test --workspace --locked -- --nocapture` に掛けると、**全 458 件 PASS・exit 0 でありながら `^SKIP ` 行が4件出る**。

- `tc_port_clock_005`(適合スイート) — `conformance_time_id.rs` の `allowed_clock_skips()` は環境を一切見ず定数 `vec!["tc_port_clock_005"]` を返す。`SystemClockHarness` が `rewind` を提供しないのは実時計というアダプターの性質であって環境の欠落ではないので、**どの OS でも恒久的にスキップされる**。HOOKS.md も TC-port-clock-005 の判定を「ハーネスが `rewind` を提供するか」としており、プラットフォームでも権限でもない。
- `pulsen-conformance` の lib ユニットテスト3件 — `SkipBudget` の仕様自体を検証するテストが `record` を直接呼ぶ(うち2件は `#[should_panic]`)。ケース名は `tc_port_clock_005_時刻の巻き戻し` / `tc_port_clock_004_時刻の前進` / `tc_port_clock_0051_別のケース` という架空の名前で、実在の適合ケースと形が区別できない。

したがって「SKIP 行が 0 件」を CI が要求すると、非 root unix でも初回から確実に赤になる。赤の原因は ADR-055 が正しく設計した振る舞いなので、条件付きステップのどれでも解消できない。

CI 側の扱いの選択肢:

1. 何もしない — Windows で権限系10件が走っていないことが誰にも見えない。
2. 期待するスキップ集合を CI にハードコードして照合する — `SkipBudget` が持つ知識を CI に複製し、区分 C の行が増えるたびに2箇所を直す。ADR-055 が「件数ではなく集合で宣言する」とした理由(宣言と実態のズレが集計で相殺されない)を CI 側で崩す。
3. 恒久スキップを除外リストに書いたうえで、unix ジョブに限り「フィルタ後の SKIP 集合が除外リストと一致しなければ失敗」を要求する。除外リストに入るのは環境非依存の恒久スキップだけで、非 root unix ではステップ3 のフィルタ適用後に残る SKIP はちょうど1件(`tc_port_clock_005`)。区分 C の行は非 root unix では**走る**ので SKIP 行を出さず、区分 C が増えても除外リストは動かない。腐るのは恒久スキップを足したときだけで、それは意図的でレビュー可能な事象。**環境由来の判断を複製しない安価な歯止めとして成立する。**採らない理由は「腐るから」ではなく、恒久スキップの宣言先が `allowed_clock_skips()` とワークフローの2箇所になり、両者を結ぶものがコンパイラにもテストにも無いこと、そして宣言集合が最も大きい Windows には適用できないこと。
4. **スキップの正しさは `SkipBudget` に委ね、CI は「宣言集合が痩せる環境で回っていないこと」という前提そのものを検査する。** SKIP 行は可視化するが合否には使わない。

スキップ件数は「宣言が正しいか」の proxy にすぎず、観測結果を期待値に写す構造になりやすい。4 は前提(非 root であること)を直接見るので循環しない。Issue 本文の「root コンテナで回すなら宣言値の見直しが要る」への直接の答えでもある。

`--nocapture` は SKIP 行を取り出すために要るが、副作用として `pulsen-conformance` の `#[should_panic]` 2件が出す「宣言外スキップ」のパニックメッセージもログへ素通しになる。ここに `RUST_BACKTRACE: 1` を全ジョブへ掛けると `SkipBudget::record` → `CaseOutcome::report` のスタックトレースまで付き、**緑の実行のログに本物と見分けのつかない失敗が2件常駐する**。赤のときに人が読むのはサマリーではなくログのほうなので、ここを汚すのはステップ3 が架空ケースをサマリーから除いたのと同じ理由で避けたい。

### Decision

- テストは `cargo test --workspace --locked -- --nocapture` で回し、出力を `test.log` に残す(`--nocapture` が無いと `SKIP` 行が握り潰される)。
- **スキップの合否判定を CI は持たない。** 宣言集合の外のスキップは `SkipBudget` がそのケースの失敗として落とす。CI が proxy で二重化しない。
- **CI が独自に守るのは環境前提のほう。** unix ランナーでは実行ユーザーが root でないこと(`id -u` が 0 でない)を各 stable ジョブの先頭で直接アサートし、成立しなければ即座に失敗させる。`container:` は使わない。
- **その唯一の判定を fail-open にしない。** `id -u` の出力は代入で受けてから検査する。`if [ "$(id -u)" -eq 0 ]` の形だと、`id` 自体が失敗しても `-e` が効かない位置なので `[` が「整数でない」で偽になるだけで、検査が空振りしたままステップが成功する。代入形なら `id` の失敗がその場で落ち、`0` でも数値でもない出力も失敗として扱える。判定できなかったときに通す側へ倒すと、守っているのは前提ではなく「前提を読めたときだけの前提」になる。
- **可視化は失敗させずに行う。** 全 OS で `test.log` の `SKIP ` 行をジョブサマリーに列挙する。ただし `pulsen-conformance` の lib ユニットテストの区間は除外する — 架空のケース名が実在の行と混ざると、サマリーを読む人間が「走らなかった適合ケース」を誤って数える。
- **除外した件数もサマリーに出す。** 除外の単位はケース名ではなくテストバイナリの区間なので、将来そのバイナリが実在ケースのスキップを出せば、それはサマリーから黙って消える。可視化しか役割を持たない機構なので、消えたことを合否判定で捕まえる経路が無い。件数が 3 から動くことが唯一の合図になる。区間で判定すること自体は、ケース名を列挙するより腐りにくいので変えない。
- **ログの色は保ったまま、抽出側で ANSI を落とす。** `CARGO_TERM_COLOR: always` を付けると cargo の `Running` 行は `\033[1m\033[92m     Running\033[0m …` になり、行頭が空白ではなく ESC で始まる(実測)。ANSI を残したまま区間を判定すると除外が丸ごと効かず、色なしなら1件のサマリーが色ありでは4件になる。色を捨てて `CARGO_TERM_COLOR` を外す手もあるが、**赤を読むのはサマリーではなくログのほう**で、`error:` が着色されているかどうかは Actions の UI で読む速さに直に効く。色は Actions の UI 向け、抽出は機械向けと役割が違うだけなので、両立できる形 — 抽出の照合用に ANSI を落とした行を作ってから判定する — を採る。`SKIP ` 行と `test result:` 行は libtest の出力でパイプ越しには色が付かない(実測)ため、ANSI が影響するのは `Running` 行の判定だけである。
- **行頭に錨を打たない。** ANSI を落としても行頭一致では足りない理由がもう1つある。`--nocapture` 下の libtest は改行を伴わない進捗行 `test <名前> ... ` を先に書き、その改行待ちの行末に別スレッドのテストの stdout が載る。`SKIP ` 行・`Running` 行・`test result:` 行はいずれも進捗行に連結した姿で現れうる(Windows で実測)。連結した `SKIP ` は抽出にも除外にも入らず、連結した `Running` は区間の切り替えを取りこぼす。連結の位置は「`... `」の直後に限らない — 判定の綴りに直付いた `okSKIP tc_port_clock_004_…` の形が実在する(run 31657976822 の Windows)。**位置を列挙しても網羅にならないので、3種類とも行のどこに現れても拾う。** `SKIP` は見つけた位置から行末までを1件の同一性に使う。区間は `Running` に加えて `Doc-tests` でも切り替え、`test result:` で閉じる — 開いたままにすると最後の `Running` 以降の SKIP がすべて除外側へ回る。
- **偽陽性と偽陰性を対称に扱わない。** この機構は可視化しか役割を持たないので、誤って1行余分に出すことと、黙って1行消すことは重さが違う。後者は他に検出経路がない。入口も区間の判定も、迷ったら「拾う・開く(＝列挙される)」側にしか倒れない形にする。
- **「SKIP 0 件」と「テストが走っていない」を同じ表示にしない。** 報告は `if: always()` で走るため、build が落ちた実行でも表示が出る。テスト結果行(`^test result:`)の有無で「到達していない」「走っていない」「走ったが 0 件」を区別する。可視化が目的である以上、最も紛らわしい局面(条件付きステップ6 を回している間)で嘘の「なし」を出すなら可視化になっていない。
- **`RUST_BACKTRACE` は設定しない。** 上記の意図的なパニック2件にスタックトレースが付くのを避ける。テストの失敗は libtest がメッセージとソース位置を出すので、バックトレースが要るのは依存クレート内部でパニックしたときに限られ、そのときは手元で `RUST_BACKTRACE=1` を付けて再現する。あわせて、この2件が緑でも出ることをワークフローの why コメントに残す。
- **Windows の期待スキップ集合は、実行前に HOOKS.md から予測して steps.md に書き、実行後に観測と突き合わせる。** 観測値を期待値へ書き写す順序は取らない。差分が出たら予測が誤っていた理由を先に特定し、それから期待値を更新する。
- `cargo test --test <名前>` を使わず `--workspace` のままにする。単一テストターゲット指定では example がビルドされず、ロック保持のフィクスチャが消えてロック系5件が「宣言済みスキップ」に化ける(Issue 補足3点目)。`--workspace` を選ぶこと自体がこの経路の構造的な回避であり、`SkipBudget` の許容集合には入れない(HOOKS.md の方針)。
- これらの理由をワークフローの why コメントとして残す。

### Consequences

- 良い点: 判断主体が `SkipBudget` の1箇所に保たれ、CI に知識が複製されない。恒久スキップが増えても CI 側の手当てが要らない。
- 良い点: 「静かな緑」を作る条件(root 実行・単一テストターゲット指定)が、やらない理由つきでワークフローに記録される。前提の検査は観測結果と独立なので、何件スキップしても判定が循環しない。
- トレードオフ: 宣言集合そのものが不当に広げられた場合(`allowed_skips()` が環境を見ずに大きな集合を返すよう書き換えられる等)、CI は気づかない。これはテストコードのレビューで見る範囲とし、CI の役割にはしない。
- トレードオフ: **マージ後の環境退行に機械的な歯止めが無い。** 非 root アサートが塞ぐのは権限系の述語だけで、`tmpdir_outside_repository()`(ランナーの一時ディレクトリがリポジトリ配下へ移る)や `holder_program()` 経由の合図タイムアウトが false へ倒れれば、許容集合が黙って広がって CI は緑のまま進む。守れるのは PR の初回実行を人が読む範囲まで。サマリーの SKIP 一覧には現れるので、実際に退行を踏んだ時点で選択肢3(unix 限定の集合一致判定)を足す判断をそのとき行う。
- トレードオフ: `--nocapture` によりテストの標準出力がすべてログに出る。既存のテストで `println!` するのは `SkipBudget::record` だけなので実害は小さい。
- トレードオフ: `RUST_BACKTRACE` を設定しないので、依存クレート内部でパニックした場合は手元で再現するまでスタックが見えない。緑のログに常駐する偽の失敗を消すほうを採った。
- トレードオフ: サマリーからの除外を cargo が出す `Running unittests src/lib.rs (…pulsen_conformance-…)` の区間で行うため、cargo の出力形式に依存する。形式が変わっても混ざるのは架空の3件だけで、合否には影響しない。
- トレードオフ: `--nocapture` 下の libtest は進捗行とテストの stdout を同じストリームへ並行に書くため、**行の切れ目が保証されない**。行のどこでも拾う形にしたのはこれに対する対処だが、代償として本文に綴りを含むメッセージを誤って拾いうる。`SkipBudget` のパニックメッセージの文言が変われば起きる。可視化にしか使わない機構なので、その場合の被害はサマリーに1行余分に出ることに留まる。件数が3から動いたときに読み手が見るのは、実在ケースの巻き込みと、この誤検出の両方である。
- トレードオフ: 区間で除外する以上、そのバイナリが実在ケースのスキップを出すようになれば一緒に落ちる。除外件数をサマリーに出すので、除外が広がったことは件数の変化として見える。読む人がいて初めて効く歯止めであり、機械的な検出ではない。

## ADR-006: 依存のキャッシュは入れず、`--locked` で依存グラフを固定する

### Status

Proposed

### Context

Rust の CI ではキャッシュがほぼ定番になっている。選択肢:

1. `Swatinem/rust-cache` — 事実上の標準だが第三者製 Action(ADR-001 の方針に反する)。
2. `actions/cache`(公式)で `~/.cargo/registry` と `target/` を保存 — キーの設計・陳腐化・サイズ上限の管理が要る。特に `target/` は OS ×ジョブごとに数百 MB になり、古い成果物を引きずった赤の切り分けが難しい。
3. `actions/cache` で `~/.cargo` のレジストリだけ — 依存のダウンロード(45クレート)を省ける。効果は10〜20秒程度。
4. **キャッシュを入れない**。

実測(macOS / rustc 1.97.1)では、クリーンな `cargo clippy --workspace --all-targets` が 55 秒、テスト実行の合計が約 12 秒。依存グラフは45クレートと小さい。1ジョブあたりの所要はチェックアウト・toolchain 導入を含めても数分に収まる見込み。

### Decision

キャッシュを入れない。代わりに **依存グラフに触れる cargo コマンドすべてに `--locked` を付ける** — `build` / `test` / `clippy` / `metadata`。MSRV ジョブが版数の読み出しに使う `cargo metadata --format-version 1 --no-deps` も含める。`--no-deps` は依存解決を行わないので付けなくても結果は変わらないが、依存グラフに触れる側で例外を作ると「どの cargo コマンドに付けるか」を都度判断することになる。

`cargo fmt` にだけは付けない。**受け付けないため**で(`error: unexpected argument '--locked' found`。実測)、方針の例外ではない — `cargo fmt` は rustfmt へのラッパーで依存解決を行わず、`--` の後ろは rustfmt のオプションとして解釈される。

キャッシュの再検討は「stable ジョブの1回が10分を超える」ようになってから行う。そのときは公式の `actions/cache` でレジストリのみを対象にする(`target/` は対象にしない)。

### Consequences

- 良い点: ワークフローが短く、赤の原因がキャッシュの陳腐化である可能性を最初から排除できる。第三者製 Action がゼロという ADR-001 の方針が保てる。
- 良い点: `--locked` により、CI が検証する依存グラフが `Cargo.lock` と厳密に一致する。ADR-002 の MSRV 検証は「このロックファイルの依存グラフが 1.89 でコンパイルできる」という意味になる。ロックファイルの更新漏れは全ジョブの即時失敗として現れる。
- トレードオフ: 毎回全依存をダウンロード・コンパイルする。現在の規模では許容範囲で、依存が増えたら再検討する。
- トレードオフ: 依存を1つ足すだけの PR でも全ジョブがフルビルドする。

## ADR-007: ジョブは fmt 1つ + OS マトリクス2組に分け、clippy は test ジョブへ同居させる

### Status

Proposed

### Context

Issue が求めるのは `build` / `test` / `clippy --all-targets -- -D warnings` / `fmt --check` / MSRV / OS マトリクス。分割の粒度に選択肢がある。

1. 1ジョブに全部を詰める — マトリクスにすると fmt が3回走る。どのコマンドで落ちたかはログを追えば分かるが、PR のチェック一覧では見えない。
2. コマンドごとにジョブを分ける(build / test / clippy を別ジョブ)— チェック一覧は読みやすいが、clippy ジョブが依存を丸ごと再コンパイルする(キャッシュを入れない以上、これは純粋な重複)。
3. **プラットフォーム非依存なものだけ分離し、同じ toolchain と `target/` を共有できるものは同居させる。**

### Decision

- `fmt`(ubuntu 1つ): 現行 stable の rustfmt で `cargo fmt --all --check`。整形結果は OS に依存せず、rustfmt の `newline_style` は既定 Auto なので Windows の CRLF チェックアウトでも結果が変わらない。3回走らせる意味がない。
- `test`(3 OS): 前提の検査 → build → test → スキップ報告 → clippy。`target/` を共有できるので clippy が依存を再コンパイルしない。順序は「動くか」→「綺麗か」。
- `msrv`(3 OS): `cargo build --all-targets` のみ(ADR-002)。
- 全マトリクスに `fail-fast: false` を付ける。1 OS の失敗で他をキャンセルすると、「Windows だけの問題か、全 OS の問題か」を1回の実行で判断できない。
- `timeout-minutes` をジョブに付け、ハングを打ち切る。
- **`run` のシェルはワークフロー既定(`defaults.run.shell: bash`)で全ジョブ・全ステップに揃える。** 指定の無い `run` は Windows でだけ pwsh になるため、放っておくと同じジョブの中で2種類のシェルが混ざる。`--` の扱い・終了コードの伝播・リダイレクトの意味がステップごとに変わる状態は、Windows の赤を切り分けるときに変数を1つ増やす。bash に寄せれば `-eo pipefail` が全ステップに効き、`tee` を挟むステップだけの特例も要らなくなる。Windows の bash は Git for Windows 同梱のもので、`$GITHUB_STEP_SUMMARY` / `$GITHUB_OUTPUT` への追記も msys のパス変換が効くので支障はない。

### Consequences

- 良い点: 合計7ジョブで、PR のチェック一覧が「fmt / 3 OS の stable / 3 OS の MSRV」と読める。重複コンパイルが無い。
- トレードオフ: test ジョブが落ちたときに build / test / clippy のどれで落ちたかはログを開かないと分からない。ステップ名で判別できるので実害は小さい。
- トレードオフ: `fail-fast: false` により、明らかに全 OS 共通の失敗でも3 OS 分の時間を使う。切り分け情報のほうが価値が高い。

## ADR-008: OS 差の吸収は probe と許容集合で表し、層を越える場合は別 Issue へ切り出す

### Status

Proposed

### Context

本 Issue は「CI を回して落ちたら吸収する」という条件付き作業を含む。何が落ちるかは実行するまで確定しないため、完了条件を「CI が緑になるまで」と書くことになる。この書き方には上限が無く、2つの形で膨らみうる。

- **層を越える膨張**: Windows の `NamedTempFile::persist` が共有違反を返す場合、短い再試行で収まらなければ `write_atomic` の置換方式そのもの、ひいては永続化ポートの契約に踏み込む。そこまで行くと「CI の導入」という Issue が別テーマの設計変更を巻き込み、PR の読み手にスコープが見えなくなる。
- **無期限化**: 「Windows では契約自体が成立しない」という結論に至ったとき、AC-2 の「3つとも緑」を満たす方法が無くなり、Issue が開いたまま残る。

停止規則を「振る舞いを変えるかどうか」で書くと境界が定まらない。`write_atomic` の中に `persist` の再試行を足すのは、`util/atomic.rs` の振る舞いを変えることでもあるし、置換の**方式**は変えないことでもある。どちらとも読めるので、境界は「変えるか」ではなく**何を変えるか**で引く必要がある。判定者と判定タイミングも決めないと、条件付きステップは「緑になるまで」を無期限に回せてしまう。

吸収の表し方にも選択肢がある。

1. `cfg(windows)` で決め打ちに分岐する — 「その環境では成立しない」を静的に宣言することになるが、実際に成立するかは環境の能力の問題であって OS の問題ではない。ADR-055 が「環境の能力から実行時に決める」とした理由をそのまま崩す。
2. **probe を足して `SkipBudget` の許容集合に入れる** — 既に ` .yaml` フィクスチャに対して採っている手。同じ形が他のケースにも一般解として使える。
3. `continue-on-error: true` で Windows ジョブを緑に見せる — 「スキップを緑と誤認しない」という本 Issue の趣旨に真っ向から反する。ジョブ単位で同じ誤認を作る。

### Decision

- **吸収は probe + 許容集合で表す。** 実測の結果 Windows で前提を作れないと判明した場合、`cfg(windows)` の決め打ちではなく「その能力があるか」を実際に試す probe を足し、その結果で `SkipBudget` の許容集合に加え、HOOKS.md に行を足す。これを条件付きステップ全体に掛かる原則とする。
- **停止規則が掛かる範囲**: **OS 差に由来する赤(ステップ6〜8)だけ。** MSRV ジョブの赤(ステップ9)と、現行 stable の clippy / rustfmt との差による赤(ステップ10)は別の軸で、この規則の対象外とする。前者は「特定の環境で契約が成立するか」という設計の問題だから射程を絞る必要があるが、後者2つは対象ファイルが原因側で決まる(MSRV 非対応の API を使っている箇所・lint が指摘した箇所・rustfmt が整形し直す全域)ので、層で線を引く意味がない。ステップ9 は `crates/pulsen/src/cli/` や `crates/pulsen/src/application/`、`rust-version` を上げるなら `Cargo.toml` と `.adr/022` / `.adr/023` を、ステップ10 の `cargo fmt --all` は `crates/pulsen-domain/` を含むソースツリー全域を正当に触る。これらを層の逸脱と読まない。
- **停止規則の判定者とタイミング**: **OS 差由来の CI が赤になった時点で、Phase 2 の実装者が判定する。** 判定するのは「その赤を消す修正が `crates/pulsen/src/util/` / `crates/pulsen/src/adapter/` / `crates/pulsen/tests/`(フィクスチャ)/ `crates/pulsen-conformance/src/` に収まるか」。収まると判定したらそのまま直す。収まらないと判定したら**その場では直さず**、別 Issue を起票して当該 OS を下の撤退条件に載せる。判定の結果(どちらに倒したか、その理由)は PR 本文に残す。迷う場合は切り出す側に倒す — 本 Issue の目的は CI を入れることであって、置換戦略を設計し直すことではない。
- **境界を具体で引く。** 上記の「収まるか」は次のように読む(OS 差由来の赤に限る)。
  - **本 Issue で扱う**: `persist` を使う置換手順を保ったまま、失敗時の再試行やエラー分類をその手順の中に足す。フィクスチャの待ち時間・環境変数の渡し方を変える。probe を足して `SkipBudget` の許容集合と HOOKS.md に反映する。
  - **切り出す**: `persist` を使わない置換方式への変更。`write_atomic` / `rename_atomic` のシグネチャや契約(失敗時に一時ファイルを残さない・対象が変わらない・読み手はロックなしで常に一貫した内容を見る)の変更。ポート trait の定義変更。`crates/pulsen-domain/` の変更。
- **撤退条件**: probe + 許容集合でも表せず、別 Issue へ切り出した結果ジョブが赤のまま残る場合、`continue-on-error` で緑に見せることはしない。**赤のまま残るジョブだけ**をマトリクスから外し、外した理由と切り出した Issue 番号をワークフローの why コメント・PR・Issue #10 のコメントに残したうえで #10 を閉じる。
  - 外す単位はジョブであってプラットフォームではない。stable の Windows が緑にならない場合に外すのは **stable の Windows だけ**で、MSRV の Windows は残す — MSRV ジョブは `cargo build --all-targets` だけでテストを実行しないので、テスト・フィクスチャ由来の赤を持たない。MSRV の Windows がコンパイルできない場合はステップ9 の対象で、そこでも解消できないときに初めて MSRV の Windows も外す。
  - 撤退後のジョブ数は、stable の Windows だけを外したなら6、MSRV の Windows も外したなら5。AC-1 の「計7」はこの場合に読み替える。
- どの出口を採る場合も、テストを緩めること(アサーションの削除・`#[ignore]`・期待値の弱化)は取らない。

### Consequences

- 良い点: 条件付き作業の射程が明示され、「緑になるまで」が無限の作業を意味しなくなる。判定の起点(CI が赤になった時点)が決まっているので、判断を先送りしたまま試行を繰り返す形にならない。Issue が閉じられる状態が常に存在する。
- 良い点: 吸収の形が ADR-055 と揃うため、`cfg` 分岐が増える圧力を受け止める先が1つに定まる。
- 良い点: 停止規則が「変えるか」ではなく「何を変えるか」で書かれているので、ステップ7 が指示する `write_atomic` への再試行追加が規則に抵触するかを読む人ごとに判断しなくてよい。
- トレードオフ: 撤退した場合、検証範囲が Issue の当初の狙いより狭くなる。ただしマトリクスから外した事実と理由がワークフロー・PR・Issue #10 に残るので、「検証済み」と誤読される形にはならない。
- トレードオフ: 境界の列挙は現時点で想定できる失敗に基づくもので、想定外の失敗には当てはまらない。その場合は「迷ったら切り出す」に倒す。

## ADR-009: 「使わない道具」を why コメントに書くとき、その道具の綴りをワークフローに残さない

### Status

Accepted

### Context

ADR-001 と ADR-005 は「使わないこと」を3つ決めている — `sort` を使わない、ジョブをコンテナで走らせない、単一のテストターゲットを指定した実行にしない。steps.md はこれらの理由をワークフローの why コメントに残すよう指示している。

一方 testing.md はこの3つを grep で確認する形にしている(`grep -n "sort"` / `grep -n "container:"` / `grep -n -- "--test "` がいずれも 0 件)。理由を書くために `container:` は使わない・`cargo test --test <名前>` は使わない、と綴りをそのまま書くと、**「使っていないこと」を確かめる grep が why コメント自体に当たる。**確認手段が壊れると、その後は目視で「これはコメントだから」と毎回除外する運用になり、実際に使い始めたときの検出力が落ちる。

コメントを消して理由を失う / grep のパターンを「コメント行を除く」形に複雑化する / 綴りを避けて理由だけ残す、の3択になる。

### Decision

理由は残し、綴りは残さない。ワークフローの why コメントでは日本語の言い換えを使う。

- `sort` → 綴りを一切書かない(重複除去は awk の `!seen[line]++` に寄せてあるので、言及する必要自体が無い)
- `container:` → 「ジョブのコンテナ指定は使わない(コンテナのランナーは root で走る)」
- `cargo test --test <名前>` → 「単一のテストターゲットを指定した実行に切り替えると example がビルドされず…」

読み手が失うのは綴り1語で、得るのは「使っていないことを機械で確認できる状態」である。前者はコメントの日本語から復元できるが、後者は綴りが1つでも混ざると復元できない。

### Consequences

- 良い点: `sort` / コンテナ実行 / 単一テストターゲット指定を後から誰かが持ち込んだとき、grep が 0 件でなくなることで気づける。可視化の仕組み(ADR-005)を CI 自身が壊さない。
- トレードオフ: ワークフローを読む人が「どのキーを避けたのか」を綴りで検索できない。この ADR と testing.md が対応表になる。
- トレードオフ: 将来 why コメントを書き足すときに同じ配慮が要る。避ける対象が「使わないと決めた道具の綴り」に限られるので、判断は機械的。

## ADR-010: `write_atomic` の置換は、OS が返した拒否コードで分類したうえで上限つきに再試行する

### Status

Accepted

### Context

Windows の stable ジョブで `util::atomic::tests::読み手は旧内容か新内容のどちらかだけを観測する` が `Os { code: 5, kind: PermissionDenied }` で落ちた。読み手が `fs::read` でハンドルを開いている最中に `NamedTempFile::persist`(`MoveFileEx`)を掛けると、対象を開いている他のハンドル(読み手・ウイルス対策のスキャン)によって置換が拒まれる。unix の `rename` は開いているハンドルに影響されないため、この経路は Windows でしか現れない。

ADR-008 の境界では「`persist` を使う置換手順を保ったまま、失敗時の再試行やエラー分類をその手順の中に足す」は本 Issue で扱う側にあたる。置換方式・シグネチャ・契約は変えない。

再試行の掛け方に選択肢がある。

1. すべての失敗を再試行する — 権限そのものの不足・容量の不足のように時間で解けない失敗まで、上限を使い切るぶんだけ遅らせる。呼び出し側が受け取るエラーは同じでも、返るのが遅くなる。
2. `io::ErrorKind::PermissionDenied` で分類する — unix の `rename` が返す `EACCES` も同じ `kind` に落ちるため、時間で解けない失敗を 1 と同様に遅らせる。unix の挙動を変えないという条件に反する。
3. **OS が返した生のコードで分類する** — Windows の `ERROR_ACCESS_DENIED`(5)/ `ERROR_SHARING_VIOLATION`(32)だけを「待って解ける拒否」とする。ただしこの2つの数値は unix では別の errno(`EIO` / `EPIPE`)なので、OS を問わず同じ数値で分類することはできない。

分類を OS ごとに変える以上、`cfg` が要る。ADR-037 は「条件付きコンパイルではなく std の定数から選ぶ」を採っているが、それが成立するのは分岐する値が std に定数として出ている場合(`MAIN_SEPARATOR`)に限られ、Win32 のエラーコードは std に無い。`util/atomic.rs` は既に `sync_dir` を `#[cfg(unix)]` / `#[cfg(not(unix))]` で分けている共通ユーティリティであり、CLAUDE.md が「アダプター層に隔離する」と言う対象の中にある。

### Decision

`write_atomic` の `persist` を、上限つきの再試行に置き換える。

- 分類は `transiently_denied` に閉じ、`#[cfg(windows)]` 版が `ERROR_ACCESS_DENIED` / `ERROR_SHARING_VIOLATION` だけを真とし、`#[cfg(not(windows))]` 版は常に偽を返す。**unix では再試行の経路に一度も入らない。**
- 上限は10回、待ち時間は 1ms から試行ごとに倍にする(累計で最大 511ms)。**待ちの列は `retry_waits()` という純粋関数に切り出し、再試行ループはこの列だけを消費して眠る。** 公称の 511ms はこの列の和であり、doc と ADR がこの数値を根拠にするときの唯一の出典である(ユニットテスト `再試行に費やす待ちの合計は公称する上限と一致する` が一致を固定する)。上限に達したら**打ち切りを表す独自のエラーに差し替えず、OS が返した拒否をそのまま返す。**
- `persist_with_retry` は分類を引数に取る。打ち切りの振る舞い(上限で止まる・元のエラーを返す)を、エラーがどう分類されるかと独立に、どのプラットフォームでも検証できるようにするため。この seam が無いと、再試行の上限を検証できるのは Windows だけになる。
- `rename_atomic` には同じ再試行を入れない。実測で赤になっていない箇所を、想定だけで変えない(plan.md「今回の赤を消すこと以外の改善をしない」)。適合スイートは Windows でまだ一度も走っていないため、`archive` 側(TC-port-task-repository-044)が同じ原因で落ちる可能性は残る。落ちたらそのときに同じ形を当てる。
  - **この項目は ADR-012 が置き換えた。** 「赤になっていない」の根拠が「観測されていない」ことだったため、判断の前提そのものが成り立っていなかった。`rename_atomic` にも同じ再試行が掛かっている。

### Consequences

- 良い点: `write_atomic` のシグネチャと契約(失敗時に一時ファイルを残さない・対象が変わらない・読み手はロックなしで常に一貫した内容を見る)が変わらない。読み手を待たせる方向(ロックの導入)に倒さずに済む。
- 良い点: unix では分類が常に偽なので、挙動が実装前と一致する。
- 良い点: 再試行の上限と「元のエラーを返す」ことが、Windows を待たずにユニットテストで検証される。
- トレードオフ: Windows で**時間で解けない** `ERROR_ACCESS_DENIED` を踏んだ場合、失敗が最大 511ms 遅れる。Win32 のコードからは「読み手が開いている」と「権限が無い」を区別できないため、この取り違えは分類の精度では消せない。上限を持つことで、遅延が有界であることだけを保証する。
- トレードオフ: **511ms は1回の呼び出しあたりの上限で、呼び出し側で合成される。** `save_degraded` は読んでから書くので最大2倍、`list` はエントリ数 N だけ読むので最大 N 倍になる。有界であることは変わらないが、境界はポートの操作ごとに数え直す必要がある。
- トレードオフ: **短い待ちは OS のタイマー粒度に丸め上げられる。** Windows の既定は約 15.6ms 刻みなので、1ms・2ms・4ms と刻んだ前半の待ちは実際にはそれより長くなる。再試行が実際に発火する唯一のプラットフォームでの実測が公称の 511ms を上回る、という向きにだけズレる。
- トレードオフ: 分類を引数で渡すぶん、呼び出し箇所1つに対して関数が1つ増える。
- トレードオフ: 一時ファイルを抱えたままの時間が、`persist` の前後の数マイクロ秒から再試行の間ずっと(最大 511ms)に伸びる。契約「失敗した場合は一時ファイルを残さない」は関数が返る限り守られるが、その途中でプロセスが落ちた場合は契約の対象外で、掃除する主体もいない。`list` は `TaskFilePath::parse_file_name` で命名形式に合わないエントリを弾くので、残った `.tmpXXXX` が走査に混ざることはない。
- 良い点: 上限が壁時計ではなく待ちの列の和として検証される。バックオフの伸び幅・初回の待ち・回数のどれを変えても、ランナーの速さに関わらずユニットテストが落ちる(`*2` を `*4` にすると実際の予算は約87秒になるが、これを検出する歯が以前は無かった)。

## ADR-011: 絶対パスのフィクスチャは `MAIN_SEPARATOR` から組み立て、綴りが変わる値は期待値から追い出す

### Status

Accepted

### Context

Windows の stable ジョブで `adapter::task_file::tests` の5件が `NotAbsolute { given: "/abs/path" }` で落ちた。`registered()` フィクスチャが `RepoPath::parse(PathBuf::from("/abs/path"))` を使っており、`/abs/path` は Windows では絶対パスにならない。ドメインの検証は正しく、誤っているのはフィクスチャの POSIX 決め打ちのほうである。

ワークスペース全体を走査したところ、絶対パス制約(`RepoPath` 等の `parse`)に POSIX 決め打ちの文字列を渡していたのは**この1箇所だけ**だった。他の6箇所(`task/path.rs`・`task/task.rs`・`task/degraded.rs`・`task/attempt.rs`・`application/home.rs`・`doubles/tests.rs`・`tests/register_task.rs`)は既に `std::path::MAIN_SEPARATOR` を見て `C:\` と `/` を選ぶ形になっている。`/tmp/wt` や `/home/u/.pulsen/...` のような残りのリテラルは、絶対性を検査されない値(表示名の導出元・レンダリング結果の比較対象)で、期待値も同じ綴りなので Windows でも成立する。

問題は 5 件のうち1件、`登録直後のタスクは整形されたjsonとして書かれる` が JSON 全体を文字列リテラルで比較していることにある。パスをプラットフォーム依存に直すと、その綴り(`C:\abs\path` は JSON では `"C:\\abs\\path"`)が期待値に現れる。

1. 比較を構造比較(`serde_json::Value` 同士)に落とす — 整形(pretty print・キー順)を検査しなくなる。テスト名が表しているのは整形のほうなので、緩めることになる。
2. 期待値も `MAIN_SEPARATOR` で分岐させ、JSON 全体を2通り持つ — 整形の期待値が二重化し、片方だけ直す事故が起きる。
3. **期待値のリテラルにはプレースホルダーを置き、綴りだけを差し込む。**

### Decision

- フィクスチャは既存の作法に合わせ、`absolute(&["abs", "path"])`(`MAIN_SEPARATOR` から組み立てる)で作る。
- 整形の期待値では `repo` の値を `<repo>` と書き、`serde_json::to_string` で符号化した実際の綴りに置換してから比較する。整形(インデント・キー順・末尾改行)は1通りのリテラルのまま検査され、プラットフォームで変わる部分だけが期待値から出る。

### Consequences

- 良い点: 整形の検査を緩めずに、絶対パスの綴りだけをプラットフォームに委ねられる。
- 良い点: 差し込む綴りを `serde_json` に作らせるので、期待値の側でエスケープを手書きしない。
- トレードオフ: 期待値のリテラルがそのままファイルの中身と一致しなくなり、読み手は `<repo>` が何に置き換わるかを1行下の `.replace` から辿ることになる。

## ADR-012: `rename_atomic` にも同じ再試行を掛け、分類と上限を1つのループに集約する

### Status

Accepted

ADR-010 の最後の項目(`rename_atomic` には同じ再試行を入れない)を置き換える。

### Context

ADR-010 は「実測で赤になっていない箇所を想定だけで変えない」として `rename_atomic` を対象外にし、`archive` 側(TC-port-task-repository-044)が落ちたらそのとき同じ形を当てる、と書いた。この判断の前提は「Windows の実測がその箇所まで到達している」ことだが、Windows の stable ジョブは `-p pulsen --lib` の6件で停止しており、**適合スイートは一度も走っていない**。したがって 044 は「赤になっていない」のではなく「まだ観測されていない」。

plan.md のリスク欄は TC-port-task-repository-042(`save` → `write_atomic`)と TC-port-task-repository-044(`archive` → `rename_atomic`)を**同一原因の2つの現れ方**として対で挙げ、「ユニットテストだけを直しても適合スイート側の赤は残るので、両方を同じ原因として扱う」と明記している。042 は `write_atomic` の修正で塞がったが、044 の経路(`fs::rename` = `MoveFileEx`)は共有違反に対して `persist` と同じ振る舞いをする。原因が同一であることが分かっている経路を、観測の順番だけを理由に次の実行へ送ると、CI を1往復増やして同じ修正をもう一度書くことになる。

ADR-008 の境界では、置換・移動の手順を保ったまま失敗時の再試行を足すことは本 Issue で扱う側にある。シグネチャ・契約・置換方式は変えない。

再試行を2箇所へ広げるときの形に選択肢がある。

1. `rename_atomic` の中に同じループを書く — 分類も上限もバックオフも二重化する。CLAUDE.md の「アトミック性・排他が要る操作は共通のユーティリティに集約し、個別に再実装しない」に反する。
2. `persist_with_retry` を `fs::rename` も扱えるよう拡張する — 名前が実態と合わなくなり、呼び出し側が「置換なのか移動なのか」をフラグで渡すことになる。
3. **再試行のループだけを切り出し、`persist_with_retry` / `rename_with_retry` を薄い当て先として残す。**

3 の障害は `NamedTempFile::persist` が一時ファイルを**消費し、失敗したときだけ返してくる**ことで、`FnMut() -> io::Result<T>` の形の共通ループには載らない。載せるには一時ファイルを `Option` に入れて呼び出しごとに取り出す形になり、不変条件違反でないところに `unwrap` が生まれる。

### Decision

- 再試行のループを `retry_while_transient` に切り出す。試行は失敗時に「次の試行へ持ち越す状態」をエラーと一緒に返す(`Result<T, (io::Error, S)>`)。`persist` は `S = NamedTempFile`、`fs::rename` は `S = ()` になる。状態を型引数にすることで、消費する操作としない操作を同じループに載せつつ `Option` と `unwrap` を持ち込まない。
- `persist_with_retry` と `rename_with_retry` は分類を引数に取る薄い当て先として残す。ADR-010 が seam を置いた理由(打ち切りの検証を分類から独立させ、全プラットフォームで走らせる)は移動側にも同じく要る。
- 分類は `transiently_denied` の1つのままにする。Windows で置換と移動を拒む条件は同じ(他のハンドルが対象を開いている)なので、コードの組を分ける根拠がない。unix では引き続き常に偽で、`rename_atomic` は再試行の経路に一度も入らない。
- 上限の定数は `MAX_ATTEMPTS` とする。置換だけを指す名前が移動にも掛かる状態にしない。値(10回・1ms から倍々)は分類と同じく1箇所に置く。
- 上限は `NonZeroU32` で持つ。上限は「1回は試みる」を含むので、0 を型で表現不能にし、数え上げ側から引き算を消す。

### Consequences

- 良い点: 044 が Windows で最初に走る時点で既に吸収されている。同じ原因での往復が1回減る。
- 良い点: 分類・上限・バックオフの出典が1箇所に保たれる。片方だけ値が動く事故が起きない。
- 良い点: 移動側の打ち切りも、`write_atomic` 側と同じ形のユニットテスト2件で全プラットフォームから検証される。
- 良い点: 分類の seam を `read_atomic` にも置き(`read_with_retry`)、3つの入り口の形が揃った。どの経路でも上限の検証を分類から独立に書ける。
- トレードオフ: **分類が空である unix では、公開関数が再試行に入る様子を原理的に観測できない。** そのためテストを3つに分ける。(1) `transiently_denied` の真偽そのもの — 期待値を `cfg!(windows)` から導くので全 OS で走り、分類の中身が動けばどの OS でも落ちる。(2) `persist_with_retry` / `rename_with_retry` / `read_with_retry` が上限内で解ける拒否を吸収すること — 阻害要因は別スレッドが取り除き、公開経路そのものを呼ぶ。(3) 公開関数が時間で解けない拒否に再試行の予算を使わないこと — 公開関数が実際に返したエラーを同じ分類に掛け、費やす予算が 0 であることを見る。経過時間との比較にはしない。壁時計で測ると判定の基準がランナーの速さに依存し、遅い Windows ランナーで `NotFound` の往復が 511ms を超えれば実装と無関係な赤になる。(2) の阻害要因を分類器の副作用で取り除く形には戻さない。最終試行では分類器が呼ばれないため、そこでは状況が変わらず、テストが検証するものが「再試行の吸収」から「分類器がいつ呼ばれるか」へすり替わる。
- トレードオフ: 実測より先に手を入れることになる。ADR-010 が避けた「想定で変える」に一歩寄るが、042 で同一原因が実測済みであることと、plan.md が両者を対として扱っていることを根拠とする。
- トレードオフ: 共通ループが型引数を2つ持つ。`S` は `persist` の都合(一時ファイルを消費し、失敗したときだけ返す)、`T` は読み取りの都合(値を返す)から来ており、どちらにも実際の呼び出し元がある(ADR-013)。呼び出し側が見るのは3つの薄い関数だけなので、この都合は `util/atomic.rs` の中に閉じる。

## ADR-013: 置換の窓は読み手側でも吸収し、読み取りを `util/atomic.rs` に置く

### Status

Accepted

### Context

`MoveFileEx(MOVEFILE_REPLACE_EXISTING)` は置き換えられる側を delete-pending に落とす。その窓のあいだに `CreateFile` を掛けた読み手は、書き手と同じ `ERROR_ACCESS_DENIED`(5) を受ける。ADR-010 / ADR-012 が吸収したのは書き手側だけなので、`FsTaskRepository` の `lookup` / `list` / `save_degraded` が使う `fs::read` はこの窓をそのまま `ReadError::Io` に写す。TC-port-task-repository-042(別スレッドが読み続ける中で `save` を反復)と 044(同じく `archive`)は、書き手が成功しても読み手が落ちればケースの失敗になる。

run 31657976822 の Windows は緑だが、そこで走った適合スイートがこの窓を一度も踏んでいないことと、踏まないこととは別である。ADR-012 が `rename_atomic` について採った「未観測は赤でないことを意味しない」を、そのまま読み手側にも当てる。

「読み手はロックなしで常に一貫した内容を見る」は永続化ポートの契約(spec/domains/task.md `TaskRepository`)であり、書き手だけを直しても満たせない。置き場所には選択肢がある。

1. `adapter/task_repository.rs` に再試行を書く — 分類・上限・バックオフが書き手と別の場所に二重化する。CLAUDE.md「アトミック性・排他が要る操作は共通のユーティリティに集約し、個別に再実装しない」に反する。
2. **`util/atomic.rs` に読み取りを置く** — 窓を作る側と窓を吸収する側が同じファイルに揃い、出典が1つで済む。

### Decision

- 内容の読み取りを `util::atomic::read_atomic` に通す。再試行の実体は書き手と同じ `retry_while_transient` / `transiently_denied` / `MAX_ATTEMPTS` で、分類・上限・バックオフの出典は1箇所のままにする。
- **エラーの意味は変えない。** 上限に達したら OS が返したエラーをそのまま返す。`NotFound` は一時的な拒否ではないので初回で返り、「消えたエントリ」と「読めないエントリ」の判別は不変。
- 契約の主張をユニットテストと適合スイートで揃える。`読み手は旧内容か新内容のどちらかだけを観測する` は「読めたときだけ内容を見る」形で読み取りの失敗を許容しており、ポート水準の契約より弱いことを主張していた。適合スイート側に合わせ、`read_atomic` が成功することを要求する。
- 対象外を明示する。`symlink_metadata`(std の Windows 実装は共有違反で `FindFirstFileW` にフォールバックする)、`read_dir`、`config_store` / `workflow_store`(`write_atomic` で書く経路が無く、置換の窓が生じない)。

### Consequences

- 良い点: 契約が書き手と読み手の両側で揃う。042 / 044 が Windows で最初に走る時点で、どちらの側も吸収済みになる。
- 良い点: ユニットテストが主張する内容が適合スイートと同じ強さになり、片方だけが緩い状態が消える。
- トレードオフ: 読み取りも最大 511ms ブロックしうる。tick は排他ロックを保持したまま読むので、この遅延がロックの保持時間にそのまま乗る。
- トレードオフ: 本当の権限不足による読み取り失敗が最大 511ms 遅れる。Win32 のコードからは「置換の窓」と「権限が無い」を区別できないため、ADR-010 と同じ取り違えを読み手側でも受け入れる。
- トレードオフ: **並行テストの読み手が無制限にスピンする一方で書き手だけが予算を持つ非対称は、テストの中にしか存在しない。** 製品側の読み手(`FsTaskRepository` の `lookup` / `list`)はスピンせず、`read_atomic` を1回通るだけである。読み手ループには `thread::yield_now()` だけを入れて病的な CPU 飢餓を取り除き、読み取り回数の上限やスリープでレースを潰す形は取らない — それは検出したいインターリーブの窓そのものを消す。
