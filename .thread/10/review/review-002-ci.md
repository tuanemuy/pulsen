# レビュー 002 — CI・ビルド基盤

対象: PR #12 / `origin/main...HEAD`（HEAD = `2c99c1b`）
前提: run 31661056619（`2c99c1b`）で全7ジョブ緑（`gh run view` で再確認済み）

ワークフローの合否判定そのもの（終了コードの伝播・`if:` 条件・握り潰し）には穴を見つけられなかった。
`continue-on-error` / `|| true` / `set +e` は1件も無く、`shell: bash` の `-eo pipefail` の下で
`tee` を挟むテストステップも、`versions=$(cargo metadata | jq …)` の代入も、失敗がそのまま
ステップの失敗になることをローカルの bash で実測して確認した。`case` の被検査式・`if` の条件に
置いた `grep -c` が `-e` の対象外になることも実測で確認しており、コメントの主張と一致する。

残る問題は1つ、**唯一の可視化機構（SKIP サマリー）が実測ログの形式に対して成立していない**こと。

### CI・ビルド基盤

#### Blockers

- **[B-001] SKIP サマリーの行頭一致が libtest の出力に対して成立せず、緑の実測ですでに取りこぼしている**

  **場所:** `.github/workflows/ci.yml:180-190`（「走らなかったケースを報告する」の awk）

  **問題:** 抽出も除外も `line ~ /^SKIP /` で行頭一致に依存しているが、`--nocapture` 下の libtest は
  テストの stdout と `test <名前> ... ` の進捗行を同じ stdout へ並行に書くため、SKIP 行が進捗行の
  末尾に連結されて行頭に来ないことがある。**run 31661056619 の windows-latest で実際に起きている:**

  ```
  test tests::並行フックを持たないハーネスではケースがスキップされる ... SKIP tc_port_clock_0051_別のケース: …
  ```

  この行は `^SKIP ` に当たらないので、除外にも一覧にも入らない。実際にサマリーへ出た値を
  run 31661056619 のログから awk を再現して確認した結果は次のとおり。

  | OS | 除外件数（表示） | 一覧の件数 |
  |---|---|---|
  | ubuntu-latest | 3 | 1 |
  | macos-latest | 3 | 1 |
  | **windows-latest** | **2** | 11 |

  **理由:** 3点で実害がある。

  1. **プロジェクト自身の合格条件を満たしていない。** `testing.md:119`（確認項目4・期待結果3）は
     「除外件数が『3 件』と表示されている（3 から動いていれば、実在ケースのスキップを巻き込んで
     いる可能性がある）」と定めている。Windows は 2 で、しかも巻き込みは起きていない。除外件数を
     出す変更が入ったのは `2c99c1b` なので、この機構を持つ**唯一の実行が初回から期待値を外して
     いる**。ADR-005 が「件数が3から動くことが唯一の合図になる」と書いた合図は、導入時点で
     常時発報の状態にある。ワークフロー `ci.yml:157-160` の why コメントも同じ主張をしており、
     観測と食い違っている。
  2. **実在の適合ケースを黙って落としうる。** 連結が起きるのはスレッドスケジューリング次第で、
     架空ケースに限らない。今回 Windows で一覧に出た11件（`tc_task_register_task_016` ほか）の
     どれかが同じ形で連結すれば、サマリーから消える。他に検出経路が無いことは ADR-005 自身が
     「可視化しか役割を持たない機構なので消えたことを他の手段では検出できない」と認めており、
     AC-6(b)（実在の適合ケース・受け入れケースが並ぶ）と AC-6(d)（期待集合との一致）が
     ランごとの運次第になる。
  3. **逆向きにも壊れる。** 連結が `Running` 行側に起きた場合、`line ~ /^ *Running /` が外れて
     `drop` が前の区間の値のまま残る。`pulsen_conformance-` の区間で `drop` が 0 のままなら、
     架空の3件が実在ケースとして一覧に混ざり、unix のサマリーが1件ではなく4件になる。これは
     AC-6(d) の突き合わせを直接壊す。

  **提案:** 抽出を行頭一致から「`SKIP ` の位置を探して、行頭または `... ` の直後なら採る」へ
  変える。`match(line, /(^|\.\.\. )SKIP /)` で位置を取り、`substr(line, RSTART + RLENGTH - 5)` を
  正規化した行として dedupe・出力に使えば、連結の有無に関わらず同じ行が得られる（`SKIP` の
  本文は行末まで続くので、後ろは切らなくてよい。念のため末尾の ` ok` / ` FAILED` を落とすと
  なお安全）。あわせて区間判定を `line ~ /^ *(Running|Doc-tests) /` で拡げるか、`^test result:`
  で `drop` を戻すと、最後の `Running` 以降ずっと `drop` が残る現在の形も閉じる。
  修正後は再度 push して、3 OS のサマリーが「除外 3 件 / unix 1 件・Windows 11 件」になることを
  確認する（testing.md 確認項目4 の期待結果に一致させる）。

#### Warnings

- **[W-001] `progress.md` の実測記録が HEAD より2コミット古く、「CI 未実行」の記述が事実と反する**

  **場所:** `.thread/10/progress.md:3`, `:54-60`

  `progress.md` は全緑を run 31657976822（`af24360`）として記録し、末尾に「全緑のあとに入った変更
  （CI 未実行）」として `ci.yml` の5点と `atomic.rs` / `task_repository.rs` を挙げている。しかし
  run 31661056619（`2c99c1b` = HEAD）が全7ジョブ緑で、この節が指す変更はすべて CI を通っている。
  AC-2 / AC-6 の実測が「どのコミットに対するものか」を PR の記録から辿れることが plan.md の
  前提なので、緑の出典を HEAD の run に更新し、この節を畳むべき。ブロックはしない（実測自体は
  存在し、結論も変わらない）が、レビューで毎回このズレを追い直すことになる。

- **[W-002] `HOOKS.md` の実測が `af24360` 基準のままで、記録した件数が HEAD と一致しない**

  **場所:** `crates/pulsen-conformance/HOOKS.md`（「3ランナーでの実測」節）

  出典を run 31657976822 / `af24360` と明記しているので AC-8 の「実測に使ったコミットを明記する」
  は満たしている。ただし `2c99c1b` で `read_atomic` とユニットテスト2件が入った結果、記録した
  「`pulsen` の lib ユニットテストが Windows 63件・unix 66件」は HEAD では **65件 / 68件** になる
  （run 31661056619 で確認。差が3件であることは不変）。また「測定したのは `af24360`（Issue #10 の
  CI とその吸収まで適用した時点）」という括弧書きは、吸収が `2c99c1b` まで続いた以上もう正確でない。

  スキップ集合そのもの（unix 1件 / Windows 11件）と「テストバイナリ15本・`test result:` 18行」は
  run 31661056619 でも同一であることを確認したので、AC-8 が守ろうとした中身は生きている。
  出典を HEAD の run に貼り替えて件数を直せば済む。test-docs 観点と重複する指摘。

#### 所見（指摘ではない）

- AC-1 / AC-2 / AC-3 / AC-4 / AC-7 は満たされていると判断した。7ジョブ構成・`fail-fast: false`・
  `permissions: contents: read`・PR 限定の `cancel-in-progress`・`defaults.run.shell: bash`（ステップ
  ごとの `shell:` は 0 件）・`actions/checkout@v7` 単独・第三者製 Action 0 件・`sort` / コンテナ指定 /
  単一テストターゲット指定の綴りが 0 件、をいずれも確認した。
- AC-4 の版数読み出しは、`--no-deps` の全メンバーを対象に `null` を除いて `unique` を取り、0件と
  複数件を `case` で落とす形になっている。空文字のときに `printf '%s\n' "" | grep -c .` が 0 を
  返すことも実測で確認した。run のログでも `MSRV: 1.89` → `1.89-x86_64-…` → `rustc 1.89.0` と
  一本で繋がっている。
- `${{ }}` は `runs-on` / `concurrency` / `env:` の値にしか現れず、`run:` のスクリプト本文へ
  テキスト展開される箇所は無い。MSRV を `env` 越しに渡す形は、フォークが書き換えられる
  `Cargo.toml` 由来の値を扱ううえで妥当。
- AC-6(a) は `id -u` を代入で受けてから `case` で判定しており、`id` 自体の失敗・非数値出力の
  どちらでも落ちる。run のログで `uid=1001` が unix 2 OS に出ていること、Windows では
  `if: runner.os != 'Windows'` でステップ自体が存在しないことを確認した。
- 3状態の分岐（`test.log` 無し / `test result:` 行無し / 走った）は、`always()` の下で
  build 失敗時にも `tee` が `test.log` を残すことを踏まえた形になっており、実ログの形式に対して
  成立している。B-001 は3状態の分岐ではなく、3状態目の中身の抽出の問題。
