spec に書かれていない実装手段の判断だけを記録する。ロック非取得(pages 共通事項)・タスクIDの解決順(PAGE-common-004)・スナップショットのタスクファイル埋め込み(ADR-015)など、既に決着している事項は再記録しない。

## ADR-001: `ls` は1タスク1行の桁揃えテーブルで出し、破損の報告は一覧の後ろに別ブロックで置く

### Status

Proposed

### Context

`spec/pages/index.md` は出力を「人間可読なテキストとする。機械可読形式(JSON等)は本フェーズのスコープ外」としか定めておらず、一覧の形式(列の並び・区切り・整列)は表示層の裁量に残っている。決めずに書くと、受け入れテストが最初に書いた綴りへ結合し、後から形式を変えるたびにテストが壊れる。

`ls` が同時に出すものは2種類ある — 読めたタスクの行(8項目)と、読めなかったファイルの報告(パスと理由)である。既存の `tick` のサマリー(`crates/pulsen/src/cli/render.rs`)は「見出し + 字下げした項目」の縦並びで、1件あたりの情報量が多いときの形として確立している。一方 `ls` は「複数タスクを見比べて、注意が必要なものを素早く見つける」(`spec/scenario/monitoring.md`)ことが目的で、縦並びだと比較ができない。

### Decision

**読めたタスクは1行1タスクの桁揃えテーブルとし、ヘッダー行を1行置く。** 列は `spec/pages/index.md#ls` の「機能」に書かれた順(タスクID / ワークフロー名 / リポジトリ / ブランチ / タスクステータス / 実行状態 / attempt_count / 更新日時)に固定し、アーカイブ済みの印と `SnapshotUnreadable` の印は行の末尾に置く。値が未確定の項目(ブランチ未確定など)は空欄ではなく明示的な記号を置く — 空欄は「値が無い」と「列がずれた」を区別できない。

**破損したタスクファイル(`Corrupt`)の報告は、一覧の後ろに独立したブロックとして置く。** テーブルの行に混ぜない — 破損ファイルはタスクIDもステータスも読めておらず、埋められない列が大半になる。ブロックにはファイルパスと読めない理由を出し、修復の入口(`spec/scenario/monitoring.md#タスクファイルの直接閲覧修復`)として機能させる。

**受け入れテストは列の綴りや桁数ではなく、「その行に必要な値がすべて現れること」で主張する。**

### Consequences

- 良い点: 比較が目的の一覧が比較できる形になる。破損の報告が一覧の読みやすさを壊さない。テストが形式ではなく内容に結合する。
- 桁揃えは文字数ではなく端末の表示幅で行う(`crates/pulsen/src/cli/render/mod.rs` の `display_width`)。見出しも、ワークフローごとに定義されるタスクステータスも全角になり得るため、文字数で測ると列がずれる。
- 東アジア文字幅の判定は、本番依存を増やさない(AC-8)ため表示層に自前で持つ。判定は BMP の East Asian Wide / Fullwidth に当たる11の符号位置範囲(ハングル字母・CJK記号・かな・CJK統合漢字と拡張A・ハングル音節・互換漢字・全角形など)を2桁、それ以外をすべて1桁とする近似である。**`WIDE` の11範囲に入らない East Asian Wide はすべて1桁に倒す** — BMP 外の漢字や絵文字だけでなく、範囲の隙間に落ちる BMP 内の Wide な記号・絵文字(`U+231A` など)や Hangul Jamo Extended(`U+A960`〜 / `U+D7B0`〜)も1桁と数える。結合文字・異体字セレクタ・ゼロ幅文字は0桁ではなく1桁と数え、Ambiguous 幅も1桁に倒す。並べるのが日本語と ASCII である限りこの近似で足りる。範囲を手で足していくと `unicode-width` の劣化再実装になるため、足りなくなったら範囲ではなく依存の可否を問い直す。
- トレードオフ: 長いリポジトリパスやワークフロー名で行が折り返しうる。切り詰めると成果の回収に使うパスが読めなくなるため、切り詰めずに折り返しを許す。

## ADR-002: `cli/render.rs` を `cli/render/` へ分割し、コマンド単位のモジュールに切る

### Status

Proposed

### Context

`crates/pulsen/src/cli/render.rs` は 1456 行あり、`add` / `tick` / `wrapper` の成功表示とエラー文言、および共有ヘルパー(`problem` / `push_field` / `push_ids`)を1ファイルに持つ。本スライスは `ls` の一覧・空表示・破損報告と、`show` の全属性表示(項目20種、縮退の場合分け7系統)を足す。同じファイルに置くと 2000 行を超え、さらに #5(abort / retry / set-status)と #6(終端処理)が控えている。

一方で、文言層を分割すると共有ヘルパーの置き場と、エラー型からの委譲経路(`add_error` → `wire_error` → `config_error` のような連鎖)をどう保つかが問題になる。

### Decision

**`cli/render.rs` を `cli/render/mod.rs` + コマンド単位のモジュール(`add.rs` / `tick.rs` / `wrapper.rs` / `ls.rs` / `show.rs`)に分割する。** `mod.rs` には共有ヘルパー(`problem` / `push_field` / `push_ids` / `push_attempts` / `source_location`)と、複数コマンドから使われる下位のエラー文言(`wire_error` / `config_error`)を残し、`pub use` で既存の呼び出し口(`render::registered` 等)を変えない。

**分割は本スライスの一部として行う。** 後回しにすると、`ls` / `show` の文言を既存ファイルへ足した状態が次のスライスの出発点になり、分割の差分が本スライスのレビュー範囲から外れたところで肥大する。

### Consequences

- 良い点: コマンドごとに文言が閉じ、#5 / #6 が足す文言の置き場が自明になる。共有ヘルパーの利用箇所が `mod.rs` への参照として明示される。
- トレードオフ: 本スライスの差分に既存コードの移動が混ざる。移動先のトップレベル項目が移動元と一致すること(項目の集合とその中身)で、移動が純粋であることを確かめる。

## ADR-003: アーカイブ済みタスクのテスト前提は、リポジトリの `archive` を呼ぶ共有フィクスチャで作る

### Status

Proposed

### Context

チェックリストの `PAGE-ls-004` / `PAGE-show-008` と6件の TC 行はアーカイブ済みタスクを前提とするが、`state/tasks/` から `state/archive/` へタスクを移すのは tick の終端処理(Issue #6)だけで、本スライスには CLI からその状態を作る経路が無い。受け入れテスト(`cli_ls.rs` / `cli_show.rs`)は実バイナリを起動するため、前提はテスト側でファイルシステムに用意するしかない。

選択肢は2つあった。

1. `state/archive/<id>.json` へタスクファイルを直接書く
2. `FsTaskRepository::archive`(Issue #1 で実装済み・適合スイート通過済み)をテストから呼んで移す

### Decision

**2(`FsTaskRepository::archive` を呼ぶ)を採り、`crates/pulsen/tests/common/mod.rs` に共有フィクスチャとして置く。** テストは `pulsen add` でタスクを作り、フィクスチャがリポジトリ経由でアーカイブへ移す。

1 を採らないのは、アーカイブ側のファイル名・配置・内容の形式をテストが自前で持つことになるためである。その知識は `TaskFilePath` とアダプターの直列化にあり、二重に持つと形式が変わったときに「テストだけが古い形式で緑」になる。ポートの契約(`archive` の直後、対象は現役側から消えアーカイブ側に現れる)は適合スイートが担保しているので、フィクスチャはその契約に乗るだけでよい。

**#6 が終端処理を実装したら、このフィクスチャは `pulsen tick` でアーカイブへ到達させる形に置き換えられる**(手順書 `spec/manual-tests/monitoring.md` の `TASK_D` がその形)。置き換えを見落とさないよう、フィクスチャの doc コメントに引き取り先(#6)を書く。

### Consequences

- 良い点: 形式の知識をテストへ複製しない。#6 の実装後に「本物の経路」へ差し替える地点が1箇所に集まる。
- トレードオフ: 受け入れテストがバイナリ越しの操作だけで閉じず、ライブラリ API を1つ使う。`crates/pulsen` は lib + bin の構成なのでコンパイルは通るが、「実バイナリだけで検証する」という受け入れテストの性質は一部崩れる。崩す範囲をアーカイブ前提の準備だけに限る。

## ADR-004: `exit` の読み取り結果は run ディレクトリの有無に入れ子で持つ

### Status

Proposed

### Context

`ShowTask` は `RunStore::attempt_exists` で run ディレクトリの有無を確かめ、**存在すれば** `read_exit` で exit を補う(`spec/usecases/task.md#showtaskshow` の処理フロー3)。存在確認は3値(在る / 無い / 確認できなかった)になるため、`read_exit` を呼ばない経路が2つ生まれる。

出力DTOで `exit` を有無と**並べて**持つと、この2経路の扱いが問題になる。「記録あり / 記録なし / 読めなかった」の3値にすればどちらも「記録なし」に落ちるが、ディレクトリごと無い場合はそれが真である一方、**存在を確かめられなかった**場合は記録の不在も主張できない — 表示が「記録なし」と言い切ると、観測できなかったことが観測結果として読める。かといって「読んでいない」を4つ目の変種として並べれば、有無と exit が独立な2軸になり、`(不在, 記録あり)` や `(在る, 読んでいない)` のような成立しない組み合わせが型で書けてしまう。

### Decision

**`exit` は `RunDirPresence::Present { exit: ExitOutcome }` として run ディレクトリの有無に入れ子で持つ。** `ExitOutcome` は `Recorded` / `Absent` / `Unreadable` の3値で、`Present` のときにしか存在しない。`Absent`(ディレクトリが無い)と `Unknown`(有無を確かめられなかった)は exit を持たない — 前者は記録が無いことが事実として導け、後者は記録について何も主張できないため、どちらも別の値を添える余地がない。

`AttemptSummary` が run ディレクトリについて持つのは `run_dir_presence` の1つだけで、`read_exit` を呼ぶのは存在確認が `Ok(true)` を返した枝に限られる。表示は run ディレクトリの行と exit の行を**別々の項目**として出し、同じ値を2度 `match` して言葉を当てる — 不在は「(記録なし)」、確認できなかった場合は「(runディレクトリの有無を確認できないため読んでいません)」で、観測の失敗が観測結果として読めないことは変わらない。

**畳む / 畳まない基準は軸の従属性で決める。片方が他方を決める従属軸は入れ子にし、真に独立な軸だけを並べる。** `snapshot`(定義済みステータス一覧と、読めない理由)は両方が立つ状態もどちらも立たない状態も無い1軸なので `SnapshotInfo` に畳む。`exit` は run ディレクトリの有無が「読めるか / 何を主張できるか」を決める従属軸なので `RunDirPresence` に入れ子にする。

従属軸というだけでは畳む先が尽きるまで畳み続けられるため、**打ち止めの条件を基準に含める。畳むのは、(1) 従属関係が下位層(ドメインの直和型・ポートの呼び出し可能性)に既にある、かつ (2) 畳んだ後も各表示項目が自分の正本フィールドを持ち続ける、の両方を満たすときに限る。** 片方でも欠けるなら畳まず、従属である事実と畳まない理由を型の doc に残す — 従属を見落としたのか、見たうえで並べたのかを、次に同じ箇所を読む者が型だけで判別できるようにする。ドメイン側の形の変更を伴う畳み込み(`AttemptRef::process` を実行状態へ入れ子にする、など)は本スライスでは行わない。出力DTO の整形がドメインの形を決める順序になり、表示の都合が中心へ流れ込む。

適用結果は2件。

- `execution_state` + `stop_info` → `execution`(`ExecutionState`)。(1)(2) をともに満たす — 従属関係はドメインが `ExecutionState` として既に閉じており(凍結要因と通知は `Stopped` の付随データ)、実行状態の行は畳んだ後も `execution` 自身を正本に持つ。
- `limits.retry` は畳まない。(1) は満たす(`RetryLimitInfo::Unknown` は `SnapshotInfo::Unreadable` と共変する)が、(2) を欠く — 畳むとカウンタ行(attempt_count)の併記の正本がスナップショット項目の内側へ移り、表示が別の項目の内部形を読むことになる。加えて `RetryLimitInfo` の3値は `spec/usecases/task.md` の `limits.retry` と TC-task-show-task-029 が名前付きで定めた契約で、「併記なし」と「導出不能」の区別はその名前に結び付いている。

### Consequences

- 良い点: 成立しない組み合わせが型で表現できない。「有無を確かめられていないので読んでいない」は `Unknown` が exit を持たないことから構造的に従い、同じ事実を2つのフィールドで二重に表さない。
- 良い点: `read_exit` を呼ぶ条件が型の形と一致する。`ExitOutcome` を作れる場所が `Present` の構築点1つに限られるため、呼ばない経路が増えても値の埋め方を選び直す余地が生まれない。
- 読み取りが失敗した場合(`ExitOutcome::Unreadable`)は、原因をポートの分類の**構造のまま**持つ — `RunFileError` の `Corrupt { path, message }` と `Io { message }` の区別を残す。文字列に潰すと、表示層がパスを出すべきかどうかを判定できなくなる。
- パスを文字列に入れる層を決める。アダプターの `Io` 系メッセージは既に対象を含むため、表示層はパスを前置しない。`Corrupt` は構造化された `path` を持つので、表示層がそれを1度だけ出す。`RunDirPresence::Unknown` も `Io` と同じ扱いにする。
- トレードオフ: 表示層が同じ値を2度 `match` する。1つの項目にまとめれば1度で済むが、`spec/pages/index.md` の縮退表(run ディレクトリ・中身の不在は注記して 0)と AC-4(exit のパスと値を示す)はどちらも独立した項目として求めており、DTO の形に合わせて表示の項目構成を変えない。
- `SnapshotInfo` / `RunDirPresence` / `execution` は、`spec/usecases/task.md` の ShowTask 出力DTO(`defined_statuses` / `snapshot_error`、`exit` / `run_dir_exists`、`execution_state` / `stop_info` をそれぞれ並べたフィールド)とフィールドの持ち方が離れるため、spec 追従として Issue #4 のコメントで提起する。

## ADR-005: ユースケーステストのフィクスチャを `usecase_fixture` に集約する

### Status

Proposed

### Context

`crates/pulsen/tests/tick_fixture/mod.rs` は、ダブルに対するテストが要る組み立て(タスクの再構築・スナップショット・走査結果・グローバル設定)をすべて持つ。本スライスが足す `ListTasks` / `ShowTask` のユースケーステストも同じ組み立てを要するが、モジュール名が tick を名乗っている。

選択肢は3つあった。(1) `tick_fixture` をそのまま使う、(2) ls / show 用に別のフィクスチャモジュールを作る、(3) 名前を用途に合わせる。

### Decision

**(3) を採り、`tick_fixture` を `usecase_fixture` に改名する。** 改名は `mod` 宣言と参照の機械的な置換で、既存の5つのテストファイルに閉じる。

(1) を採らないのは、tick を名乗るモジュールを `list_tasks.rs` が使う状態が次のスライス(#5 / #6 が足す abort / retry / set-status のユースケーステスト)でさらに増えるため。(2) を採らないのは、タスクの再構築とスナップショットの組み立てが2箇所に分かれ、ドメインの形が変わったときに片方だけが古いまま緑になるため。

### Consequences

- 良い点: ユースケーステストの前提の組み立て方が1箇所に集まる。#5 / #6 が足すテストの置き場が自明になる。
- トレードオフ: 本スライスの差分に、tick のテストファイル5件の1行変更が混ざる。

## ADR-006: ダブルは「そのスライスのユースケースが呼ぶメソッド」まで台本を持つ

### Status

Proposed

### Context

`ScriptedTaskRepository` は `create` / `list_active` / `save` / `save_degraded` の4メソッドだけに台本を持ち、残りは呼ばれるとパニックする(「ダブルが扱わない操作はテスト側の不変条件違反」)。本スライスの `ListTasks` は `list_archived` を、`ShowTask` は `find` を呼ぶため、そのままではユースケーステストが1件も書けない。

### Decision

**`find` と `list_archived` に台本(`with_find` / `with_list_archived`)を足し、`archive` はパニックのまま残す。** 台本を持たせるのは、そのメソッドを呼ぶユースケースが揃ったものに限る — `RunStore` に `attempt_exists` だけを足して gc 用の3メソッドを宣言しない規約(Issue #1)と同じ基準をダブルにも当てる。

`find` は受け取ったタスクIDを記録する。解決順(現役 → アーカイブ)はポートの契約でありユースケースは関与しないため、呼び出し側が主張できるのは「どのIDを何回引いたか」だけになる — 入力境界の検証が解決より前に行われることは、この記録が空であることとして書ける。

### Consequences

- 良い点: 台本を持つメソッドが、実装済みのユースケースの集合と一致し続ける。
- トレードオフ: #6 が終端処理を実装するとき `archive` の台本を足す変更が要る。パニックのまま残すことで、その時点で必ず気づく。

## ADR-007: 適合ケースの観測は、ポートに在るならフックとメソッドの両方で主張する

### Status

Proposed

### Context

`TC-port-run-store-001` の台帳の期待文(`spec/testcases/ports/run-store.md`)は「親を含めて attempt ディレクトリが作成され、`attempt_exists` が true になる」である。`.thread/2/adr.md` の ADR-084 はこの観測を、選択肢 (a)「`attempt_exists` を宣言して #4 の行を先取りする」を退けて (c)「ハーネスのフック(`attempt_dir_present`)と既存の read 系に置き換える」で満たすと決めた。(a) を退けた理由は Issue #2 の AC-6(未実装メソッドの宣言・スタブが1つも無い)というスライス限定の制約で、ADR-084 自身が Consequences に「#4 が `attempt_exists` を足すときに `TC-022 / 023` とあわせてフックの要否を見直す」と書いている。

本スライスで `attempt_exists` がポートに宣言され、(a) を退けた制約は消えた。予告されていた見直しをここで行う。

### Decision

**`TC-port-run-store-001` の操作後の観測を、`attempt_dir_present`(フック)と `attempt_exists`(ポート)の併用に改める。** 前は `attempt_dir_present` が false、後は `attempt_dir_present` が `Some(true)` かつ `attempt_exists` が `Ok(true)` であることを主張する。

**「前後で反転することを主張する」という ADR-084 の主眼は変えない。** フックだけでは常に `true` を返すハーネスでケースが緑になり、行の主眼(親を含めて attempt ディレクトリが作成されること)が検証されない。メソッドだけでは、被試験の実装が自分の書き込みを自分で観測しているだけになり、「環境から見て実際に在るか」を問えない。どちらか一方に寄せると、いま両側で閉じている問いのどちらかが開く。

### Consequences

- 良い点: 台帳の期待文が名指しする `attempt_exists` を、代替観測ではなくそのまま主張できる。ADR-084 が `TC-port-run-store-001` に付けていた「代替観測で満たしたものとしてチェックを付ける」という例外(plan.md「チェックリスト行にチェックを付ける基準」)が要らなくなる。
- `attempt_dir_present` フックは廃止しない。`crates/pulsen-conformance/src/run_store.rs` の TC-018(`:339`)と `assert_attempt_dir_absent`(`:448`。write 系の置き場作成の追加ケースが使う)は、`attempt_exists` では代替できない「行の主張とは別に、環境から見てディレクトリごと作られた / まだ無い」を問うており、提供できないハーネスではその分岐だけを飛ばす形で残る。
- `.thread/2/adr.md` の ADR-084 は #2 の作業ログとして決定節のまま残し、書き換えない。作業ログは `.adr/` の supersede 機構の対象外で、遡って書き換えるとその時点のスライスで何が成り立っていたかが読めなくなる。見直しの記録は本項が持つ。
- この判断は適合スイート全体と将来の別バックエンドのハーネスに波及するため、`.adr/` への昇格候補。判定は Phase 8 で行う。

## ADR-008: 表示語は spec が語を与えている項目については spec の語を正本にする

### Status

Proposed

### Context

`show` の出力は項目名と状態名の集合で、その語の出所は2種類ある。`spec/pages/index.md#show` の「機能」が挙げる項目名(`workspace_path` / `attempt_count` / `notified_at` など)や、`spec/requirements.md` §6.4 と `spec/pages/index.md#abort` が鉤括弧で与える状態名(「人間によるabort」)のように **spec が語そのものを書いているもの**と、spec が「表示する」としか書いておらず語が表示層に委ねられているものである。

両者を区別せずに表示語を決めると、spec が語を与えている項目でも実装が独自の言い換えを当てうる。それが起きたのが `StopReason::Aborted`(spec「人間によるabort」に対し実装「利用者による中断」)と `notified_at`(spec の識別子に対し実装「通知」)の2件だった。手動テストの手順書は spec の語で期待文を書くため(`spec/manual-tests/monitoring.md:342` / `intervention.md:223` / `intervention.md:609` / `setup.md:480` が `show` の出力に対して「人間による abort」を名指しする)、言い換えは手順書と出力を照合不能にする。さらに `notified_at` は `AC-6` が掲げるタスクファイルの直接閲覧の入口 — show の項目とタスクファイルのキーの突き合わせ — を、この1項目だけ読み手の推測にしていた。

### Decision

**spec が語を与えている項目(項目名・状態名)は spec の語をそのまま出す。spec が語を与えていない項目だけが表示層の裁量である。**

適用結果は2件。

- `StopReason::Aborted` の表示語を「人間による abort」にする。ASCII の前後に空白を置くのは既存の表示語(「spawn 失敗の上限の超過」)と同じ流儀で、手順書の綴りとも一致する。ドメインの `StopReason::Aborted` の doc も同じ語に揃える — 語の出所が2つあると、#5 が abort を実装するときに同じ食い違いが再生産される
- `notified_at` の項目名を素の識別子 `notified_at` にする。`workspace_path` / `attempt_count` と同形になる。「通知(notified_at)」の括弧併記を採らないのは、show の出力に併記形の項目が他に1つも無く、非対称が別の形で残るため

`StopReason` の他3経路(`RetryLimitExceeded` / `JudgeLimitExceeded` / `SpawnFailLimitExceeded`)は、spec が経路の存在だけを述べて表示語を与えていないため裁量に留まる。

### Consequences

- 良い点: 手動テストの手順書が期待する綴りと出力が照合できる。show の項目名とタスクファイルのキーが綴りで辿れ、`AC-6` の修復の入口が推測を要さない。
- 良い点: 表示語を決めるときに問うことが「spec がこの語を書いているか」の1点に定まり、項目ごとに語感で選び直す余地が無くなる。
- spec が show の項目名として挙げていない項目(凍結要因・在籍・現在attempt・同定情報・定義済みステータス・スナップショット保存先)は表示層の裁量であり、本 PR では変えない。
- トレードオフ: 隣接する項目で日本語と識別子が混在する(`凍結要因` の次に `notified_at` が並ぶ)。見た目の一貫性より、綴りで辿れることを採る。
- この判断は #5(abort / retry / set-status)が同じ問題に必ず当たるため `.adr/` への昇格候補。判定は Phase 8 で行う。
