### Warnings

Use Case の観点では問題なし。以下は「なぜ問題なしと判断したか」の根拠で、指摘ではない。

- **処理フロー1〜9の骨格**: `Tick::execute` はロック取得(`Ok(None)` → `Skipped` / `LockError::Failed` → `TickError::LockFailed`)→ `list_active`(`ReadError::Io` → `TickError::Scan`)→ エントリごとの分岐、の順で spec の1〜2に一致する。`_guard` は名前つき束縛なので走査全体でロックが生きる。分岐は `branch_of` が実行状態(と Pending / Failed の動作種別)の網羅 `match` として1箇所で決め、タスクを消費する手続きへ渡す前に判断だけを値にしている(ADR-089)。判断はドメイン(`Task` の遷移関数・`LaunchingClassifier`)にあり、ユースケースは観測 → 判断 → 実行の配線に徹している。
- **手続きA の順序と失敗時の遷移**: `ensure_workspace`(`workspace` が None のときだけ `WorkspacePlanner::derive` → `create` → `confirm_workspace` → `save`)→ `expand` 5段 → `record_launching` → `save` → `prepare_attempt` → `spawn_wrapper` で spec と1対1。worktree 失敗は `record_tool_failure(WorktreeCreate, …, applicable_retry_limit)` → `save` → 終了、展開失敗5経路はすべて `record_spawn_failure_in_place` → `save` → 終了、`prepare_attempt` の失敗と `spawn_wrapper` の同期エラーは**状態を変更せず報告のみ**で、launching 記録後に pending へ戻す経路が構成上存在しない。`launch.rs` の2つの `expect`(確定済みワークスペース・リトライ上限)はどちらも `branch_of` / `ensure_workspace` が保証する不変条件で、到達経路がない。
- **手続きC の順序と失敗時の遷移**: 冒頭の `current_attempt` None 検査(run ファイルにも触れない)→ `read_pid_file` / `read_starttime` → `classify` の3分岐 → `SuspectSpawnFailure` で `write_invalidation_marker`(`Err(Io)` は状態を変更せず報告)→ 再読 → `classify_recheck` の2分岐、で spec と一致。run ディレクトリ不在は `Ok(None)` として猶予経路へ合流する。
- **マーカー順序プロトコルの競合窓**: 二重起動に至る窓は残っていない。tick が `SpawnFailed` を確定させるのはマーカー書き込み**後**の再読で pid が不在だった場合だけで、ラッパーは pid 書き込み**後**にマーカーを確認する。したがってその再読より後に pid を書くラッパーは、必ずマーカー書き込み後にマーカーを確認して抑止される。逆に再読で pid が現れれば `ConfirmRunning` へ進み pending へ戻さない。マーカーを書けなかった場合に状態を変えないのも同じ理由で正しい。`read_run_files` が pid → starttime の順で読むことも必要条件になっている — 逆順だと2回の読み取りの間に両方が書かれた健全な起動が「pid あり・starttime なし」と観測され、順序破れとして launching に滞留する。マーカーは attempt ごとの run ディレクトリに閉じるため、次 attempt(`record_launching` が採番)を抑止することもない。`record_spawn_failure` の `save` が失敗してマーカーだけが残った場合も、次の tick が同じ attempt を再観測して同じ結末に収束する。
- **`RunWrapper` の順序**: `own_identity` → `write_starttime` → `write_pid_file` → `marker_exists` → `run_agent` → `write_exit`。starttime が pid より先であること、マーカー確認が pid の後であることが `RunStoreCall` の並びで主張されている。`marker_exists` の `Ok(true)` と `Err(Io)` を同じアームに畳んで未起動終了にしているのも spec のとおり(安全側)。ステップ1〜3 の失敗は `Silent` で即終了し、それ以前の呼び出し記録しか残らない。config もロックも触れず、`compose_wrapper` は `run_dir` から復元した `StateRoot` だけで `RunStore` を組む(`--home` に依存しない)。
- **1タスクの失敗での続行**: `process` はエントリごとに独立で、どの経路も `summary.errors` へ積んで戻る。`tick_scan.rs` の「あるタスクの処理が失敗しても残りのタスクは続行する」が実際に前のタスクを失敗させたうえで後続の起動を主張している。
- **書き込んだ tick の報告**: タスクファイルへ書いた経路を全部たどっても、`launched` / `confirmed_running` / `frozen` / `errors`(`WorktreeCreateFailed` / `CommandExpansionFailed` / `SpawnNotObserved` / `PrepareAttemptFailed` / `SpawnFailed` / `SaveFailed` / `Transition`)のいずれかが必ず埋まる。報告は `commit` が `Saved` を返したときだけ積まれるので、保存できなかった tick は `SaveFailed` 1件になる。`Freeze` を引数で受け取り保存後の状態から凍結を導出しない形も、#3 の catch-up 通知が過去の凍結を再計上する縮退を先に潰している。表示側は `issue_outcome` の網羅 `match` で「失敗を記録 / 起動の結果が未確定 / スキップ」に振り分け、書き込みの有無と見出しの語義が食い違わない。
- **冪等性**: `状態が変化しないタスク群には連続実行しても書き込みが発生しない` / `worktree作成の直後にクラッシュしても同じワークスペースが再導出される` / `runファイルの破損が続く限り繰り返しても報告とスキップだけが続く` が、いずれも同じハーネスで tick を複数回回して主張している。展開は tick ごとに行われ、config の修正が次の tick に反映されることも受け入れテストで通っている。
- **スコープ外の不実装・未配線アーム**: `Cleanup` / `Observe` / `Advance` / `Notify` は空アームで、`tick_scan.rs` の `配線していない分岐のタスクにはエージェントを起動せず書き込みもしない` が「何が起きるか」の期待を持たずに「書き込まない・起動しない」だけを主張している(#3 / #6 がアームを埋めても書き換えにならない形)。宣言だけのポートメソッド・スタブは無い(`RunStore::read_exit` は `write_exit` と対の往復契約として適合スイートが実行しており、実装も完結している)。
- **判断と副作用の分離**: `branch_of` / `Freeze::of_recorded_failure` / `issue_outcome` はいずれも純粋関数。猶予時間の判定・上限超過の判定・pid と starttime の組み合わせの解釈はすべてドメイン側にあり、ユースケースは分岐先を選ぶだけになっている。
- **実効的なテスト**: ダブルは台本を使い切ると `panic` するため、呼び出し回数と順序の主張が空振りしない。AC-17 の一覧(ロック異常・`list_active` の Io・worktree 作成失敗と上限超過・展開失敗5経路・`prepare_attempt` 失敗・`spawn_wrapper` の同期エラー・`RunFileError` 3種・マーカー書き込み失敗・猶予境界 30 / 31 / 巻き戻り・`save` 失敗)はすべてダブルに対するユースケーステストで消化されている。受け入れ側は `wait_until` を「これから観測する成果物そのもの」(`exit` を読むなら `exit`、pid を待つなら `pid`、滞留の合図ならログの行)に立てており、タイムアウト時は不在の対象と run ディレクトリの一覧を添えて落ちる。`cargo test --workspace` は全件緑(221 + 各結合ターゲット、exit 0)。
- **残す必要のない記述**: コメントは why / why not に限られており、指摘への弁明や修正経緯は残っていない。`.thread/2/adr.md` の ADR-086 は「猶予経路は既存の `SpawnFailed` を使う」と書いているが、これは後続の ADR-090 が明示的に上書きしており(「ADR-086 は…1つの変種に畳むことまでは根拠づけていない」)、ADR の系列としては整合している。
