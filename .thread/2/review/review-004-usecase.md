問題なし。以下は判断の根拠として残す。

- **Tick の処理フロー(spec 1〜9 / AC-12)**: `execute` は「ロック取得 → `list_active` → エントリごとの分岐」の順で、`Ok(None)` を `TickOutcome::Skipped`(0 スキップ)、`LockError::Failed` と `ReadError::Io` を `TickError`(非0)に写す。分岐は `TaskEntry::Corrupt` / `SnapshotUnreadable` / `Intact` の網羅 `match`、実行状態は `branch_of` の網羅 `match`(`ExecutionState` の5変種＋動作種別3種)で、ワイルドカードが無い。ステップ8(gc)は `run_retention` を参照する経路自体が存在せず、スコープ外が「未実装のまま素通り」ではなく「書かれていない」形で満たされている。
- **サマリーの語義**: spec の全フィールドを持ち、本スライスで埋まるのは `launched` / `confirmed_running` / `frozen` / `errors` だけ。`confirmed_running` の追加と `errors` の構造化は ADR-086 / ADR-073 で、`is_empty` による「処理対象なし」は ADR-084 で契約化され、progress.md の spec 追従提起にも載っている。表示は `cli::render` が「起動 / 起動確認 / 凍結 / 失敗を記録 / 起動の結果が未確定 / スキップ」に振り分け、`issue_outcome` が網羅 `match` なので分類の追加が振り分け漏れを起こさない。
- **書き込みを行った tick の報告(ADR-084)**: 書き込みが起こる経路を全数辿った — `confirm_workspace` 保存後は必ず展開失敗の記録・起動記録・`SaveFailed` のいずれかへ合流し、`record_tool_failure` / `record_spawn_failure_in_place` / `record_launching` / `confirm_running` / `record_spawn_failure` の保存はいずれも成功時に `errors` か `launched` / `confirmed_running` / `frozen` を、失敗時に `SaveFailed` を積む。「書き込んだのに処理対象なしと表示される」経路は無い。`commit` が唯一の保存地点で、`Freeze` を遷移の呼び出し側から受け取るため、#3 の catch-up 通知が過去の凍結を再計上しない。
- **手続きA(AC-13)**: 順序は「workspace 確保 → 展開5段 → `record_launching` → `save` → `prepare_attempt` → `spawn_wrapper`」で spec と一致。展開失敗5経路はすべて `record_spawn_failure_in_place`(attempt を採番しない)、worktree 作成失敗は `record_tool_failure(WorktreeCreate)`、どちらも上限超過で `Stopped` を保存して `frozen` に記録する。`prepare_attempt` 失敗と `spawn_wrapper` の同期エラーは状態を変更せず報告のみで、`record_launching` の保存に失敗したときだけ run ディレクトリにも spawn にも進まない(遅延起動と新 attempt の並走を作らない)。
- **手続きC(AC-14)**: 冒頭の `current_attempt` None 検査 → `read_pid_file` / `read_starttime` → `classify` → `SuspectSpawnFailure` で `write_invalidation_marker` → 再読 → `classify_recheck` の順で、`RunFileError` とマーカー書き込み失敗はいずれも書き込まずに報告してスキップする。run ディレクトリ不在は `Ok(None)` として猶予経路に合流する。
- **RunWrapper の順序(AC-10)**: `own_identity` → `write_starttime` → `write_pid_file` → `marker_exists` → `run_agent` → `write_exit`。starttime が pid より先であること、マーカー確認が pid の後であることを `calls()` の並びで主張しており、実際に順序を入れ替えた変異(使い捨て worktree で検証)で3件が落ちることを確認した。マーカーありと `Err(Io)` はどちらも `Suppressed` で `run_agent` を呼ばず、CLI は 0 で終える。config もロックも取らず、`compose_wrapper` は `RunDirPath::state_root` だけから RunStore を組む。
- **二重起動の競合窓**: ラッパー「pid 書き込み → マーカー確認」× tick「マーカー書き込み → pid 再確認」の対が成立している。再確認で pid が現れた場合に `ConfirmRunning` へ進む(その attempt のラッパーはマーカーを見て未起動終了し、次スライスの手続きD が exit なし・プロセス死亡として拾う)経路は spec 自身が定めた形で、実装が新たに窓を開けてはいない。マーカー書き込み失敗で pending に戻さない扱いも spec どおり。手続きCで pending に戻った後の再起動は必ず新しい attempt 番号・新しい run ディレクトリを使う(`起動待ちへ戻ったタスクは次のtickで新しいattempt番号で再起動される`)。
- **1タスクの失敗の隔離**: 全経路が `summary.errors` への push で終わり、`process` のループを抜けない。`あるタスクの処理が失敗しても残りのタスクは続行する` と `実行状態の異なる複数のタスクがそれぞれの分岐で1ステップずつ処理される` が裏付けている。
- **冪等性**: `worktree作成の直後にクラッシュしても同じワークスペースが再導出される`・`状態が変化しないタスク群には連続実行しても書き込みが発生しない`・`runファイルの破損が続く限り繰り返しても報告とスキップだけが続く` が、同じ入力から同じ判断が再導出されることを主張している。
- **未配線アーム**: `Cleanup` / `Observe` / `Advance` / `Notify` は本体が空で、`配線していない分岐のタスクにはエージェントを起動せず書き込みもしない` が「サマリーに現れない・書き込まない・worktree に触れない・run ファイルに触れない・ラッパーを起動しない」を4種すべてで主張する。スコープ外のポートメソッド(`starttime_of` / `kill` / `try_kill_remnants` / `list_runs` / `delete_attempt` / `remove_task_dir_if_empty` / `attempt_exists`)とサービス(`RunningClassifier` / `JudgementService` / `IdentityCheck` / `CommandRunner` / `NotificationService` / `GcPolicy`)は宣言もスタブも存在しない。
- **判断と副作用の分離**: 分類は `LaunchingClassifier`、遷移は `Task` の遷移関数、分岐の選択は純粋関数 `branch_of` / `Freeze::of_recorded_failure` に閉じ、ユースケースは観測・判断・実行の配線に徹している。`expect` は不変条件(1・2、ワークスペース確保済み、AgentRun のリトライ上限)にのみ置かれ、いずれも型と分岐で成立が保証される。
- **AC-17 の一覧**: ロック機構の異常・`list_active` の Io・worktree 作成失敗と上限超過・展開失敗5経路・`prepare_attempt` 失敗・`spawn_wrapper` の同期エラー・`RunFileError` の3分類(pid 側 / starttime 側 / マーカー後の再読)・マーカー書き込み失敗・猶予境界(30 / 31 / 巻き戻り)・`save` 失敗が、すべてダブルに対するユースケーステストとして実装され、実プロセス・実ファイルシステムを使わずに通る。ダブルは呼び出しを記録してから台本を返し、台本を使い切ると panic するため、余分な呼び出しも取りこぼしも観測できる。
- **コード・コメント**: 残っているのは why / why not(順序を固定する理由、pending に戻さない理由、`Freeze` を導出しない理由、`prepare_attempt` 失敗でも spawn を続ける理由、`--home` を使わない理由)で、経緯や弁明は無い。ADR-065 以降への参照は `.adr/` へ未昇格だが、steps.md ステップ19(片付けフェーズ)の作業として残っており、progress.md の「未着手」にも記載がある。
