#### 確認した内容

- **AC-2**: `ExitCode`(`is_success` は 0 のときだけ真)・`PidFileContent` は I/O を持たない値。`RunDirPath` の6導出(`pid` / `starttime` / `exit` / `stdout.log` / `stderr.log` / `invalidated`)は名前定数を1箇所に置いた純粋関数で、`derive` と `attempt_dir_name` が同じ定数を共有する。`state_root()` の逆写像は `derive` との一致で検証しており、`attempt-01` / `attempt-+1` のような表記ゆれを `None` に落とす。
- **AC-3**: `classify` は `(pid, starttime)` の4通りを網羅した `match` で分岐し、pid ありで starttime 無しだけが `Err(InconsistentRunFiles)`。猶予の超過は `elapsed_since`(負を 0 に飽和)が `GRACE_PERIOD`(30秒)を**上回った**ときだけ成立し、30秒 / 31秒 / 巻き戻りの3境界がテストされている。`classify_recheck` は pid 無しなら starttime の有無を問わず `SpawnFailed`。分類器は `Timestamp` と観測値だけを受け取り、報告用のパス・文言を持たない。
- **AC-4**: 問い合わせ5種と `WorkspacePlanner::derive` を確認。`applicable_retry_limit` の Cleanup は `effective_retry_limit` に委譲するが、`WorkflowDefinition::effective_retry_limit` は Cleanup に対して常に `DEFAULT_RETRY_LIMIT = 2` を返すため spec の「Cleanup = 2」と一致する。`WorkspacePlanner` の2つの `expect` は `TaskId` の文字集合(`[a-z0-9-]`・先頭英数字)が `WorktreePath` の絶対性と `BranchName` の禁止パターン(`..` / `.lock` / 先頭 `-` / `/` 端)をいずれも構成的に満たすため、不変条件違反のみのパニックになっている。
- **AC-5**: 遷移6種はすべて `self` を消費して新しい値を返し、前提検査(`ensure_restartable` / `ensure_launching`)は6状態を列挙した網羅 `match`。上限超過は `limit_exceeded`(`count > limit`)に集約され、等号で凍結しないことが3経路それぞれでテストされている。`confirm_running` は `spawn_fail_count` のみリセット(`attempt_count` / `judge_attempt_count` は保持)、`record_spawn_failure_in_place` は実行状態も `current_attempt` も変えず次番号も動かさない。`AttemptRef::launching` / `with_process` を `pub(super)` に閉じ、番号と `run_dir` の食い違いを構成で排除している。`TransitionError` の `MissingCurrentAttempt` / `InvalidState { expected: &[ExecutionStateKind] }` は spec の `InvariantViolated { message }` からの意図的な差し替えで、ADR-073(文言は表示側)に沿う。
- **AC-6**: `RunStore` 9・`ProcessController` 3・`WorktreeManager` の `create` 1 のみが宣言され、`attempt_exists` / `list_runs` / `delete_attempt` / `remove_task_dir_if_empty` / `starttime_of` / `kill` / `try_kill_remnants` / `remove` の宣言もスタブも無い。付随する値・エラー型(`WrapperLaunchSpec` / `WrapperIdentity` / `SpawnError` / `WorktreeError` / `RunFileError` / `Io`)はすべて値として返り、trait のドキュメントが契約(read 系のディレクトリ不在 = `Ok(None)`、write 系のアトミック性、`spawn_wrapper` の起動後不関知、`run_agent` の全域性)を明示する。
- **スコープ**: 除外対象(`RunningClassifier` / `JudgementService` / `GcPolicy` / `IdentityCheck` / `NotificationService` / `complete_run` / `skip_run` / `fail_run` / `record_judge_failure` / `advance` / `abort` / `retry` / `set_status` / `mark_notified`)はドメインに1つも現れない。`DegradedTask` は無改変。
- **ドメインの純度**: `crates/pulsen-domain/Cargo.toml` の `[dependencies]` は空のまま。`cfg(test)` 以外の `cfg` は0件。変更ファイルのテストモジュール外のパニックは3箇所(`WorkspacePlanner` の2つと `current_status_def`)で、いずれも生成経路が保証する不変条件に対するもの。
- **ドメインロジックの外部漏れ**: 猶予時間・上限規則・分類・パス配置を再実装している箇所は無い。tick は `LaunchingClassifier` / 遷移関数を呼ぶだけで、`GRACE_PERIOD` も報告文言の生成にしか使わない。`attempt-` 接頭辞・run ファイル名の生リテラルはドメイン外では test の期待値にしか現れない。`branch_of` は実行状態と動作種別の網羅 `match`。
- **実効性**: `cargo test -p pulsen-domain` は 221 件すべて通る。新規テストは前提状態の検査を `every_execution_state()` で6状態網羅し、カウンタ規則・事後条件・境界を仕様の言葉で名付けている。弁明や修正経緯のコメントは無く、残っているのは why(飽和加算の理由・逆写像の検証理由・pid を先に読む理由)のみ。
