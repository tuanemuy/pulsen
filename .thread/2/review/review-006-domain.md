### Warnings

- **[W-001]** `pid` が現れていれば猶予の超過によらず起動確認になることが、どのテストにも固定されていない。
  - 場所: `crates/pulsen-domain/src/execution/launching.rs`(`LaunchingClassifier::classify` のテスト群)、`crates/pulsen/tests/tick_confirm_spawn.rs`
  - 理由: spec の `classify` は「pid・starttime とも Some → `ConfirmRunning`」を経過時間と無関係に定めており、実装も `match (pid, starttime)` を先に置くことでそれを満たしている。しかし `pid` ありのケースを通すテストは `after(1)`(ドメイン)と経過 0(ユースケース。`Harness` の既定時刻が `NOW`)だけで、**猶予超過かつ pid あり**の組み合わせが1件も走っていない。判定の順序を「経過を先に見る」形へ入れ替えても全テストが緑のまま通る。入れ替わると、pid を書き終えたラッパーに対して tick が無効化マーカーを書く経路が生じ、ラッパー側の「pid 書き込み → マーカー確認」と噛み合ってエージェントが起動されないまま running に取り込まれる — 本スライスが順序で防いでいる並走・取りこぼしの片方が復活する。AC-3 の「全分岐と境界が網羅される」に対しても、境界(30/31)と pid 分岐の直積のうち1象限が空いている。
  - 提案: `pidとstarttimeが揃っていれば同定情報つきで起動確認になる` の観測時刻を `after(1)` と `after(31)` の2点に広げる(表明は同じ)。ドメイン側だけで足り、ユースケース側の追加は要らない。

## 確認した内容(指摘に至らなかった点)

- **ドメインの独立性**: `pulsen-domain/Cargo.toml` の `[dependencies]` は空のまま。`crates/pulsen-domain/src/` に `std::fs` / `std::process` / `std::env` / `std::io` / `SystemTime` の参照はなく、ターゲット述語つき `cfg`(`unix` / `windows` / `target_os` / `target_family`)も 0 件。`#[cfg(test)]` のみ(AC-1)。
- **AC-2**: `ExitCode`(`new` / `get` / `is_success`)・`PidFileContent`(pid・kill同定子)と `RunDirPath` の6導出(`pid_file` / `starttime_file` / `exit_file` / `stdout_log` / `stderr_log` / `marker_file`)がいずれも純粋関数で、パス名は定数に集約され、ユニットテストで固定されている。`state_root()` の逆写像は `derive` との一致を条件にしており(ADR-079)、`attempt-01` / `attempt-+1` のような数値として読めてしまう表記が弾かれることまでテストされている。
- **AC-3**: `classify` / `classify_recheck` はともに `match (pid, starttime)` の網羅で、ワイルドカードなし。境界は 30秒=`KeepWaiting` / 31秒=`SuspectSpawnFailure` / 巻き戻り(`elapsed_since` の 0 飽和)=`KeepWaiting` が固定されている。`classify_recheck` の「pid なしなら starttime の有無を問わず `SpawnFailed`」も両方の入力で表明されている。`InconsistentRunFiles` は run_dir も文言も持たず、文脈の付与は報告側(`cli::render`)にある。
- **AC-4**: 問い合わせ5種と `WorkspacePlanner::derive` は spec どおり。`applicable_retry_limit` は AgentRun / Cleanup とも `effective_retry_limit` へ委譲し(Cleanup の 2 は組み込みデフォルトとしてそこから返ることがテストで示されている)、Wait は `None`。`next_attempt_number` は `current_attempt` が `None` なら `FIRST`。
- **AC-5**: 遷移6種はすべて `self` を消費して新しい `Task` を返し、`now` で `updated_at` を更新する。前提状態の検査は6状態の網羅 `match` で、テストも `every_execution_state()` で6状態を回して受理/拒否を主張している。カウンタ規則は `limit_exceeded`(`count > limit`)に集約され、等号で凍結しないこと・0 上限で初回凍結すること・`confirm_running` が `spawn_fail_count` だけを 0 にすること・`record_spawn_failure_in_place` が実行状態も attempt 番号も変えないことが個別に固定されている。`AttemptRef` の生成口は `launching` / `with_process`(いずれも `pub(super)`)に閉じ、番号と `run_dir` の食い違いが構成上書けない。
- **エラーと panic**: ドメインの失敗はすべて `Result` の値。新規コードの `expect` は `current_status_def`(不変条件1・生成経路の両方で保証)と `WorkspacePlanner::derive` の2つのパース(`WorktreeRoot` が絶対パスであること・`TaskId` の文字集合が git 参照名として安全であること)だけで、いずれも不変条件違反にのみ到達する。`TaskId::MAX_LENGTH` 端や `a--b` / `abc-` などの端のIDからも導出できることがテストされている。
- **spec からの逸脱**: `TransitionError`(`expected: &'static [ExecutionStateKind]` / `MissingCurrentAttempt`)・`ToolFailureKind`・`InconsistentRunFiles` の enum 化はいずれも ADR-087 / 088 / 073 に理由と spec 追従の提起が残っており、「不正な状態を型で表現不能にする」「表示の知識をドメインに置かない」の方向へ寄せた変更として筋が通っている。永続化される `FailureKind` は5値のまま。
- **ロジックの配置**: tick / wrapper のユースケースは観測(ポート)→ 判断(`LaunchingClassifier` / `Task` の遷移)→ 実行(ポート)の配線に徹しており、分類規則・カウンタ規則・パス導出の再実装はない。アダプター(`adapter/run_store.rs`)も run ディレクトリ内のファイル名を `RunDirPath` の導出関数から得ている。`confirm_spawn` が pid → starttime の順で読む理由(逆順だと正常な起動が順序破れに見える)はコメントで why として残っている。
- `cargo test -p pulsen-domain` 220件・`cargo clippy -p pulsen-domain --all-targets` は緑。
