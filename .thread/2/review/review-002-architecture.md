#### Warnings

- **[W-001]** `WorktreeManager::create` の適合ケース TC-015 が、`cargo test`(全体実行)の1回で失敗した
  - 場所: `crates/pulsen/src/adapter/worktree.rs:163-235`(`create`) / `crates/pulsen-conformance/src/worktree_manager.rs:283`
  - 理由: このレビュー中の最初の全体実行で `tc_port_worktree_manager_015_別ブランチのworktreeがあれば失敗し既存に触れない` が `panicked at ... 既存の実体には触れず失敗する` で落ちた。この panic は `assert_create_failed` の `Ok(()) => panic!` アームであり、**`create` が「別ブランチの worktree が居座るパス」に対して `Ok` を返した**ことを意味する。plan.md「リスクと注意点」が「パスの存在だけで成功にすると、別ブランチの worktree を掴んだまま起動して他タスクの成果を壊す」と名指ししている失敗モードそのもので、成立すれば tick が他タスクの worktree にエージェントを起動する。その後 `cargo test` 全体 3 回・`--test conformance_worktree` 12 回・スイートバイナリ直起動 25 回・単一ケース 60 回では再現しなかったため Blocker にはしないが、`create` の分岐は `worktree list --porcelain` の出力・`fs::canonicalize`・`try_exists` の3つの観測に依存しており、どれかが揺れると「登録なし・パス不在」経路(`worktree add -b`)へ落ちて `Ok` になる構造を持つ。1/40 でも同定が外れうるなら本番では毎 tick 起こりうる
  - 提案: 少なくとも次のどちらかを行う。(1) 再現条件の特定(`registered_entry` が `None` を返した場合・鍵が一致しなかった場合に、突き合わせた鍵と git の出力を `WorktreeError::Failed` の message に載せて診断可能にする)、(2) `registered_entry` が `None` かつ実体も無いという「新規作成」経路に入る前に、`ws.branch` を指す登録が**別のパス**に無いことも確認して、同定が外れたときに `Ok` ではなく `Failed` へ倒す(安全側に倒す)。再現しないまま残すなら、少なくとも観測した事実を progress.md の「既知の制限」に記録する

- **[W-002]** `Task::is_wait` / `Task::is_cleanup` は本スライスに production の呼び出しが無く、添えられた why が現在の呼び出し元を実際と違う形で述べている
  - 場所: `crates/pulsen-domain/src/task/task.rs:209-239`
  - 理由: doc は「真偽だけが要る経路(`record_launching` の前提検査、**待機の素通し**、手続きBの終端処理)がこれらを使い」と書くが、待機の素通しを担うのは `crates/pulsen/src/application/tick/mod.rs:379-395` の `branch_of` で、そこは `current_status_def()` の網羅 `match`(ADR-083)であって `is_wait` を呼ばない。実際に呼び出しがあるのは `is_agent_run`(`record_launching`)だけで、`is_wait` / `is_cleanup` は本スライスのどこからも呼ばれない(ユニットテストのみ)。ADR-061 は「呼び出しの無い `pub` は落とし、必要になったスライスで理由つきで戻す」と定めており、残すこと自体は AC-4(台帳 DOM-task-050)が要求するので争わないが、**why が現在の形の理由になっていない**のは CLAUDE.md「残すのは現在の形が成り立つ理由」に反する
  - 提案: why を現状に合わせる。「動作種別の3判別は台帳が一組で定める読み取り口で、本スライスで呼ぶのは `is_agent_run` のみ。`is_wait` / `is_cleanup` は #3 / #6 の手続きが使う」のように、いま呼ばれていないことと引き取り先を明示する(`branch_of` が網羅 `match` を使う理由は ADR-083 にあるので、そこを指すのでもよい)

- **[W-003]** `TransitionError` の一部が、表示専用のエラーなのに完成した表示文言をドメインに持っている
  - 場所: `crates/pulsen-domain/src/task/transition.rs:15-19,29-33`、`crates/pulsen-domain/src/task/task.rs:316-318,442-445`、`crates/pulsen/src/cli/render.rs:152-165`
  - 理由: `InvalidState { expected: &'static str, actual: ExecutionStateKind }` の `expected` には `"pending | failed"` という**表示用の文字列**が入り、`render.rs` がそれをそのまま `format!("実行状態が {} ではなく {}", expected, actual.as_str())` に埋めている。`InvariantViolated { message: String }` も同様に日本語の完成文をドメインが作る。ADR-073 は同じ tick の報告について「文言は CLI 層で組み立てる」と決め、`TickIssue` / `InconsistentRunFiles` からは完成文言を外している。`TemplateError::describe` 系(ADR-082)は「タスクファイルに失敗要因として**永続化される**」という why が付いているので別扱いだが、`TransitionError` は永続化されず表示にしか使われないため、その why が効かない。さらに `InvariantViolated`(「起動記録済みのタスクに現在 attempt がありません」)は、手続きCが冒頭で同じ条件を検査して `TickIssue::MissingCurrentAttempt` を積む(`confirm_spawn.rs:41-46`)ため、**同じ事実に構造化された表現と文字列表現の2つが並存**している
  - 提案: `expected` を `&'static [ExecutionStateKind]`(または前提を表す小さな enum)にして文言を `render` に寄せる。`InvariantViolated` は破れの種別を列挙にするか、tick 側の `MissingCurrentAttempt` と重複しない形に整理する
