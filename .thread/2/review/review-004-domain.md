指摘はゼロ。以下は、指摘に至らなかった判断のうち、次のラウンドで蒸し返さないために根拠を残しておくもの。

- **spec との差分はすべて adr.md で決着済み**。`TransitionError::InvalidState.expected: &'static [ExecutionStateKind]` と `InvariantViolated { message }` → `MissingCurrentAttempt`（ADR-073）、`InconsistentRunFiles` の分類化（ADR-073）、`ToolFailureKind` の新設（ADR-078 相当）、`CommandLine::rehydrate`（ADR-071）、`RunDirPath::state_root`（ADR-070 / ADR-079）、write 系のディレクトリ作成を契約に明記（adr.md 321行）。いずれも「表示専用のエラーは分類だけを持つ」「永続化される説明は `describe()` としてドメインに1箇所」という規則で一貫しており、spec 追従の提起対象として記録もされている。
- **`Task::is_wait` / `is_cleanup` は本スライスに呼び出しが無い**が、ADR-061 の基準は `PulsenHome` のレイアウト用アクセサに向けたものであり、spec/domains/task.md が問い合わせ3種を一組の読み取り口として定め、plan の AC-4 が3種すべてを要求している。コード側にも why が添えられている（`Task::is_agent_run` の doc）。落とすべきものとは判断しない。
- **`Task::confirm_running` が不変条件4（AgentRun での workspace 確定）を再検査しない**のは spec の前提状態表（`Launching` のみ）どおり。手動修復で `Launching` かつ workspace 未確定を作れば Running が workspace 無しで成立しうるが、検査点は `record_launching` に置くという spec の設計であり、本スライスで足す性質のものではない。

### 確認した点（要点）

- **AC-2**: `ExitCode`（`is_success` / `get`）・`PidFileContent` が `execution/value.rs` に、`RunDirPath` の6導出関数（`pid_file` / `starttime_file` / `exit_file` / `stdout_log` / `stderr_log` / `marker_file`）が `task/path.rs` にある。すべて I/O を持たない純粋関数で、`runディレクトリのファイル配置は固定の名前で導出される` が6つとも固定名で検証している。ファイル名・段名は `const` に括られ、アダプター（`adapter/run_store.rs`）は導出結果を受け取るだけでレイアウトを持たない。
- **AC-3**: `LaunchingClassifier::classify` / `classify_recheck` は `(pid, starttime)` の網羅 `match` として書かれ、pid Some・starttime None だけが `Err(InconsistentRunFiles::MissingStartTime)` になる。境界は 0/29/30秒 → `KeepWaiting`、31秒 → `SuspectSpawnFailure`、-3600秒 → `KeepWaiting`（`Timestamp::elapsed_since` が負を 0 に飽和）で網羅。`classify_recheck` は pid None を starttime の有無によらず `SpawnFailed` に落とすことを2ケースで主張している。`GRACE_PERIOD` は `DurationSpec` の組み込み定数で、値そのものにもテストがある。
- **AC-4**: 問い合わせ5種を確認。`next_attempt_number` は `current_attempt` None で `AttemptNumber::FIRST`。`applicable_retry_limit` は AgentRun / Cleanup とも `snapshot.effective_retry_limit` に委譲し、`WorkflowDefinition::effective_retry_limit` が Cleanup に対して `DEFAULT_RETRY_LIMIT`(=2) を返すことを確認した（ワークフロー既定値に引きずられない）。Wait は `None`。`WorkspacePlanner::derive` は `path = <worktree_root>/<task-id>` / `branch = pulsen/<task-id>` を全域関数として導出し、`expect` は TaskId の文字集合が保証する不変条件（絶対パス・git 参照名の有効性）に限られている。文字集合の端（`a` / `0` / `a--b` / `abc-` / 最大長）でもテストされている。
- **AC-5**: 遷移6種と `TransitionError` 5種。前提状態の検査は `ensure_restartable` / `ensure_launching` の網羅 `match` に集約され、6実行状態すべてを回すテスト（`every_execution_state`）が遷移ごとに前提の成否を網羅している。カウンタ規則も spec どおり — `limit_exceeded` は `count > limit` の1箇所に集約され、「上限と等しい回数では凍結しない / 超えると凍結する」を `record_spawn_failure` / `record_spawn_failure_in_place` / `record_tool_failure` の3経路で個別に主張。`confirm_running` は `spawn_fail_count` だけをリセットし `attempt_count` / `judge_attempt_count` を保持することを `RetryCounters::rehydrate(1, 2, 0)` で固定。`record_spawn_failure_in_place` は実行状態も `current_attempt` も `next_attempt_number` も変えないことを主張。`record_launching` は `AttemptRef::launching`（`pub(super)`）だけを生成口とし、番号と `run_dir` の食い違いを構成で排除している。
- **AC-6**: `RunStore` 9メソッド・`ProcessController` 3メソッド・`WorktreeManager::create` 1つ増、で spec のポート表と1:1。除外対象（`attempt_exists` / `list_runs` / `delete_attempt` / `remove_task_dir_if_empty` / `starttime_of` / `kill` / `try_kill_remnants` / `remove`）の宣言もスタブも無い。付随する値・エラー型（`WrapperLaunchSpec` / `WrapperIdentity` / `SpawnError` / `WorktreeError` / `RunFileError` / `Io`）はいずれもフィールド非公開＋アクセサ、または報告用の不透明 `message` を持つ enum で、分岐に使う `RunFileError` だけが `Corrupt` / `Io` に分かれている。
- **関数型モデリング全般**: `pulsen-domain/Cargo.toml` の `[dependencies]` は空のまま。ドメイン内に `use` される外部クレートは0件。ターゲット述語つき `cfg`（`unix` / `windows` / `target_os` / `target_family`）はドメインに1件も無い。本番コードのパニックは `Task::current_status_def`（不変条件1、生成経路2つで保証）と `WorkspacePlanner::derive` の2箇所のみ。新規追加分に `_ =>` のワイルドカードアームは無い（`ExecutionState::Stopped { .. }` はフィールド省略であってアームのワイルドカードではない）。すべての遷移が `self` を消費して新しい値を返し、`RetryCounters` の更新系・`AttemptRef` の生成系は `pub(super)` でドメイン内に閉じている。
- **ロジックの漏れ**: `application/tick/{mod,launch,confirm_spawn}.rs` と `application/run_wrapper.rs` は判断をすべてドメイン（`Task` の遷移関数・`LaunchingClassifier`）に委ね、猶予時間・上限超過・分類規則を再実装していない。適合スイート（`pulsen-conformance/src/{run_store,process_controller}.rs`）とテストダブルにもドメイン判断の複製は無い（`is_success` の利用のみ）。`FsRunStore` はパスを `RunDirPath` の導出関数から取り、レイアウト定数を持たない。表示文言は `cli::render` に集約され、ドメインに残る `describe()` はタスクファイルに永続化される説明（展開失敗の失敗要因）に限られている。
- **コメント**: 経緯・弁明の記述は見当たらない。ドメイン側のコメントはいずれも why / why not（飽和加算にする理由、逆写像を `derive` の直下に置く理由、write 系がディレクトリを作ることを契約にする理由、`ToolFailureKind` を分ける理由、`InconsistentRunFiles` に run_dir を持たせない理由）。
- **実行確認**: `cargo test -p pulsen-domain --lib` = 220 passed / 0 failed、`cargo clippy -p pulsen-domain --all-targets` = 警告なし（`wildcard_enum_match_arm = warn` を含む）。
