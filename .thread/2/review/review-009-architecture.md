マージを妨げる欠陥は見つからなかった。以下は確認の要点。

- **依存方向**: `pulsen-domain/Cargo.toml` の `[dependencies]` は空のまま(Cargo.toml 群に差分なし = 新規依存ゼロ)。`crates/pulsen-domain/src/` に `std::fs` / `std::process` / `std::env` の出現は0件で、ドメインは I/O に触れない。`pulsen-conformance` の依存も `pulsen-domain` のみ。
- **OS 依存の隔離(AC-1)**: testing.md が定める grep(`cfg\([^)]*\b(unix|windows|target_os|target_family)\b`)を実行し、`crates/pulsen-domain/` が0件、`crates/pulsen/src/` 側が `util/atomic.rs` / `adapter/process.rs` / `adapter/task_repository.rs`(`#[cfg(all(test, unix))]`)の3ファイルであることを確認。期待値と一致する。`cargo fmt --check` / `cargo clippy --all-targets -- -D warnings` / `cargo test --workspace` はいずれも緑(全357件、失敗0・スキップ0)。
- **合成ルート**: `env::current_exe` / `env::current_dir` / 乱数の解決はいずれも `cli::wire` の中に閉じ、`compose()` からは切り出されている(ADR-068 / ADR-091)。`tick` は `wire::process_controller()` だけを追加で呼び、`add` が `workflow_store()` / `id_generator()` を呼ぶ。ラッパーは `compose_wrapper(&run_dir)` でホームも config も読まず、`RunDirPath::state_root()` から `StateRoot` を復元する(ADR-070 / ADR-079)。`WrapperRuntime` を別型にしたことで、ラッパー経路にホーム解決が紛れ込まない形が型で示されている。
- **未実装メソッドの宣言・スタブの不在(AC-6)**: `attempt_exists` / `list_runs` / `delete_attempt` / `remove_task_dir_if_empty` / `starttime_of` / `kill` / `try_kill_remnants` / `WorktreeManager::remove` はソース中に宣言が1件も無く、ヒットするのは適合スイート冒頭の「後続スライスで扱う」旨の doc コメントだけ。`GcPolicy` / `RemoveOutcome` / `RunningClassifier` / `JudgementService` / `IdentityCheck` / `CommandRunner` / `NotificationService` / `NOTIFY_TIMEOUT` / `complete_run` / `skip_run` / `fail_run` / `record_judge_failure` / `advance` / `abort` / `retry` / `set_status` / `mark_notified` も0件。`RunStore::read_exit` は AC-6 が挙げる9メソッドに含まれ、`port.rs` 冒頭に「同一スライスで行う書き込みと対になる読み取り」という宣言基準の why がある。
- **スコープ外の実装の不在**: `Branch` の網羅 `match`(`tick/mod.rs`)で `Cleanup` / `Observe` / `Advance` / `Notify` のアームは空で、引き取り先の Issue 番号だけを why コメントとして持つ(ADR-065)。ダミーの処理もエラー報告も無い。
- **`wrapper` の引数の往復(AC-11)**: `adapter/process.rs` が組む argv(`wrapper --run-dir <p> --workspace <p> -- <tokens...>`)の定数 `WRAPPER_SUBCOMMAND` / `RUN_DIR_FLAG` / `WORKSPACE_FLAG` / `COMMAND_SEPARATOR` は `pub` で、受け入れテスト `tests/common/mod.rs::wrapper()` が同じ定数から argv を組んで実バイナリを起動する。`pub` の理由(定義箇所が CLI とアダプターに分かれるので往復テストで受理を主張する)が定数の doc にある。`trailing_var_arg` + `allow_hyphen_values` で `-` 始まり・空文字列トークンを受ける(ADR-069)。実機で `pulsen wrapper --run-dir rel ...` が非0・run ディレクトリ無書き込みで終わることも確認。
- **終了コードと出力先**: `cli/mod.rs` は成功を `println!`、失敗を `eprintln!` に振り分け、tick のロック競合だけ 0(pages の exit code 規約)。実機確認 — 空ホームの `tick` は「処理対象のタスクはありませんでした。」で 0、config 不在の `tick` は未初期化案内で 1、不正引数の `wrapper` は 1。`--help` の一覧は `add` / `tick` / `help` で `wrapper` は現れず、`wrapper --help` は到達できる(`tests/cli_usage.rs` が両方を主張)。
- **出力と縮退状態の共通規則**: `render::tick_summary` は ADR-090 の3見出し(「失敗を記録」/「起動の結果が未確定」/「スキップ」)を `issue_outcome` の網羅 `match` で振り分ける。分類を足したら振り分け先を決めない限りコンパイルが通らない。ADR-084 の不変(書き込んだ経路は必ずサマリーのいずれかを埋める)は `commit` / `errors` の集計として成立している。
- **ADR 参照の解決と記述の一致**: 本文が参照する ADR-065〜091 はすべて `.thread/2/adr.md` に実在し、`.adr/` の既存番号(最大 064)と衝突しない。ADR-027 の変更(フック対応表の正本を HOOKS.md 一本にする)は HOOKS.md 末尾の宣言と整合。HOOKS.md の集計(9ポート169行 / A38・B113・C18)は追加分(worktree 7 + run store 21 + process controller 16 = 44)と一致し、区分別の内訳も各節の見出しと合う。適合の実行件数(process_controller 16 / run_store 22 = 21+追加1 / worktree 17 = 16+追加1)も AC-8 / AC-9 / AC-7 の宣言どおり。
- **呼び出しの無い `pub` の why**: `Task::is_wait` / `is_cleanup` は本スライスに本番の呼び出し側が無いが、「spec が一組で定める読み取り口」であることと、tick が `current_status_def` の網羅 `match` を通す理由が `is_agent_run` の doc に書かれている(AC-4 が3種を要求)。`RunDirPath::attempt_dir_name` の `pub` は plan.md と doc に理由がある。
- **`.thread/2/` の記述と実装の食い違い**: plan.md の AC-1 / AC-6 / AC-8 / AC-9 / AC-11 / AC-12 / AC-18、スコープの「含まれないもの」、ADR-065〜091 の Decision を実装と突き合わせて相違なし。progress.md の「spec 追従の提起」11項目はいずれも実装の現状と対応している。
- **実効的なテスト**: `tests/cli_tick.rs`(16件)が AC-12 の各点(ロック競合0スキップ・破損タスクファイルの混在・スナップショットのみ破損・アーカイブ除外・`state/tasks/` 未作成・対象リポジトリの外からの起動)を、`tests/cli_tick_missing_cwd.rs` が「作業ディレクトリを失っていても tick が成立する」を実バイナリで裏付ける。`tests/cli_wrapper.rs` が argv の往復と run ディレクトリの成果物を実バイナリで観測する。
