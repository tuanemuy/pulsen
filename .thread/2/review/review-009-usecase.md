マージを妨げる欠陥は見つからなかった。以下は確認できた事実の記録。

- **処理フロー1〜9**: `Tick::execute` が「ロック取得 → `list_active` → エントリ分岐 → サマリー」の順で、ロック競合は `TickOutcome::Skipped`(CLI で 0)、`LockError::Failed` と `ReadError::Io` だけが `TickError`(非0)。手続きB・E は未配線で、`run_retention` の分岐そのものが存在しない(スコープ外の不実装)。
- **手続きA の順序**: `ensure_workspace` → `expand` → `record_launching` → `commit` → `prepare_attempt` → `spawn_wrapper` が spec と ADR-016 の順に一致。`record_launching` の保存に失敗した場合は `prepare_attempt` も `spawn_wrapper` も呼ばずに打ち切り、`prepare_attempt` の失敗は報告のみで spawn を続行、`spawn_wrapper` の同期エラーでも実行状態・`spawn_fail_count` を変えない。テンプレート展開の5経路はすべて `record_spawn_failure_in_place` に落ち、attempt を採番しない。
- **手続きC の順序と競合窓**: `read_pid_file` → `read_starttime` → `classify` → (猶予超過なら) `write_invalidation_marker` → 再読 → `classify_recheck`。マーカー書き込みの `Err(Io)` は状態を変えずに報告してスキップする。読み取りを pid 先行にしているため、正常な起動が「pid あり・starttime なし」と誤観測されない。マーカー書き込みが pid の再読より前にあり、ラッパー側の「pid 書き込み後にマーカー確認」と対になっているため、遅延起動したラッパーが新 attempt と並走する窓は残らない(マーカー書き込み後に pid が現れた場合は running へ取り込み、ラッパーは未起動で終わる — 次tickの「exit なし・プロセス死亡」に委ねる spec の記述どおり)。
- **`RunWrapper` の順序**: `own_identity` → `write_starttime` → `write_pid_file` → `marker_exists` → `run_agent` → `write_exit`。`marker_exists` の `Ok(true)` と `Err(Io)` を同じアームで起動抑止に倒し、1〜3 の失敗は `Silent` として何も書き残さない。config もロックも触れない。
- **1タスクの失敗での続行**: `process` はエントリごとに独立し、失敗は `TickIssue` として `errors` に積むだけで走査は続く(`あるタスクの処理が失敗しても残りのタスクは続行する`)。
- **書き込んだ tick の報告**: タスクファイルへ書き込む全経路が `launched` / `confirmed_running` / `frozen` / `errors` のいずれかを埋める。`commit` が `Persisted::Failed` を返した場合は成功側の計上を行わないため、永続化できていない凍結・失敗記録がサマリーに載らない(`凍結を伴う遷移を保存できなければ凍結にも失敗の記録にも数えない`)。
- **冪等性**: 判断材料は永続化された事実と `Clock` だけで、`状態が変化しないタスク群には連続実行しても書き込みが発生しない` / `worktree作成の直後にクラッシュしても同じワークスペースが再導出される` / `破損したrunファイルが削除されれば不在として無効化マーカー経路に合流する` が連続 tick で確認されている。
- **未配線アーム**: `Branch` の網羅 `match` で `Cleanup` / `Observe` / `Advance` / `Notify` を空アームにし、`配線していない分岐のタスクにはエージェントを起動せず書き込みもしない` が「2本目のラッパーを起動しない」ことだけを主張している(#3 / #6 がアームを埋めても書き換えにならない形)。
- **判断と副作用の分離**: `branch_of` は純粋関数、上限超過の判定は `Task` の遷移関数、猶予時間の判定は `LaunchingClassifier`。ユースケースは「観測 → 判断 → 実行」の配線と報告のみ。凍結の有無を保存後の状態から導出せず `Freeze` として遷移側から渡す設計も、#3 の catch-up 通知で過去の凍結を再計上しない根拠として成立している。
- **実効的なテスト**: `ScriptedRunStore` / `ScriptedProcessController` は台本を使い切ると panic するため、想定外の余分な呼び出しが緑にならない。AC-17 の一覧(ロック機構の異常・`list_active` の Io・worktree 作成失敗と上限超過・展開失敗5経路・`prepare_attempt` 失敗・spawn の同期エラー・`RunFileError` 各種・マーカー書き込み失敗・猶予境界 30/31/巻き戻り・`save` 失敗)はすべてダブルに対するユースケーステストで消化されている。順序の主張は `calls()` の並びで行われ、結果の値では表せない性質を実際に押さえている。`cargo test -p pulsen --test tick_scan --test tick_launch --test tick_confirm_spawn --test run_wrapper` は全件 pass。
- **AC の検証**: AC-10 / AC-12 / AC-13 / AC-14 / AC-15 / AC-17 はいずれも対応するテスト(`run_wrapper.rs` / `cli_wrapper.rs` / `tick_scan.rs` / `tick_launch.rs` / `tick_confirm_spawn.rs` / `cli_tick.rs` / `cli_tick_missing_cwd.rs`)で裏付けられている。「スコープ / 含まれないもの」に挙がった要素(手続きB・D・E、notify、`attempt_exists`、abort / retry / set-status、`DegradedTask` の再通知)はコードにもポートにも現れない。
- **残す必要のない記述**: ユースケース層・CLI 層・テストのコメントはいずれも why / why not に留まり、指摘への弁明や修正経緯は残っていない。
