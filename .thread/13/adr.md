# ADR — Issue #13: ロック保持フィクスチャの合図タイムアウトが、スキップではなく失敗として現れる

採番はこのファイル内の連番。`.adr/` への昇格判定は片付けフェーズ(steps.md ステップ10)で行い、昇格するときは `.adr/073` 以降を使う(既存の最大番号は 072)。

判定の結果、ADR-001 / 002 / 003 / 005 / 006 を1本に畳んで `.adr/073-holder-capability-skip-vs-fail.md` に昇格した。ADR-004 / ADR-007 は寿命テストは満たすが波及テストを満たさないため作業ログ限りとする。各エントリの Status 行を参照。

## ADR-001: 合図のタイムアウトは環境の能力の probe として表し、`SkipBudget` の宣言をそこから導く

### Status

Accepted → `.adr/073-holder-capability-skip-vs-fail.md` の「決定」の「能力は probe で1度だけ判定し、宣言と挙動の双方がその1点を見る」に昇格

### Context

`spawn_holder` は「実行ファイルが無い」と「合図が `SIGNAL_DEADLINE` 以内に返らない」を区別せず `None` を返し、許容集合は `holder_program().is_some()`(＝前者)だけを見ている。後者が起きると、環境の遅さが `SkipBudget` 違反＝実装の失敗として現れる。

区別の付け方には2つの方向がある。

1. **`spawn_holder` の戻り値の型で区別し、タイムアウトの事実を許容集合へ反映する** — `SkipBudget` は `LazyLock`(`crates/pulsen-conformance/src/lib.rs` の `conformance_cases!` が生成)で、最初の `record` の時点で許容集合を確定する。観測してから宣言へ書き写す構造になり、`.adr/068` が「前提を直接見るので循環しない」として避けた形に戻る。加えて対象5件は並列に走るため、2件目以降のタイムアウトは評価済みの集合に間に合わず、非決定的な赤が別の形で残る。
2. **能力の probe を先に置き、宣言と挙動の双方がそれを見る** — `.adr/055` の `permission_restrictions_effective`、`.adr/071` の「probe + 許容集合」と同じ形。

`SIGNAL_DEADLINE` を延ばす対処は Issue 本文が明示的に否定している(閾値を動かしても区別は付かない)。`cfg(windows)` の決め打ちは `.adr/071` が却下している(成立するかは環境の能力の問題で、OS の問題ではない)。

### Decision

`crates/pulsen/tests/common/lock.rs` に `HolderCapability`(`Available`(解決済みの実行ファイルは `lock.rs` の外へ出さない) / `SignalTimedOut` / `ProgramMissing` / `ProgramUnusable(io::Error)` — 最後の1つを分ける理由は ADR-007)と、`OnceLock` で1度だけ評価する `holder_capability()` を置く。`spawn_holder` / `hold` と、`conformance_lock.rs` / `common/mod.rs` の `allowed_skips()` は、いずれもこの1点だけを見る。許容集合に足すのは `SignalTimedOut` のときだけ。

2つの方向は択一ではなく、probe を骨として、起動結果の型の区別(`Started`)をその材料に使う。

probe が「実際に1回保持させてみる」形を取るのは、それがフィクスチャの本番の手順そのものだから。`probe_permission_restrictions`(`crates/pulsen-conformance/src/lib.rs:236-237`)の「フックが掛ける制限と同じ手順で判定するため、判定と実際のスキップが食い違わない」と同じ性質をロック側にも与える。

### Consequences

- 良い点: 評価順・並列実行に関わらず、宣言と実態が一致する。吸収の形が `.adr/071` の「probe + 許容集合」に乗るため、新しい原則を足さずに済む。
- 良い点: `SignalTimedOut` 環境での待ち時間が減る。現状は4〜5件がそれぞれ期限ぶん待つが、変更後は probe の1回だけが待ち、残りは起動を試みずに `None` を返す。
- 良い点(ただし射程は限られる): probe が Windows の初回起動スキャンの代金を先に払うので、本番5件は温まった状態で走る。**これで減るのは cold-start 由来の遅さだけ**で、Issue が挙げたもう一方の要因(負荷の高い共有ランナー)は probe の測定条件に入っていない — probe が測るのは1プロセスの単発の起動で、本番の4件が libtest の既定で並列に走る負荷も、`cli_add_error.rs` 側で重なる `pulsen` 本体の起動も再現しない。「宣言と実態が一致する」は無条件に成り立つが、「間欠性そのものが減る」は cold-start 分に限られる(裏から書いたものが ADR-006 のトレードオフ)。
- トレードオフ: probe が本番のケースと同じ資源(プロセス起動)を1つ奪う。`.thread/10/steps.md` が挙げた懸念だが、コストは1プロセスぶんで、それが warm-up を兼ねることでほぼ相殺される。
- トレードオフ: **probe の測定は無負荷では行われない。** `holder_capability()` は `OnceLock` の遅延評価なので、probe が走るのは最初にロックの能力を必要としたテストスレッドの中 — すなわち同じテストバイナリの他のケースが並列に走っている最中である(`conformance_lock` では4件がほぼ同時に到達し、`cli_add_error` では他のケースの `Home::new()` / `Repo::with_commit()` や `pulsen` 本体の起動が並行する)。しかも1回きりなので、負荷の山に当たった1回が全体の宣言を決める。偽陽性で `SignalTimedOut` に倒れると許容集合が黙って広がり、5件が走らなくても緑になる。誤差は安全側に効かない。`.adr/068` が既に記録した「マージ後の環境退行に機械的な歯止めが無い」の範囲内で、`SKIP` 一覧には現れる。

## ADR-002: 能力側と失敗側を分ける基準 — 実行ファイルの不在も起動の失敗も許容集合に入れず、ケースの失敗にする

### Status

Accepted → `.adr/073-holder-capability-skip-vs-fail.md` の「決定」の「能力側と失敗側を分ける基準」と、「影響」の `.adr/068` の帰結が改まる項に昇格

### Context

現状の `conformance_lock.rs:112` と `common/mod.rs:46` は `holder_program().is_none()` を許容集合に入れている。一方 `.adr/068` は「`--workspace` を選ぶこと自体がこの経路の構造的な回避であり、`SkipBudget` の許容集合には入れない(HOOKS.md の方針)」と明記しており、記述と実装がずれている。

実行ファイルの不在は、環境の能力ではなくビルド構成の誤り(example がビルドされない実行の仕方を選んだこと)である。許容集合に無条件で足すと、フィクスチャの作り忘れまで緑になる。

ただし「ビルド構成の誤りだから失敗」という理由だけでは、能力の型の4区別を振り分けられない。`ProgramUnusable`(実行ファイルはあるが起動できない — Defender の隔離・`noexec` マウント・実行形式の不一致)は実行の仕方の誤りではなく、`crates/pulsen/tests/` の中では手の打ちようがない環境の性質であり、その点で `SignalTimedOut` と同じ顔をしている。どちらへ倒すかを決められる基準そのものが要る。

### Decision

**基準:** 許容集合に入れてよいのは、スキップにしたときに「なぜ走らなかったか」と「次に何をすればよいか」がその宣言だけから定まる能力に限る。定まらないものは静かな緑にせず、赤にして材料を人の目の前に出す。この基準で4区別は次のように分かれる。

- `SignalTimedOut` → **能力側。** 観測が「合図が期限内に返らなかった」に閉じており、環境の遅さという説明と、負荷の低い環境なら成立するという見通しが宣言から読める。
- `ProgramMissing` → **失敗側。** 原因も回避方法も一意(`cargo test --workspace` のように example をビルドする形で回す)。緑にすると、フィクスチャの作り忘れをそのまま隠す。
- `ProgramUnusable` → **失敗側。** 起動が失敗した理由は `spawn` が返した `io::Error` としてしか手元に無く、それが恒久的な環境の性質なのか一度きりの事故なのかを probe は判別できない。スキップに逃がすと、次に何をすればよいか誰にも分からない緑が残る。赤にすれば `io::Error` が案内に載り、その環境で何が起きているかを人が判断できる(ADR-007 のトレードオフ欄が「この経路は実地の検証を持てない」と認めていることも、静かな緑にしない側を支える)。
- `Available` → 該当なし(ケースが走る)。

`ProgramMissing` は許容集合に入れず、そのケースの失敗にする。ズレは実装側を `.adr/068` に寄せて解く(ADR には手を入れない)。失敗メッセージには、`ProgramMissing` なら原因(実行ファイルの不在)と回避方法(`cargo test --workspace` のように example をビルドする形で実行する)を、`ProgramUnusable` なら `io::Error` の内容を含める。

`.adr/068` は書き換えないが、この決定はその「決定」欄が述べた帰結 — 単一テストターゲット指定でロック系のケースが「宣言済みスキップ」に化ける — を過去のものにする。ADR は判断が下された時点の記録なので遡って直さず、**現行の述語へ辿る導線は後から来た側に置く**。すなわち、この決定を昇格させる `.adr/073` の「影響」に、068 のこの帰結が「4件＋1件が失敗する」に改まった旨を1文書く。`.adr/` が相互参照する運用(`.adr/005` / `037` / `071`)と同じ形であり、068 だけを読んだ人が古い帰結のまま止まらない。

### Consequences

- 良い点: 「スキップを緑と誤認しない」という `.adr/055` の狙いが、フィクスチャの作り忘れに対しても効く。記述と実装のズレが消える。
- 良い点: 振り分けが基準で決まるので、後から区別が増えたときも同じ問い(スキップの宣言だけで次の一手が定まるか)で判断できる。
- 良い点: 古くなる ADR を書き換えずに、前方参照で現行の述語へ繋ぐ形が取れる。`.adr/` の「判断時点の記録」という性質と、正本を読んだ人が現在の姿に辿り着けることが両立する。
- トレードオフ: `cargo test --test conformance_lock` / `--test cli_add_error` の単体実行が、これまでの緑から5件の失敗に変わる。失敗メッセージが理由と回避方法を持つ以上、緑に見える状態より危険度は低い。CI は `--workspace` なので影響を受けない。
- トレードオフ: 保持プロセスを一切起動できない環境では5件が赤のままになり、`cargo test --workspace` が緑にならない。その環境を許容集合へ入れるかどうかは、案内に出た `io::Error` を根拠に改めて下す判断であり、材料の無いまま宣言を広げる形は取らない。

## ADR-003: probe の置き場所はテストのフィクスチャ層(`tests/common/lock.rs`)にする

### Status

Accepted → `.adr/073-holder-capability-skip-vs-fail.md` の「決定」の「probe の置き場所の基準」に昇格

### Context

既存の probe には2つの置き場所の前例がある。`permission_restrictions_effective` は `crates/pulsen-conformance/src/lib.rs`(スイート側)、`tmpdir_outside_repository` は `crates/pulsen/tests/common/git.rs`(適用側)。

### Decision

`crates/pulsen/tests/common/lock.rs` に置く。

保持プロセスのパス解決は `env!("CARGO_BIN_EXE_pulsen")` を起点にする(`.adr/032`)ため、`pulsen` クレートのテストターゲットでしか成立せず、`pulsen-conformance` からは書けない。加えて、`lock_holder` という具体的なフィクスチャの存在は適用側の知識であり、別実装(in-memory 等)にスイートを適用する後続スライスがその知識を背負う筋合いは無い。`ExclusiveLockHarness` の trait 定義もフックのシグネチャも変えない。

同じファイルに置くことで、`conformance_lock.rs`(適合4件)と `cli_add_error.rs`(受け入れ1件)が同じ判定を共有し、両者の扱いが割れない(`.adr/055` が「同じ probe を受け入れテスト側のスキップ集計にも使えるため、適合スイートと CLI テストで root への態度が割れない」としたのと同じ理由)。

同じ立場を正本の表にも適用する。`HOOKS.md` の「判定」列は、フック由来の行ではフック水準(「ハーネスが `hold_from_other_process` / `try_acquire_from_other_process` を提供するか」)で書かれている。ここに適用側にしか存在しない関数名を主語として置くと、スイートの正本がこの適用先に結合する。判定列はフック水準の主語を保ち、この適用先での実態(合図が期限内に返るか)は括弧の補足として書く。先例の `permission_restrictions_effective` が判定列に直接現れるのは、それがスイート側(`pulsen-conformance`)の関数だからで、事情が違う。

この縛りは判定列だけでなく、同じ行の「前提を作れない環境」列にも掛ける。列が違っても正本が適用先に結合することに変わりはなく、`SIGNAL_DEADLINE` のような適用側の定数名を書けば、`crates/pulsen/tests/` での改名だけで表が古くなる。閾値の名前は適用側の関心で、この列が伝えるべきは前提の壊れ方(合図が期限内に返らない)だけである。

### Consequences

- 良い点: 依存の向きが崩れない。スイートは適用先を知らないままでいられる。コードでも表でもその立場が揃う。5件の判定が1箇所に集まる。
- トレードオフ: `permission_restrictions_effective` と probe の置き場所が2箇所に分かれる。分岐の基準(スイート側が判定できる能力か、適用側の具体的フィクスチャに依存する能力か)は明確なので、判断に迷う形にはならない。

## ADR-004: `spawn_holder` の戻り値は `Option` のまま「宣言済みスキップか」だけを運び、失敗はパニックで表す

### Status

Accepted(作業ログ限り。昇格しない) — 寿命テストは満たすが波及テストを満たさない。`None` の意味の絞り方とパニックで失敗を表す形は `crates/pulsen/tests/common/lock.rs` に閉じており、フックの `Option` 契約もハーネスの trait も変えないので、覆しても波及先は同ファイルの中に留まる。理由はコードのすぐ横の doc コメントで伝わる

### Context

区別を呼び出し側へどう届けるかに選択肢がある。

1. **`spawn_holder` が3値(または `Result<Option<_>, _>`)を返し、呼び出し側3箇所がそれぞれ `match` する** — 型としては最も明示的。ただし判断(どれをスキップにし、どれを失敗にするか)が3箇所へ散り、`hold` / `hold_from_other_process` / `try_acquire_from_other_process` のそれぞれで取り違えられる余地が残る。フックの戻り値は `Option` なので、結局どこかで潰す必要がある。
2. **`Option` のまま `None` の意味を1つに絞り、失敗はパニックで表す** — 区別は `HolderCapability` が持ち、境界の `Option` は「宣言済みスキップかどうか」だけを運ぶ。

`CLAUDE.md` の「エラーは値として返す。パニックは不変条件違反にのみ使う」はドメイン層の規約であり、テストのフィクスチャは既に `expect("一時ホームを作れる")`(`tests/common/mod.rs`)の形で前提の破れをパニックで表している。

### Decision

2を採る。`spawn_holder` / `hold` の `None` は「この環境は合図を期限内に返せない(＝宣言済みスキップ)」だけを意味する。実行ファイルの不在・起動の失敗・合図の読み取り失敗(ADR-007)と、probe 成立後のタイムアウトはパニックさせる。

あわせて `hold` の `!locked`(誰も保持していないパスでロックを取得できなかった)も `None` から外してパニックにする。ここを `None` のままにすると、`None` がふたたび2つの意味を持ち、本Issueが解こうとしている病がそのまま残る。`try_acquire_from_other_process` は `locked == false` が正当な観測結果になりうる(TC-004 がそれを判定する)ので、`spawn_holder` が `bool` を返す形は保つ。

`holder_program()` は private にする。古い述語を使う呼び出し側が残らないことをコンパイラに保証させる。

### Consequences

- 良い点: `None` の意味が1つになり、フックの `Option` 契約を変えずに区別が成立する。判断が `lock.rs` の1箇所に集まる。
- トレードオフ: 失敗が型ではなくパニックで表れるため、「どの失敗が起きうるか」はシグネチャからは読めずドキュメンテーションコメント頼りになる。テストのフィクスチャという位置づけと、既存の `expect` の使い方に揃える判断。

## ADR-005: probe の判定基準は「合図が期限内に返ったか」に限り、ロック取得の成否は含めない

### Status

Accepted → `.adr/073-holder-capability-skip-vs-fail.md` の「決定」の「probe の判定基準は『合図が期限内に返ったか』だけに限る」と「期限の無い待ちは、正常に保持できたと分かっている相手にだけ許す」(射程の限定を含む)に昇格

### Context

probe が起動した保持プロセスは、新しい一時パスに対して必ずロックを取れるはずである。取れなかった場合(`locked == false`)や、合図を読み取れなかった場合をどう扱うかで、`HolderCapability` に区別を足すかどうかが決まる。

### Decision

probe は「合図が期限内に返ったか」だけで `Available` / `SignalTimedOut` を決め、`locked` の値は捨てる。合図を読み取れなかった場合も、期限内に返ったことは確かなので `Available` に数える。誰も保持していないパスでロックを取得できないことも、合図を読み取れないことも、環境の能力ではなく異常なので、パニック(ADR-004 / ADR-007)としてケース側に現れる。

この判定基準は後始末にも掛かる。probe が起動した保持プロセスは `kill()` + `wait()` で畳み、stdin を閉じて正常終了を待つ `release` は使わない。probe は正常終了できるかを測っていないので、後始末をそこに依存させると測っていない性質でハングしうる。しかも probe は `OnceLock::get_or_init` の中にあり、期限の無い `wait()` で止まれば `holder_capability()` を呼ぶ全スレッド(`SkipBudget` の `LazyLock` 初期化を含む)がそこで止まる。`.adr/060` が「フィクスチャのハングはテストの失敗より診断が難しい」として期限を置いた対象を、probe で期限の無い待ちに戻さない。

同じ基準を、`spawn_holder` / `hold` の**失敗経路の後始末**にも掛ける。合図を読み取れなかった場合(`SignalUnreadable`)も、誰も保持していないパスで取得の合図が返らなかった場合(`!locked`)も、保持プロセスが想定どおりに振る舞っていないと判断した直後であり、そこからパニックする相手の正常終了を期限なしに待つ理由が無い。どちらも `kill()` + `wait()` に揃え、`release` を使うのは正常に保持できたプロセスを畳むときだけにする。`lock_holder` は取得に失敗すれば即終了するので `!locked` の `release` が実際に止まる確率は低いが、同じ関数の2つの失敗経路で後始末の基準が割れる形を残さない。

**この基準の射程は probe と `lock.rs` の失敗経路の2つに限る。** 適合ハーネスの `try_acquire_from_other_process` は `locked` の値によらず `release` を呼ぶので、取得できなかった保持プロセスの正常終了を期限なしに待つ形が残るが、そこは射程の外に置き、実装は変えない。ここに期限を掛けるには子の終了を期限つきで待つ汎用の手当てと3 OS での検証が要り、`lock_holder` を触れない以上この経路の実地検証の手段も無い。射程を広げるのはその手当てと同時にする。

### Consequences

- 良い点: probe が測るものと、probe が依存するものが一致する。判定にも後始末にも「合図が期限内に返るか」以外の前提が入らない。
- 良い点: 「期限の無い待ちは、正常に保持できたと分かっている相手にだけ許す」という基準が、probe と `lock.rs` の失敗経路の双方に同じ形で通る。射程はこの2つで、適合ハーネスからの `release` 呼び出しは含まない。
- 良い点: 能力の区別が「保持プロセスを使えるか」の軸だけで閉じ、ロック取得や合図の読み取りの異常で変異が増えない。
- トレードオフ: probe は本番の手順を「合図まで」しか再現せず、ロックが実際に効くかまでは確かめない。その差は最初のケースで失敗として現れるので、静かな緑にはならない。
- トレードオフ: `kill` で畳むため、保持プロセスが正常終了の経路を通らない。probe が使うのは自分で作った一時ディレクトリのロックだけなので、後片付けの取りこぼしは `tempfile` の削除に吸収される。

## ADR-006: probe が `Available` と判定したあとのタイムアウトは失敗にする

### Status

Accepted → `.adr/073-holder-capability-skip-vs-fail.md` の「決定」の「probe が成立したあとのタイムアウトは失敗にする」に昇格

### Context

probe が成立した環境でも、本番のケースで合図が期限を超える可能性は残る。ここを再びスキップへ逃がすこともできる。

### Decision

失敗にする。温まったあとのタイムアウトは環境の遅さではなく異常として読める。ここをスキップへ逃がすと、区別を作った意味が消える。

実際に赤が出た場合の対処は `.adr/071` の停止規則で `crates/pulsen/tests/` の中(`SIGNAL_DEADLINE` の調整)に収まる範囲であり、そのときは区別が付いているので閾値を動かす判断を正当に行える。

### Consequences

- 良い点: 「環境の能力」と「異常」の線が、probe の成立という観測可能な事実で引かれる。
- トレードオフ: probe が通ったあとに一度だけ極端な負荷を踏むと赤になる。probe が測るのは1プロセスの単発の起動で、本番の4件が同時に立ち上がる負荷そのものを再現しないため、この余地は残る(ADR-001 の良い点の射程を裏から書いたもの)。その赤は原因(probe は通ったのにタイムアウトした)がメッセージから読めるので、原因の見えない間欠的な赤にはならない。

## ADR-007: 「起動できない」「合図を読み取れない」を、それぞれ独立した区別として持つ

### Status

Accepted(作業ログ限り。昇格しない) — 寿命テストは満たすが波及テストを満たさない。増えた区別はいずれも「失敗として現れる側」の内訳で、許容集合の述語(合図のタイムアウトか否か)を動かさないため、覆しても波及先は `crates/pulsen/tests/common/lock.rs` とそのパニック文言に留まる。`ProgramUnusable` を失敗側に置く**理由**は `.adr/073` の基準として昇格済み

### Context

現行 `spawn_holder` の `None` には5つの経路が潰れている — 実行ファイル不在・`spawn` の失敗・`stdout` の取得失敗・合図の期限超過・合図の読み取りエラー。ADR-001 が分けたのはこのうち先頭と4つ目で、残りをどこに寄せるかが決まっていない。

素直な寄せ方には、それぞれ原因を取り違える形がある。

- **起動の失敗を `ProgramMissing` に寄せる** — Issue が名指しする Windows Defender は、初回起動を遅らせるだけでなく実行ファイルを隔離・ブロックしうる。そのとき出る案内は「実行ファイルが無い。`cargo test --workspace` で実行する」で、原因も回避方法も誤っている。加えて現行は `spawn` の `io::Error` を `.ok()?` で捨てているため、診断に要る情報(`Permission denied` / `Operation not permitted` / `%1 は有効な Win32 アプリケーションではありません` など)がどこにも出ない。
- **読み取りエラーを `Signaled { locked: false }` に寄せる** — 「合図を読めなかった」が、`hold` では `!locked` の失敗(取得の合図が返らなかった)として、`try_acquire_from_other_process` 経由では TC-004 の「ドロップで解放され、別プロセスが取得できる」の失敗として現れる。どちらも実際の原因を述べていない。

本Issueが直しているのはまさに「原因の違うものが同じ顔で出る」ことなので、区別を作った先で同じ潰し方を繰り返さない。

### Decision

- 能力の型に `ProgramUnusable(io::Error)` を足し、`ProgramMissing`(実行ファイルが無い)と分ける。値は `spawn` が返した `io::Error` をそのまま持ち、パニックメッセージに載せる。文字列に畳まないのは、`io::Error` が `Send + Sync + 'static` で能力の型にそのまま置け、後から `ErrorKind` で述語を書く材料が残るため。probe が `ProgramMissing` を返すのは `holder_program()` が `None` だったときだけにする。
- 起動結果の型に `SignalUnreadable(Child)` を足し、`Signaled` と分ける。`spawn_holder` はここで保持プロセスを畳んでから「合図を読み取れなかった」とパニックする。
- `stdout` の取得失敗は起動の失敗と同じ扱い(`SpawnFailed`)にする。パイプを持たない子プロセスは合図を返しようがなく、原因も回避方法も起動失敗と同じ経路にある。変種名を `NotStarted` にしないのは、enum 名 `Started` で終わる名前が `clippy::enum_variant_names` に掛かり、CI の `-D warnings` で赤になるため。
- **パニック文言は観測に忠実にする。** 名前の付いた区別が増えても、フィクスチャが実際に観測していない原因を断定しない。`!locked` の経路は「保持プロセスが、誰も保持していないロックを取得した合図を返さなかった」と述べるにとどめる — `spawn_holder` は `stderr(Stdio::null())` で子の標準エラーを捨てており、`lock_holder` はロックの競合(`ロックは別の保持者がいる`)も機構の異常(`ロックを扱えない: …`)も引数の誤りもそこにしか書かないので、`locked == false` から「取得できなかった」と原因を名指しする材料は手元に無い。

`stderr` を `piped` にして `!locked` の経路でだけ読み出し、文言の根拠にする道も取らない。読み出しは EOF まで、つまり子の終了まで期限なしに待つ形になり、ADR-005 が probe と失敗経路の後始末から外したばかりの依存を、同じ経路のメッセージ生成として戻すことになる。原因の特定に要る情報の量と、期限の無い待ちを1つ増やす代償が釣り合わない。

`HolderCapability` は Issue の言う3区別より1つ多くなるが、増えた区別は「失敗として現れる側」の内訳で、許容集合の述語(`SignalTimedOut` か否か)は変わらない。

### Consequences

- 良い点: AC-4 の「原因と回避方法が分かる」が、実行ファイル不在の場合だけでなく起動失敗の場合にも成立する。`hold` に届く経路が絞られたことで、そのパニック文言は他の失敗(合図の読み取り・起動)と取り違えられなくなる。
- トレードオフ: `!locked` の文言は観測に忠実な代わりに、ロックの競合なのか機構の異常なのかを名指ししない。区別が要る場面が実際に出たときに、`stderr` を拾う形を期限付きで入れるかを改めて判断する。
- 良い点: 分岐が enum の網羅で表れるため、後から経路が増えたときにコンパイラが寄せ先の判断を要求する(`CLAUDE.md`「分岐は網羅する」)。
- トレードオフ: `allowed_skips()` の `match` の腕が増える。ワイルドカードを使えばまとめられるが、新しい能力が黙って許容側にも失敗側にも倒れうるので使わない。
- トレードオフ: `ProgramUnusable` の経路は3 OS で安定して再現する手段が無く、実地の検証を持てない(検証はコードレビューによる)。
