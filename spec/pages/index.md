# ページ設計(CLIコマンド設計)

pulsen は CLI ツールであり、画面に相当するのはコマンドとその出力である。本書はシナリオ([../scenario/index.md](../scenario/index.md))を実現するコマンドの一覧と、各コマンドの目的・機能・入出力・状態を定義する。仕様の根拠は [../requirements.md](../requirements.md)。

## 共通事項

- コマンド名は `pulsen` とする。
- グローバルホームの解決: `--home <dir>` フラグ > 環境変数 `PULSEN_HOME` > 既定 `~/.pulsen/`。すべてのコマンドが同じ規則で解決する。
- ls / show は読み取り専用であり、ロックを取得しない(タスクファイルはアトミック置換で更新されるため、ファイル単位の読み取りは常に一貫した内容になる)。
- 状態を変更するコマンド(add / tick / abort / retry / set-status)は、tickと同一の排他ロックを取得して実行する。ロック待ちはせず、取得できなければ「別の操作が実行中」と報告する。
- すべてのコマンド(内部の wrapper を除く)は起動時にグローバル設定(config.yaml)を読み込む。config.yaml のキーはすべて任意であり、内容の検証は参照時に行う: `agents` の各定義は add の登録時検証が、`notify_cmd` の未定義は「通知を行わない」として stopped 確定処理が扱う(他の動作に影響しない)。
- タスクIDの解決は `state/tasks/` → `state/archive/` の順で探索する。tasks でヒットすれば現役として扱い、archive でのみヒットすれば「アーカイブ済み」、どちらにも無ければ「タスク不在」とする。
- exit code 規約: 成功 = 0、入力・状態起因のエラー = 非0。tick のロックスキップのみ例外的に 0(cron 運用でアラートにしないため)。
- 出力は人間可読なテキストとする。機械可読形式(JSON等)は本フェーズのスコープ外。

## 縮退状態の共通規則

縮退状態(リソースの不在・破損・競合)に対する各コマンドの挙動は、次の生成規則から導出する。

1. **各コマンドは、自身の動作に必要なリソースだけを検証する。** 依存するリソースが読めなければその動作を拒否して非0で終了し、依存しないリソースの破損には影響を受けない。
2. **読めないリソースには書き込まない。** 破損したファイルの上書き・stopped 化は行わず、修復は人間の直接修復(monitoring.md の直接修復シナリオ)に委ねる。
3. **複数タスクを扱うコマンド(ls / tick)は、問題のあるタスクをスキップして報告し、処理全体を失敗させない**(requirements §9)。単一タスクを対象とするコマンドは非0で報告する。
4. **状態を変更できなかった場合、部分的な変更を残さない。** ロック競合・検証エラー時は何も変更せず終了する(再実行すればよい)。

この規則を各コマンド × 縮退状態に展開した結果を以下に示す。「—」は関与しない(そのコマンドの動作がそのリソースに依存しない)ことを表す。

| 縮退状態 | add | tick | ls | show | abort | retry | set-status |
|---|---|---|---|---|---|---|---|
| config.yaml 不在・パース不能 | 非0 ※1 | 非0 ※1 | 非0 ※1 | 非0 ※1 | 非0 ※1 | 非0 ※1 | 非0 ※1 |
| ロック競合 | 非0(登録前) ※2 | 0 スキップ | —(非取得) | —(非取得) | 非0 | 非0 | 非0 |
| state/ 配下ディレクトリ不在 | 自動作成 ※3 | 自動作成 ※3 | 0(空一覧) | 非0(タスク不在) | 非0(タスク不在) | 非0(タスク不在) | 非0(タスク不在) |
| タスク不在(未登録・ID誤り) | — | — | —(表示されない) | 非0 | 非0 | 非0 | 非0 |
| アーカイブ済み | — | —(走査対象外) | `--all` でのみ表示 | 0 表示+注記 ※4 | 非0(操作不可) | 非0(操作不可) | 非0(操作不可) |
| タスクファイル パース不能 | — | 0 スキップ+報告 | 0 報告 ※5 | 非0 | 非0(書き込まない) | 非0(書き込まない) | 非0(書き込まない) |
| スナップショット 不在・パース不能 | — | 0 スキップ+報告 | 0 検出・報告 ※5 | 0 注記付き表示 ※6 | 通常どおり ※7 | 0 受理+警告 ※7 | 非0 拒否 ※7 |
| runディレクトリ・中身の不在 | — | §6.1 の観測分類に従う ※8 | — | 0 不在を注記 | launching のみ依存 ※8b | — | — |
| worktree 不在(手動削除等) | — | 実行失敗の既存経路 ※9 | — | 0 パス表示のみ ※9 | — | — | — |

- ※1 全コマンド共通。不在なら「グローバルホームが未初期化」である旨・解決後のホームパス・作成が必要であることを、パース不能なら**構文エラー・重複キーは行・列、スキーマ違反はキーのパス(論理位置。`agents.claude.cmd` 等)**を表示して非0。状態は変更しない(壊れた設定で部分的に動作しない)。
- ※2 add のロック競合は登録前に起きるためタスクは作られない。
- ※3 `state/` 配下(tasks / runs / archive)は状態を書き込むコマンドが必要に応じて自動作成する(config.yaml と異なり、中身をツールが管理する領域のため)。
- ※4 アーカイブから読んで表示し、アーカイブ済みであること・worktree は削除済みであることを明示する。
- ※5 tickにスキップされ続けるタスクを一覧から発見できるようにするための修復の入口。ファイルパスと読めない旨を一覧に含めて報告する。tickはスナップショット破損タスクに対し、stopped かつ notified_at なしの場合の再通知(通知に必要な情報はスナップショット非依存。at-least-once(requirements §8)を破損時も維持する)だけを行い、それ以外の処理(起動・spawn確認・観測・判定・遷移・終端処理)はすべてスキップして報告する。
- ※6 タスクファイル由来の項目は表示し、スナップショット由来の項目(定義済みステータス一覧等)に読めない旨を注記する。
- ※7 スナップショットに依存するのは set-status(遷移先の検証)と tick(定義に基づく判断)のみ。abort(kill と stopped 記録)は依存しないため通常どおり動作する。retry(カウンタリセットと pending 化)も依存しないため受理するが、pending に戻しても tick に拾われないため、スナップショットの修復が必要である旨を警告する。
- ※8 running の観測で pid / exit が得られない状態は、requirements §6.1 の既存分類(プロセス死亡系)に落ちる。ページ側の追加規則はない。
- ※8b abort が runディレクトリに依存するのは launching の pidファイル参照・無効化マーカー書き込みのみ(running 以降の同定子はタスクファイルから取る)。launching でrunディレクトリ自体が不在なら、ディレクトリを作成して無効化マーカーを書き(※3 と同じくツール管理領域のため)、pidファイル再確認を経て stopped の記録のみを行う(遅延起動したラッパーの排除プロトコルを維持する)。
- ※9 進行中の worktree 消失はエージェント実行の失敗として表面化する(task-execution.md の異常系)。クリーンアップでは削除済み扱いで続行する(requirements §9.1)。show は workspace_path を表示するのみで、存在検証は行わない。

## コマンド一覧

| コマンド | 目的 | 主なシナリオ |
|---|---|---|
| `add` | タスクの登録 | タスクの登録と自動進行 |
| `tick` | 1回のtickパスの実行 | タスクの登録と自動進行 / セットアップ(定期実行) |
| `ls` | タスク一覧の表示 | 状態の確認と追跡 |
| `show` | タスク詳細の表示 | 状態の確認と追跡 |
| `abort` | タスクの停止 | 人間の介入と復旧 |
| `retry` | 凍結タスクの再試行 | 人間の介入と復旧 |
| `set-status` | タスクステータスの手動遷移 | 人間の介入と復旧 / 終端処理 |
| `wrapper`(内部) | デタッチ起動のラッパーモード | (利用者は直接使わない) |

縮退状態(config破損・ロック競合・タスク不在・ファイル破損等)の挙動は「縮退状態の共通規則」に集約した。以下の各コマンドの「状態」には、そのコマンド固有の状態のみを記載する。

## add

タスクを pending で登録する。実行はしない(次回tickを待たず開始したい場合は `add && tick` と合成する。ADR-007)。

構文: `pulsen add --workflow <name|path> --repo <path> [--base <branch>]`

- `--workflow`: ワークフロー名またはYAMLファイルパス。値がパス区切り文字を含むか `.yaml` / `.yml` で終わる場合はファイルパスとして、それ以外は名前として `workflows/<name>.yaml` を解決する(存在の有無に依存しない決定的な規則)。成功時は解決したワークフロー名と解決先を表示する。タスクに記録・表示するワークフロー名は、名前指定ならその名前、パス指定ならYAMLの `workflow:` キー(なければファイル名から拡張子を除いたもの)とする
- `--repo`: 対象リポジトリのパス
- `--base`: ベースブランチ。省略時はリポジトリの HEAD が指すブランチ。HEAD からブランチを特定できない場合(detached HEAD・コミットのない空リポジトリ)は、`--base` の明示指定を案内してエラーとする(タスクは作られない)

機能:

- ワークフロー定義の解決・パース・検証(initial の指定とその参照先の存在、各ステータスの next の参照先の存在、エージェント実行ステータスの next 必須、動作宣言が prompt / skill / run のいずれか1つであること(run の値は cleanup / wait)、参照エージェント名、skill 指定時の skill_input、テンプレートのプレースホルダと参照する値の供給(requirements §3.1))
- リポジトリパス・ベースブランチの存在検証
- 検証済み定義のスナップショット保存とタスクファイルの作成(実行状態 pending)
- タスクIDの発行と表示

状態:

- 成功: タスクIDを表示して 0 で終了
- 検証エラー(ワークフロー不在・YAML不正・エージェント未定義・skill_input 欠落・リポジトリ/ブランチ不在): 原因を表示して非0。タスクは作られない。ワークフロー名の解決失敗時は解決を試みたパス(`workflows/<name>.yaml` の絶対パス)を、参照エージェント名が未定義の場合は config.yaml に定義済みのエージェント名の一覧を添える

## tick

1回のtickパスを実行して終了する。定期実行は外部スケジューラー(cron等)がこのコマンドを呼ぶ。

構文: `pulsen tick`

機能:

- 全タスクファイルの走査と、実行状態・タスクステータスに応じた処理(起動 / launching分類 / 観測・判定 / 遷移 / クリーンアップ / 通知)
- `run_retention` 設定時: 保持期間を超えたattemptのrunディレクトリのgc(保護規則・失敗時の扱いは requirements §9.2。未設定なら行わない)
- 処理結果のサマリー表示。見出しの規約は下記

サマリーの見出しの規約:

- **ID を並べる見出しはサマリーの10フィールド(`launched` / `confirmed_running` / `judged` / `transitioned` / `skipped_back` / `frozen` / `notified` / `archived` / `gc_deleted` / `gc_errors`)と1対1で対応**し、空の見出しは出さない。規約はこの1対1対応と非表示のほうであり、日本語の文言は表示層の裁量に残す(例: 起動 / 起動確認 / 判定確定 / 遷移 / 実行待ちへ復帰 / 凍結 / 通知 / 終端処理 / gcで削除 / gcで削除できず)
- 報告(`errors`)の見出しは4つで、**文言まで規約として固定する**:
  - **失敗を記録** — カウンタを消費して帳簿に失敗を残した
  - **起動の結果が未確定** — 起動したかどうかが確定しておらず、猶予経路が分類する
  - **スキップ** — 何も記録せず、次のtickが同じ判断を再導出して再試行する
  - **後始末が残っている** — OS 側に残ったものがあり、後始末の主体は tick ではなく人間
- 見出しの軸は「タスクファイルに何を残したか」ではなく「**報告が何を残したか＝運用者が次に取る行動**」

状態:

- 成功: 実行したアクションのサマリーを表示して 0。記録すべきことが1つも起きなかった tick は「処理対象のタスクはありませんでした」を表示して 0

## ls

タスクの一覧を表示する。

構文: `pulsen ls [--status <task-status>] [--state <exec-state>] [--all]`

- `--status`: タスクステータス(ユーザー定義)で絞り込む。ワークフローごとに定義が異なるため値の検証は行わず、未知の値は「該当なし」として空の一覧になる(exit code 0)
- `--state`: 実行状態(pending / launching / running / completed / failed / stopped)で絞り込む
- `--all`: アーカイブ済み(`state/archive/`)も表示する
- 併用時の合成規則: `--status` と `--state` は AND で絞り込む。`--all` は絞り込みではなく対象集合の拡張(現役のみ → 現役+アーカイブ)であり、拡張後の集合に対して絞り込みが適用される

機能:

- タスクID・ワークフロー名・対象(リポジトリ)・ブランチ・タスクステータス・実行状態・attempt_count・更新日時の一覧表示(ブランチは成果の回収に使うため `--all` のアーカイブ済み行でも表示する)
- タスクステータスと実行状態の両方を常に表示する(同じタスクステータスでも実行状態で意味が異なるため)
- パース不能なタスクファイル、およびスナップショットが読み取り不能なタスクの検出・報告(修復の入口)

状態:

- 成功(タスクあり): 一覧を表示して 0。`--all` ではアーカイブ済みの行にその旨の印を付けて判別できるようにする
- 成功(該当なし): 空である旨を表示して 0
- `--state` に固定6値以外の値が指定された: 有効な値の一覧を添えて非0

## show

タスクの詳細を表示する。

構文: `pulsen show <task-id>`

機能:

- タスクファイルの全属性の表示: ワークフロー名、対象(リポジトリ・ベースブランチ)、現在のタスクステータス、実行状態、workspace_path、branch、attempt_count、judge_attempt_count、spawn_fail_count(各カウンタは適用される上限値を併記)、現在attemptのrunディレクトリパス・PID・kill同定子・starttime、直近の失敗要因(worktree作成・削除、アーカイブ移動、spawn失敗などツール操作の失敗メッセージ)、notified_at、更新日時。一度も実行されていないタスクでは attempt 関連の項目を「なし」と、workspace が未確定(最初の実行前)なら「未作成」と、launching で同定情報が未取り込みなら該当項目を「未取得」と表示する
- スナップショットされたワークフロー定義の定義済みステータス一覧の表示(set-status の遷移先確認に使う)と、スナップショットの保存先パスの表示(判定コマンド・timeout 等の定義内容はファイルを直接閲覧する)
- 最新attemptの実行メタデータへの参照の表示: runディレクトリの `stdout.log` / `stderr.log` / `exit` のパスと exit の値
- stopped タスクでは凍結要因(直前実行の終了情報・最終出力への参照、またはツール操作の失敗要因)の表示

状態:

- 成功: 詳細を表示して 0

## abort

タスクを停止して stopped を記録する。stopped・アーカイブ済み以外のすべての実行状態に適用できる。

構文: `pulsen abort <task-id>`

機能:

- 分岐は実行状態のラベルではなく kill 対象の有無で決まる(requirements §6.5)。kill 対象の同定情報が得られれば starttime 照合付きでプロセスグループ相当をkillして stopped を記録し、得られなければ stopped の記録のみを行う。照合不一致(PIDが別プロセスに再利用されている)・プロセス既死亡の場合は、誤殺を避けて kill せず stopped の記録のみを行う(requirements §6.2)
- 同定情報の取得元: タスクファイルに取り込み済みの同定子(running 等)、または launching ならrunディレクトリのpidファイル。launching でpidファイルがない場合は、無効化マーカーを書いてからpidファイルを再確認し、なお存在しなければ記録のみ、存在していれば照合付きkillを行う
- pending / failed / completed のように kill 対象が存在しない状態では、プロセス操作なしで stopped を記録する
- tickと同一のロックを取得して実行し、CLI操作自体が stopped を確定させる(次のtickを待たない)。凍結要因として「人間によるabort」を記録する(show の原因調査で他の経路と判別できる)
- stopped の記録後、requirements §8 と同一の手順で通知を行う(notify_cmd 実行 → notified_at 追記)。notify_cmd 実行に失敗した場合は notified_at が残らず、次のtickが再通知する(at-least-once)

状態:

- 成功: stopped を記録した旨(kill の有無を含む)を表示して 0。notify_cmd の実行に失敗した場合も stopped の記録が完了していれば 0 とし、通知に失敗した旨と次のtickが再通知することを警告として表示する
- すでに stopped: その旨を表示して 0(何も変更しない。冪等な成功として扱う)
- kill 操作の失敗(照合一致後のシグナル送出・ジョブ終了自体のエラー): 状態を変更せず、原因を表示して非0(再実行を案内する。stopped は記録しない — プロセスが生きたまま凍結扱いになることを防ぐ)

## retry

凍結(stopped)したタスクを再試行する。

構文: `pulsen retry <task-id>`

機能:

- attempt_count・judge_attempt_count・spawn_fail_count をリセットし、実行状態を pending に戻す(現在のタスクステータスから再実行。worktreeは前回の状態を引き継ぐ)

状態:

- 成功: pending に戻した旨を表示して 0
- stopped 以外への retry: 拒否して非0。failed は「放置すれば自動リトライされる」、pending は「既に実行待ち」、completed は「判定済み。次のtickが次ステータスへ遷移させる」、launching / running は「実行中。止めたい場合は先に abort」と案内する

## set-status

タスクステータスを手動で遷移させる。

構文: `pulsen set-status <task-id> <status>`

機能:

- 遷移先がスナップショットされた定義に存在することを検証する(遷移経路の制約はない)
- 受理時、遷移先の動作種別によらず一律に attempt_count・judge_attempt_count・spawn_fail_count をリセットし、実行状態を pending にする(stopped なら凍結が解ける)。次のtickの動作は遷移先の定義に従う(エージェント実行なら起動、何もしないなら滞留、クリーンアップなら終端処理)

状態:

- 成功: 遷移した旨を表示して 0
- launching / running のタスク: 拒否して非0。「先に abort せよ」と案内する
- 遷移先がスナップショット定義に存在しない: 定義済みステータスの一覧を添えて非0

## wrapper(内部コマンド)

ツール自身のバイナリをラッパーモードで再実行するための内部サブコマンド。tickのデタッチ起動でのみ使われ、利用者向けのインターフェースではない(ヘルプの一覧にも表示しない)。

機能(requirements §4.1 のラッパーの責務):

- starttime → pid の順で自身の同定情報をrunディレクトリへ書く
- 無効化マーカーを確認し、存在すればエージェントを起動せず終了する
- エージェントを起動し、stdout / stderr をログへリダイレクトし、終了後に exit ファイルを書く

状態: 利用者は直接観測しない。結果はすべてrunディレクトリのファイル(pid / starttime / exit / ログ)として現れる。

終了コードは**ラッパー自身が責務を果たせたか**を表す。エージェントを実行した場合とマーカーにより起動しなかった場合は 0(上記の「エージェントを起動せず終了する」に従う)、同定情報を何も残せずに終えた場合と起動引数が不正な場合は非0。**エージェントの終了コードは伝播しない** — エージェントの結末は run ディレクトリの `exit` ファイルだけが持つ記録であり、2箇所に分けると「exit なし = プロセス死亡として分類する」という tick 側の規則と食い違う。

## シナリオとの対応

| シナリオカテゴリ | 使用するコマンド |
|---|---|
| セットアップとワークフロー定義 | (ファイル編集) + add(検証) + tick(cron登録) |
| タスクの登録と自動進行 | add / tick |
| 状態の確認と追跡 | ls / show + タスクファイル・runディレクトリの直接閲覧 |
| 人間の介入と復旧 | abort / retry / set-status(+ 通知は notify_cmd 経由でツール外) |
| 終端処理とアーカイブ | tick(クリーンアップ実行) / set-status(手動でクリーンアップへ) / ls --all / show |

グローバル設定(config.yaml)・ワークフロー定義(workflows/*.yaml)の作成はテキストエディタで行い、専用コマンドは提供しない(検証は add の登録時検証が担う)。
