# テストケース: RunWrapper

参照元: [../../usecases/execution.md](../../usecases/execution.md)(RunWrapper)

デタッチ起動されるラッパーモード(内部コマンド)。自身の同定情報と終了結果をrunディレクトリへ永続化し、エージェントを worktree で実行する。ロックは取得せず、config も読まない。

## 正常系

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| 正しい起動引数(run_dir / workspace / agent_cmd)で起動された | ラッパーを実行する | `own_identity` で自身の pid・kill同定子・starttime を取得し、starttime → pid の順で runディレクトリへ書き込む | |
| starttime・pid の書き込みに成功し、無効化マーカーが存在しない | (続けて同一実行) | エージェントが workspace(worktree)を作業ディレクトリとして起動され、標準出力・標準エラーが `stdout.log` / `stderr.log` へリダイレクトされる | |
| エージェントが exit 0 で正常終了する | (続けて同一実行) | exit ファイルに 0 が書き込まれ、ラッパーが終了する | |
| エージェントが非0(例: 1)で終了する | (続けて同一実行) | exit ファイルにその値が書き込まれる(判定は tick 側の責務。ラッパーは符号化と永続化のみ) | |
| pid 書き込み後のマーカー確認で無効化マーカーが存在する | ラッパーを実行する | エージェントを起動せず正常終了する(遅延起動の排除。その後の分類は実行状態に依る — tick が再確認で pid を取り込み running へ進めたケースは tick 手続きD のエッジケースが定める) | |
| マーカー確認自体が失敗する(`marker_exists` が `Err(Io)`) | ラッパーを実行する | エージェントを起動せず終了する(無効化されていないことを確認できない以上、起動は安全側に倒す)。次tickが「exitなし・プロセス死亡」として failed に分類する | |
| config.yaml が不在・破損した環境 | ラッパーを実行する | 動作に影響しない(config は読まない。必要な情報はすべて起動引数で受け取る) | |
| tick が並行して動作している | ラッパーを実行する | ラッパーはロックを取得せず動作する(書き先は自attemptのrunディレクトリに閉じ、tickと競合しない) | |

## 異常系

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| 起動引数が不正(`WrapperLaunchSpec` の直列化の破れ) | ラッパーを実行する | runディレクトリに何も書かず非0で終了する(pid が現れないため、猶予時間経路が spawn失敗として分類する) | |
| `own_identity` が失敗する(Io) | ラッパーを実行する | 何も書き残さず終了する(自前のエラー報告経路を持たない。観測されないことで tick が分類する) | |
| starttime の書き込みが失敗する | ラッパーを実行する | 何も書き残さず終了する(猶予時間経路が spawn失敗として分類する) | |
| pid の書き込みが失敗する(starttime は書き込み済み) | ラッパーを実行する | 以降を書かずに終了する。starttime のみの状態は書き込み順序の正常な中間状態であり、pid 不在として猶予時間経路が spawn失敗に分類する | |
| エージェントのコマンドが存在しない(起動不能) | ラッパーを実行する | exit ファイルに 127 を書いて終了する(spawn失敗ではなく通常の実行失敗(failed)として分類させる) | |
| エージェントのコマンドが実行不能(権限なし等) | ラッパーを実行する | exit ファイルに 126 を書いて終了する | |
| エージェントがシグナルで死んだ(exit code を持たない終了) | ラッパーを実行する | exit ファイルに 128+シグナル番号 を書いて終了する(デフォルト判定では非0 = failed で足りる) | |
| ログのリダイレクト先を開けない(権限・ディスク満杯等) | ラッパーを実行する | エージェントを起動せず exit ファイルに 126 を書いて終了する(通常の実行失敗として failed 経路に合流させる) | |
| workspace(worktree)が手動削除等で存在しない状態で起動された | ラッパーを実行する | エージェント起動不能として非0(126 等)が exit ファイルに符号化され、通常の実行失敗(failed 経路)に合流する(失敗の現れ方はエージェント・コマンドテンプレートに依るため、期待は failed 経路への合流を軸とする。pages ※9) | |
| exit の書き込みが失敗する | ラッパーを実行する | exit を書けないまま終了する(次tickが「exitファイルなし・プロセス死亡」として failed に分類する) | |
| エージェントが非0で終了する / 同定情報一式を残せずに終える | ラッパー自身の終了コードを観測する | 前者は **0**(エージェントは実行できており、その終了コードは伝播しない — 非0の値は `exit` ファイルだけが持つ)、後者は **非0**(起動引数が不正な場合も同じく非0)。ラッパー自身の終了コードが表すのはラッパーが責務を果たせたかであって、エージェントの成否ではない | |

## 境界値

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| エージェントの exit code が 0 / 非0 / 126 / 127 / 128+n の各値 | ラッパーを実行する | いずれもそのままの数値が exit ファイルに符号化されて永続化される(区別・解釈はしない) | |
| テンプレートが `{workspace}` を参照しない agent_cmd | ラッパーを実行する | 参照の有無によらず、カレントディレクトリは常に worktree(workspace)でエージェントが起動される | |

## エッジケース

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| tick が pid の存在を観測した時点 | (書き込み順序を検証する) | starttime は必ず先に書かれているため、pid が存在すれば同定情報一式が揃っている(starttime → pid の順序保証。requirements §4.1) | |
| マーカー確認は pid 書き込みの後に行われる | (順序を検証する) | ラッパー側「pid 書き込み後にマーカー確認」とツール側「マーカー書き込み後に pid 再確認」の順序の組により、どちらの観測が先でも遅延起動ラッパーと新attemptの並走が排除される | |
| ラッパーが pid を書いた直後に tick / abort がマーカーを書いた(ラッパーのマーカー確認前) | ラッパーの動作を観測する | マーカー確認で存在を検出し、エージェントを起動せず終了する(二重起動防止) | |
| ラッパーのマーカー確認(不在)後にツール側がマーカーを書いた | ツール側の動作を観測する | ツール側はマーカー書き込み後の pid 再確認で pid を検出し、pending へ戻さず running に取り込む(並走しない) | |
| tick と並行して starttime / pid / exit が書き込まれている | tick 側から読み取る | 各ファイルはアトミック置換で書かれるため、読み手は常に「不在」か「完全な内容」のどちらかのみを観測する(書きかけは観測されない) | |
| エージェントが何も出力せず終了した | ラッパーを実行する | ログファイルは空(または最小限)のまま exit が書かれる。異常ではない(判定は exit による) | |
| エージェント実行中(exit 書き込み前)にラッパーごと kill された | 次の tick を観測する | exit は書かれず、tick が「exitなし・プロセス死亡」として failed に分類する(残存プロセスは try_kill_remnants のベストエフォート対象) | |
