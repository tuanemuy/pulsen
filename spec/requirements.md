# 要件定義: エージェントタスクスケジューラー

## 1. 目的

単一マシン上で動作する、AIエージェントタスクの汎用スケジューラーを開発する。実装・レビュー・打鍵などのワークフローとその対象を投げると、ツールがworktreeを準備し、定義されたステータス遷移に沿って、各ステータスに適したエージェント実行を定期的に行う。

## 2. 責務境界

**ツールの責務**

- タスクステータスと実行状態の管理(帳簿)
- タスクごとのworktreeの作成・記録と、クリーンアップ時の削除
- 定期実行: 各タスクの現在ステータスに定義されたエージェントを、指定のモデルと入力(プロンプトまたはスキル)で実行する
- エージェント実行の終了の観測、正常/異常の判定、リトライ、凍結(stopped)と通知

**ツールが感知しないこと**

- エージェントの内部処理。ツールはエージェントを起動し、終了を観測するのみで、実行中に何をするかには関与しない
- プロンプトやスキルの中身。スキルはエージェントが自律的に呼び出せるもの(エージェント側の機構で解決されるもの)とし、ツールはスキル名を入力として引き渡すのみで実体を解決しない
- 成果内容の意味的な判定(判定はプロジェクト依存の内容ではなく、実行結果に対して行う)
- タスクの重複。同一対象・同一ワークフローのタスクが複数存在することを許容し、重複排除は行わない(各タスクは独立したworktreeで実行される)
- worktreeの内容。ツールはworktree内のファイルを読み書き・リセットしない(作成と削除のみ)。中途半端な変更やkill残骸(`index.lock` 等)からの回復もエージェント実行側の責務とする

タスクステータスを変更するのは「completed による次ステータスへの遷移」と「人間による手動遷移」の2つのみとし、ツールがそれ以外の理由でタスクステータスを書き換えることはない。

対象プラットフォームは特定のOSに限定しない(Linux / macOS / Windows を想定する)。プロセス同定・デタッチ起動・ファイルロック等のOS依存の機構は、プラットフォーム抽象(§4.3)として定義し、コアのロジックから隔離する。

## 3. 概念モデル

| 概念 | 説明 |
|---|---|
| ワークフロー | YAMLで定義される、タスクステータスと、ステータスごとの動作の集合 |
| タスク | ワークフローのインスタンス。対象(リポジトリ・ベースブランチ等)と現在のタスクステータスを持つ。**1タスク = 1worktree** |
| タスクステータス | ユーザーがYAMLで自由に定義する状態 |
| 実行状態 | ツールが固定的に管理するプロセスの状態。ユーザー定義不可 |
| エージェント | ツールが実行する主体(Claude Code等)。ワークフロー単位でデフォルトを定義し、ステータス単位で上書き可能。モデルも同様 |
| プロンプト / スキル | エージェント実行時に与える入力。ステータスごとにどちらかを指定する。スキルはエージェントが自律的に呼び出せるものとする |

ステータスごとの動作は次の3種類のいずれかを定義する。

1. **エージェントを実行する**(エージェント・モデルを指定し、プロンプトまたはスキルを与える)
2. **何もしない**(滞留。人間の判断待ち等。遷移は手動操作による)
3. **クリーンアップする**(ツールがworktreeを削除し、タスクを終端へ進める)

### 3.1 エージェント定義(グローバル設定)

エージェントの実体はグローバル設定で「エージェント名 → コマンドテンプレート」のマップとして定義する。ワークフローYAMLは論理名のみを参照し、環境依存(コマンドパス・引数形式)はグローバル設定に隔離する。

- テンプレートはプレースホルダ展開で解決する: `{model}` `{prompt}` `{skill}` `{workspace}` 等
- プロンプト指定時とスキル指定時で引き渡し形式が異なる場合に備え、スキル→入力文字列の変換規則もエージェント定義側に持たせる
- コマンドは**シェルを介さず直接起動する**(OSごとのシェルの差異を持ち込まないため)。判定コマンド(§6.3)・通知コマンド(§8)も同様とする
- コマンドは文字列またはトークン配列で定義できる。文字列は単純な空白分割で解釈し、クォートによるグルーピングは解釈しない。空白を含む引数やシェルの機能が必要な場合は配列形式で明示する(POSIX環境の例: `["sh", "-c", "cd {workspace} && …"]`)。プレースホルダはトークン単位で展開する

定義イメージ:

```yaml
agents:
  claude:
    cmd: claude -p {input} --model {model}
    skill_input: "/skill {skill}"   # スキル指定時に {input} へ展開される形式
```

## 4. 実行モデル

ツールは**ステートレス**である。各エージェント実行は独立した新規セッションであり、ツールは前段の実行の出力やコンテキストを引き継がない。実行に与えるのはワークスペースと、そのステータスに定義されたプロンプトまたはスキルのみである。ステータス間で受け渡されるものは、worktree内に残された成果(コード・ファイル)がすべてとなる。

ツールは定期実行(tick)される。各tickで、状態ファイル群(タスクファイル・runディレクトリ)とプロセスの生存確認から情報を導出し、各タスクの実行状態と現在のタスクステータスに応じて定義された動作を行う。

- エージェント実行が定義されたステータスの未実行タスク → エージェントを起動する
- 何もしないステータス → 何もしない
- クリーンアップが定義されたステータス → worktreeを削除し、終端処理を行う(§9.1)
- 実行中タスク → 終了の観測と判定を行う(§6)

tickは二重起動防止(排他ロック。§4.3)により多重実行を防ぐ。並列度制御は行わず、各tickで実行可能なタスクはすべて起動する。イベント駆動(webhook等)の仕組みは持たない。外部との連携が必要な処理も、それを行うエージェント実行のステータスとしてワークフロー上に表現されるだけであり、ツールから見れば他のエージェント実行と区別されない。

### 4.1 起動方式(2フェーズ起動)

エージェントは、監視プロセスなしで終了を観測できるよう、**ラッパープロセス経由でデタッチ起動する**。ラッパーは自身の同定情報と終了コードをrunディレクトリ(§9.2)へ書き残す。

ラッパーの責務は次のとおり(実現形態は問わない。§4.3)。

1. 新しいプロセスグループ相当の実行単位(§4.3)で、ツール本体から切り離されて起動する
2. 実行開始時にまず **starttimeファイル**(OSから取得した自プロセスの起動時刻。§4.3)を書く
3. **pidファイル**(自身のPID。kill対象の同定に追加の情報が必要なプラットフォームでは、プラットフォーム実装が定義する同定子も併記する。§4.3)を書く。tickはpidファイルの存在をもって同定情報一式が揃ったとみなすため、starttime → pid の順序を守る
4. runディレクトリの**無効化マーカー**(spawn失敗の分類・abort時にツールが書く。後述・§6.5)を確認し、存在すればエージェントを起動せずに終了する。ラッパー側の「pid書き込み後にマーカー確認」とツール側の「マーカー書き込み後にpid確認」の順序の組により、どちらの観測が先でも遅延起動したラッパーとの並走が排除される
5. エージェントを起動し、標準出力・標準エラーをログファイル(§9.2)へリダイレクトする
6. エージェント終了後に **exitファイル**(終了結果)を書く。正常終了はexit codeを、シグナル等exit codeを持たない終了はシェルの慣例に合わせた非0の数値(POSIXでは 128+シグナル番号)として符号化する(判定のデフォルト(§6.3)では非0はすべてfailedであり、それ以上の区別は要しない)

これによりspawnの成否・プロセス同定・終了コードのすべてがツール側プロセスの生存に依存せず永続化される。ラッパーは**ツール自身のバイナリをラッパーモードで再実行する方式**で実現する(全対象OSで同一の仕組みになり、起動時刻の記録もツールと同一の取得手段で行える)。

起動は次の2フェーズで行い、tickのクラッシュがどの時点で起きても次のtickが安全に復旧できるようにする。

1. **launching記録**: ロック下でタスクファイルに `launching` マーカー・attempt番号・runディレクトリのパスを書き込む(アトミック置換による更新。§4.3)
2. **spawn**: ラッパーをデタッチ起動する

attempt番号はlaunching記録のたびに新しく採番する単調増加の連番とし、過去の試行(spawn失敗でpendingへ戻った試行を含む)のattempt番号は再利用しない。リトライ上限の判定に用いる attempt_count(§6.4)とは独立に管理する。

tickは `launching` のタスクを次の通り分類する。

- pidファイルあり → その内容(PID・kill同定子)とstarttimeをタスクファイルへ取り込み、`running` へ進める。以降のkill(§6.1・§6.5)はタスクファイルに取り込んだ同定子を参照する
- pidファイルなし・exitファイルなし・**猶予時間(30秒程度、固定)超過** → spawn失敗とみなす。まず当該attemptのrunディレクトリへ**無効化マーカー**を書き、その後pidファイルを**再確認**する。なお存在しなければ `pending` へ戻す(以後ラッパーが起動しても、pid書き込み後のマーカー確認で終了するため、新しいattemptと並走しない)。再確認で存在していれば、pendingへは戻さず通常どおりpidファイルの内容を取り込んで `running` へ進める(ラッパーがマーカーを見て起動せず終了していた場合は、次tickで「プロセス死亡」として failed に分類される)
- pidファイルなし・猶予時間内 → 何もしない(ラッパーの書き込み待ち)

runディレクトリはattempt番号を含むパス(§9.2)とし、前回試行の残骸との混同を構造的に排除する。二重起動の検出は「同一attemptのrunディレクトリの状態確認」に還元される。

### 4.2 終了の観測

- ツールは監視プロセスを持たず、waitも行わない。終了の観測は、tickによる「exitファイルの有無」「PIDの生存」の受動的なチェックのみで行う。
- exitファイルはexit codeの永続化を兼ねるため、tick間で失われない。

### 4.3 プラットフォーム抽象

OS依存の機構に頼る操作は以下に限定し、抽象境界の背後にプラットフォームごとの実装として隔離する。ツールのコアロジック(状態遷移・分類・判定)はOS非依存とする。

| 操作 | 責務 | 実現手段の例 |
|---|---|---|
| プロセス起動時刻の取得 | 自プロセスおよび任意PIDの起動時刻を取得する | Linux: `/proc/<pid>/stat` / macOS: `libproc` / Windows: プロセス作成時刻API |
| デタッチ起動 | ラッパーをツール本体から切り離した新しいプロセスグループ相当の単位で起動する | POSIX: `setsid` / Windows: デタッチ起動＋ジョブオブジェクト |
| プロセスグループ相当のkill | エージェントとその子プロセスの残存確認と一括終了(誤殺なく同定できる場合に限る。§6.2) | POSIX: プロセスグループへのシグナル送出 / Windows: ジョブオブジェクトの終了 |
| ファイルの排他ロック | tickの二重起動防止、およびtickとCLI操作の相互排他を実現する | POSIX: `flock` / Windows: `LockFileEx` 相当 |
| アトミックなファイル置換 | 一時ファイル書き込み後の置換をアトミックに行う | POSIX: `rename` / Windows: 同等のアトミック置換API |

- starttimeの表現・精度はOSごとに異なるため、記録と照合は必ず**同一の取得手段**で行う。値は同一マシン内での比較にのみ使い、可搬な意味を持たせない。
- kill対象の同定子はプラットフォーム実装が定義する(POSIX: プロセスグループID、Windows: タスクID・attempt番号から決定的に導出する名前付きジョブオブジェクト名 等)。pidファイル(§4.1)へ永続化する内容もこれに従い、tickはツールの再起動後でもファイルの情報だけからkillを実行できること。
- プロセスの生存確認は独立した操作とせず、「当該PIDの起動時刻の取得」に還元する。取得できなければ死亡、取得できれば記録済みstarttimeとの照合(§6.2)で同一性を判定する。
- ここに挙げた以外のOS依存操作を追加しないことを設計上の制約とする。新たに必要になった場合はこの一覧に追記して隔離する。

## 5. ワークスペース(worktree)管理

- worktreeの作成はツールの責務とする。1タスクにつき1worktreeを割り当てる。作成はworktreeの用意(git worktree add 相当)のみを指し、依存インストール等の初期化はツールの関知外とする(必要ならワークフロー上のエージェント実行で行う)。
- タスクは対象(リポジトリ、ベースブランチ等)を属性として持ち、ツールはそこからworktreeを作成する。worktreeのパスとブランチ名はタスクIDから決定的に生成する。
- 最初の実行時にワークスペース(worktreeパス、ブランチ)を確定してタスクファイルに保存し、以降のすべてのステータスで同じワークスペースを実行対象とする。これにより各実行の対象が常に特定できる。
- **worktreeの削除はクリーンアップ動作時のみ行う。** 失敗・凍結したタスクのworktreeは自動削除されず、人間が確認・対応するまで保持される。
- **リトライ時、worktreeは前回の状態をそのまま引き継ぐ。** ツールによるリセットは行わない(§2の責務境界)。timeout kill後のworktreeは不整合(`index.lock` 等)を含み得るが、その回復はエージェント実行側の責務であり、必要ならステータスのプロンプト/スキルで指示する。クリーンな再実行が必要なワークフローも同様にプロンプト側で表現する(例: 冒頭で `git reset` を指示)。

## 6. 実行状態と遷移

実行状態は以下の6つに固定する。

```
pending → launching → running → (判定) → completed(→ 次ステータスへ)
                                       → failed(→ リトライ、上限超過で stopped)
                                       → stopped(凍結)
```

| 実行状態 | 意味 | 次のtickの行動 |
|---|---|---|
| pending | 実行待ち | 起動する(§4.1) |
| launching | 起動記録済み・spawn確認未了 | pidファイルを確認し running / pending へ分類する(§4.1) |
| running | エージェント起動確認済み・分類未了 | 観測・判定する |
| completed | 正常終了と分類された | 次のタスクステータスへ遷移する |
| failed | 正常終了と分類できなかった | リトライする |
| stopped | 凍結 | 何もしない(人間の判断待ち) |

`running` は「プロセスが生存中」を意味しない。実プロセスの生死は、PIDの生存確認とexitファイルの有無から導出する。「終了済み・判定未了」は独立した状態としては持たず、「running かつ exitファイルあり」という観測可能な条件で表す。exit codeは永続化されているため、判定の失敗が起きても、次のtickが同じ条件を検出して再判定するだけで復旧できる(判定は冪等)。

### 6.1 tickにおける running タスクの分類

各tickは running のタスクを以下の通り機械的に分類する。

- exitファイルあり → 判定を実行する(§6.3)
- exitファイルなし・プロセス生存・timeout未超過 → 何もしない(実行継続)
- exitファイルなし・プロセス生存・timeout超過 → プロセスグループ相当の単位(§4.3)をkillし failed とする
- exitファイルなし・プロセス死亡 → プロセスグループ相当の単位(§4.3)に残存プロセスがあれば終了を試みたうえで、failed とする(exit code不明。OOM・マシン再起動等の一過性の死は自動リトライで回復させる)。残存プロセスの終了は、ラッパーのみが死亡した場合の孤児エージェントがリトライと同一worktreeで並走することを防ぐベストエフォートの措置であり、誤殺なく同定できる場合に限って行う(§6.2)
- エージェントの自己申告(出力のパース等)は判定に一切使用しない。

### 6.2 プロセス同定(PID再利用対策)

PIDの「生存」判定およびkillの実行前には、必ず記録済みstarttime(§4.1)と、OSから取得した当該PIDの実起動時刻(§4.3)を照合する。不一致の場合はPIDが別プロセスに再利用されたとみなし、「死亡」と判定する。killは照合一致時のみ行い、無関係なプロセスを誤殺しない。

この照合はPID単位の生存判定・killの規則である。ラッパー死亡後の残存プロセスの終了(§6.1)ではラッパーPIDの照合が使えないため、プラットフォーム実装が対象を誤殺なく同定できる場合(Windowsのジョブオブジェクト、POSIXで生存メンバーが属したままのプロセスグループ等)に限って行い、同定できない場合は行わない(孤児が残存し得ることは許容する)。

### 6.3 判定

- 判定方法はステータスごとにYAMLで定義可能。未定義の場合のデフォルトは exit code(0 = completed、非0 = failed。シグナル死等の異常終了も failed)。
- 判定コマンドを定義した場合、ツールは以下の環境変数を与えて実行する: `TASK_ID` / `WORKSPACE`(worktreeパス)/ `EXIT_CODE`(エージェントの終了結果の数値。異常終了の符号化は§4.1)/ `RUN_DIR`(当該attemptのrunディレクトリ)。引数は使用しない(拡張時の互換性のため)。
- 判定コマンドのexit codeは3値で解釈する: **0 = completed、10 = failed、それ以外 = 判定失敗**。「判定した結果failedだった」と「判定自体が壊れた」を区別し、スクリプトの内部エラー(慣習的にexit 1)を誤ってfailed分類しないための割り当てである。
- 判定失敗は `judge_attempt_count`(attempt_count とは独立のカウンタ)を加算し、次tickで再判定する。上限(デフォルト3、グローバル設定で変更可)超過で stopped とする(判定不能は環境・定義の不具合であり、エージェントの再実行では解決しないため、リトライせず凍結する)。
- 判定コマンド自体にも短い固定timeout(グローバル設定、デフォルト60秒程度)を設け、超過は判定失敗として扱う。

### 6.4 分類後の処理

- `completed` → YAMLで定義された次のタスクステータスへ遷移する。
- `failed` → attempt_count を加算し、次のtickで再実行する。上限超過で stopped とする。
- `stopped` → タスクステータスは変更せず、そのまま凍結する。以降のtickは当該タスクに対して何も行わない。確定時に通知する(§8)。再開は人間の操作(retry / set-status)による。

stopped に至る経路は「リトライ上限超過」「判定不能」「人間によるabort」の3つのみである。

### 6.5 abort

`abort <task-id>` は、実行中のプロセスグループ相当の単位(§4.3)をkill(§6.2の照合付き)し、即座に stopped を記録する。次のtickを待たずCLI操作自体が確定させる(tickとの競合を避けるため、tickと同一のロックを取得して行う)。

- `launching` のタスクに対しては、pidファイルがあれば通常通りkillする。なければ当該attemptのrunディレクトリへ無効化マーカー(§4.1)を書いたうえでpidファイルを再確認し、なお存在しなければタスクファイルを直接 stopped に書き換える(遅延起動したラッパーはpid書き込み後のマーカー確認で終了する)。再確認で存在していれば通常通り照合付きkillを行って stopped とする。

## 7. ワークフロー定義(YAML)

- `initial:` で初期ステータスを必須指定する(キーの記述順には依存しない)。
- ステータスごとに以下を定義できる。
    - 動作(エージェント実行 / 何もしない / クリーンアップ)
    - エージェント実行の場合: プロンプトまたはスキルの指定、エージェント / モデルの上書き、timeout、リトライ上限
    - completed時の次ステータス
    - 判定コマンド(任意。省略時はexit code)

定義イメージ:

```yaml
workflow: implement
agent: claude
model: claude-opus-4-8
initial: queued
statuses:
  queued:
    skill: plan
    next: planned
  planned:
    skill: implement
    model: claude-sonnet-4-6
    timeout: 30m
    next: implemented
  implemented:
    prompt: "変更内容をセルフレビューし、指摘事項があれば修正する"
    next: done
  done:
    run: cleanup
```

### 7.1 定義のスナップショット

タスク登録時にワークフロー定義をタスク側(タスクファイルまたはrunディレクトリ配下)へ**スナップショット**し、以降そのタスクはスナップショットのみを参照する。元YAMLの編集は既存タスクに影響しない(実行途中で定義が変わるとtickの決定性が壊れるため)。定義更新を既存タスクへ適用する操作は提供しない。スナップショットにより「このタスクは何の定義で動いたか」が事後に確定する。

### 7.2 デフォルト値

- timeout: グローバルデフォルト **1h**。ステータス単位で上書き可。`timeout: none` で明示的に無制限化できる(エージェントのハングを事故なく検出するため、無指定を無制限とは扱わない)。
- リトライ上限: デフォルト **2**。ステータス単位で上書き可。
- 判定失敗の再判定上限・判定timeout: §6.3のとおりグローバル設定。

## 8. 人間介入と通知

- ツールによるエスカレーションは stopped(凍結)に一本化する。stopped 確定時に、グローバル設定の通知コマンド(`notify_cmd`)を実行する。通知手段の中身はツールは感知しない。
- 通知は **at-least-once** とする。処理順序は「stoppedをタスクファイルへ書く → notify_cmd 実行 → `notified_at` を追記」。`notified_at` のない stopped タスクを次tickが検出して(再)通知する。クラッシュ時の二重通知は許容し、通知の欠落を許さない。notify_cmd 自体の失敗もこの仕組みで自動再試行される。
- 凍結に至った要因(直前実行の終了情報・最終出力への参照)はタスクファイルに記録し、参照可能にする。
- 人間はCLIで再試行(retry)または手動ステータス遷移(set-status)を行って再開する。
- 人間の判断を待つステータス(レビュー待ち等)が必要な場合は、「何もしない」動作のステータスとしてワークフロー設計者が任意に定義する。これはワークフロー設計の話であり、ツールの機構ではない。

## 9. 状態管理(ファイル)

- 状態はすべてファイルで管理し、データベースは使用しない。これは要件ではなく現時点での方針であり、本節はこの方針の下での仕様を記述する。
- 1タスク = 1ファイル(例: `state/tasks/<task-id>.json`)。主な属性: ワークフロー名、対象(リポジトリ・ベースブランチ等)、現在のタスクステータス、実行状態、workspace_path、branch、attempt_count、judge_attempt_count、現在attemptのrunディレクトリパス・PID・kill同定子・starttime、notified_at、更新日時。
- 更新は「一時ファイルへ書き込み後にアトミック置換(§4.3)」で行い、アトミック性を保証する。書きかけ状態のファイルが観測されてはならない。
- 書き込みは、tickおよびCLI操作が同一の排他ロック(§4.3)を取得して行う。
- tickはタスクディレクトリを走査して全タスクを読み込む。想定規模(単一マシン・数十〜数百タスク)ではフルスキャンで十分とする。
- タスクファイルは人間可読とし、直接の閲覧・修復を可能にする。

### 9.1 終端処理(クリーンアップ)

クリーンアップ動作のステータスに到達したタスクについて、tickは次を行う。

- worktreeを削除する(git worktree remove 相当)
- **ブランチは削除しない**(成果物そのものであり、ツールの責務外)
- タスクファイルを `state/tasks/` から `state/archive/` へ移動する(削除しない)。これによりtickの走査対象から外れる
- runディレクトリは削除しない(保持ポリシーは§9.2)

### 9.2 runディレクトリ

実行の成果メタデータは worktree と完全に分離し、`state/runs/<task-id>/attempt-<n>/` に集約する。

- 内容: `pid` / `starttime` / `exit` / `stdout.log` / `stderr.log`(ラッパーが標準出力・標準エラーをリダイレクトする)。加えて、遅延起動の抑止に用いる無効化マーカー(§4.1)が置かれ得る
- `pid` / `starttime` / `exit` の書き込みは、タスクファイルと同様にアトミック置換(§4.3)で行い、書きかけの内容が観測されないようにする
- attempt番号をパスに含めることで、前回試行との混同を構造的に防ぐ
- クリーンアップでは削除しない(凍結・過去タスクの調査材料を保護するため)。肥大化への対応は、明示的なgc操作または保持期間のグローバル設定として別途提供する

## 10. CLI

最小セット:

- `run` — タスクの登録 / 実行
- `abort <task-id>` — 実行中タスクの中断(→ stopped。§6.5)
- `retry <task-id>` — 再試行(attempt_count・judge_attempt_count をリセットし pending に戻す)
- `set-status <task-id> <status>` — 手動ステータス遷移。**launching / running のタスクには拒否し、「先にabortせよ」と案内する**(kill+遷移の複合動作は提供しない。全ケースは abort → set-status → retry の組み合わせで表現する)
- `ls` — タスク一覧(ステータスでのフィルタ含む。`--all` でアーカイブ済みも表示)
- `show <task-id>` — タスク詳細(最終出力への参照・実行メタデータ含む)

すべてのCLI操作は、tickと同一のロックを取得した上で状態を変更する。
