# 要件定義: エージェントタスクスケジューラー

## 1. 目的

単一マシン上で動作する、AIエージェントタスクの汎用スケジューラーを開発する。実装・レビュー・打鍵などのワークフローとその対象を投げると、ツールがworktreeを準備し、定義されたステータス遷移に沿って、各ステータスに適したエージェント実行を定期的に行う。

## 2. 責務境界

**ツールの責務**

- タスクステータスと実行状態の管理(帳簿)
- タスクごとのworktreeの作成・記録と、クリーンアップ時の削除
- 定期実行: 各タスクの現在ステータスに定義されたエージェントを、指定のモデルと入力(プロンプトまたはスキル)で実行する
- エージェント実行の終了の観測、正常/異常の判定、リトライ、凍結(stopped)と通知

**ツールが感知しないこと**

- エージェントの内部処理。ツールはエージェントを起動し、終了を観測するのみで、実行中に何をするかには関与しない
- プロンプトやスキルの中身。スキルはエージェントが自律的に呼び出せるもの(エージェント側の機構で解決されるもの)とし、ツールはスキル名を入力として引き渡すのみで実体を解決しない
- 成果内容の意味的な判定(判定はプロジェクト依存の内容ではなく、実行結果に対して行う)
- タスクの重複。同一対象・同一ワークフローのタスクが複数存在することを許容し、重複排除は行わない(各タスクは独立したworktreeで実行される)
- worktreeの内容。ツールはworktree内のファイルを読み書き・リセットしない(作成と削除のみ)。中途半端な変更やkill残骸(`index.lock` 等)からの回復もエージェント実行側の責務とする

タスクステータスを変更するのは「completed による次ステータスへの遷移」と「人間による手動遷移」の2つのみとし、ツールがそれ以外の理由でタスクステータスを書き換えることはない。

対象プラットフォームは特定のOSに限定しない(Linux / macOS / Windows を想定する)。プロセス同定・デタッチ起動・ファイルロック等のOS依存の機構は、プラットフォーム抽象(§4.3)として定義し、コアのロジックから隔離する。

## 3. 概念モデル

| 概念 | 説明 |
|---|---|
| ワークフロー | YAMLで定義される、タスクステータスと、ステータスごとの動作の集合 |
| タスク | ワークフローのインスタンス。対象(リポジトリ・ベースブランチ等)と現在のタスクステータスを持つ。**1タスク = 1worktree** |
| タスクステータス | ユーザーがYAMLで自由に定義する状態 |
| 実行状態 | ツールが固定的に管理するプロセスの状態。ユーザー定義不可 |
| エージェント | ツールが実行する主体(Claude Code等)。ワークフロー単位でデフォルトを定義し、ステータス単位で上書き可能。モデルも同様 |
| プロンプト / スキル | エージェント実行時に与える入力。ステータスごとにどちらかを指定する。スキルはエージェントが自律的に呼び出せるものとする |

ステータスごとの動作は次の3種類のいずれかを定義する。

1. **エージェントを実行する**(エージェント・モデルを指定し、プロンプトまたはスキルを与える)
2. **何もしない**(滞留。人間の判断待ち等。遷移は手動操作による)
3. **クリーンアップする**(ツールがworktreeを削除し、タスクを終端へ進める)

### 3.1 エージェント定義(グローバル設定)

エージェントの実体はグローバル設定で「エージェント名 → コマンドテンプレート」のマップとして定義する。ワークフローYAMLは論理名のみを参照し、環境依存(コマンドパス・引数形式)はグローバル設定に隔離する。

登録するコマンドはAIエージェントに限らない。ツールはテンプレートを展開して起動し、終了を観測するだけで、実体が何であるかを検証しない。シェルスクリプト等の任意のコマンド(ポーリングのチェックスクリプト等)も同じ仕組みで登録してよい。

- テンプレートはプレースホルダ展開で解決する。`cmd` で使えるのは `{input}`(ステータスのプロンプト、またはskill_inputで変換されたスキル入力)・`{model}`・`{workspace}`(worktreeパス)の3つ、`skill_input` の中で使えるのは `{skill}`(スキル名)である。この集合に含まれない名前は未知プレースホルダとして登録時検証(§10)で弾く
- プロンプト指定時とスキル指定時で引き渡し形式が異なる場合に備え、スキル→入力文字列の変換規則もエージェント定義側に持たせる
- コマンドは**シェルを介さず直接起動する**(OSごとのシェルの差異を持ち込まないため)。判定コマンド(§6.3)・通知コマンド(§8)も同様とし、定義形式(文字列/トークン配列。下記)も共通とする
- テンプレートが参照するプレースホルダに与える値が解決できない場合(例: `{model}` を使うテンプレートに対し、ワークフロー/ステータスの `model` 指定がない)は登録時検証(§10)で弾く。逆に、値があるのにテンプレートが参照しない場合は許容する(その値は単に渡らない)。`model` は必須のキーではなく、テンプレートが `{model}` を参照する場合にのみ要求される
- コマンドは文字列またはトークン配列で定義できる。文字列は単純な空白分割で解釈し、クォートによるグルーピングは解釈しない。空白を含む引数やシェルの機能が必要な場合は配列形式で明示する(POSIX環境の例: `["sh", "-c", "{input}"]`。作業ディレクトリは常にworktreeで起動される(§4.1)ため `cd` は不要)。プレースホルダはトークン単位で展開する

定義イメージ:

```yaml
agents:
  claude:
    cmd: claude -p {input} --model {model}
    skill_input: "/skill {skill}"   # スキル指定時に {input} へ展開される形式
```

## 4. 実行モデル

ツールは**ステートレス**である。各エージェント実行は独立した新規セッションであり、ツールは前段の実行の出力やコンテキストを引き継がない。実行に与えるのはワークスペースと、そのステータスに定義されたプロンプトまたはスキルのみである。ステータス間で受け渡されるものは、worktree内に残された成果(コード・ファイル)がすべてとなる。

ツールは定期実行(tick)される。tickは `tick` サブコマンド(§10)として提供し、1回の呼び出しで1回のtickパスを実行して終了する。定期性はcron・launchd・タスクスケジューラ等の外部スケジューラーが担い、ツール自身は常駐しない。各tickで、状態ファイル群(タスクファイル・runディレクトリ)とプロセスの生存確認から情報を導出し、各タスクの実行状態と現在のタスクステータスに応じて定義された動作を行う。

- エージェント実行が定義されたステータスの未実行タスク → エージェントを起動する
- 何もしないステータス → 何もしない
- クリーンアップが定義されたステータス → worktreeを削除し、終端処理を行う(§9.1)
- 実行中タスク → 終了の観測と判定を行う(§6)

tickは二重起動防止(排他ロック。§4.3)により多重実行を防ぐ。並列度制御は行わず、各tickで実行可能なタスクはすべて起動する。イベント駆動(webhook等)の仕組みは持たない。外部との連携が必要な処理も、それを行うエージェント実行のステータスとしてワークフロー上に表現されるだけであり、ツールから見れば他のエージェント実行と区別されない。

### 4.1 起動方式(2フェーズ起動)

エージェントは、監視プロセスなしで終了を観測できるよう、**ラッパープロセス経由でデタッチ起動する**。ラッパーは自身の同定情報と終了コードをrunディレクトリ(§9.2)へ書き残す。

ラッパーの責務は次のとおり(実現形態は問わない。§4.3)。

1. 新しいプロセスグループ相当の実行単位(§4.3)で、ツール本体から切り離されて起動する
2. 実行開始時にまず **starttimeファイル**(OSから取得した自プロセスの起動時刻。§4.3)を書く
3. **pidファイル**(自身のPID。kill対象の同定に追加の情報が必要なプラットフォームでは、プラットフォーム実装が定義する同定子も併記する。§4.3)を書く。tickはpidファイルの存在をもって同定情報一式が揃ったとみなすため、starttime → pid の順序を守る
4. runディレクトリの**無効化マーカー**(spawn失敗の分類・abort時にツールが書く。後述・§6.5)を確認し、存在すればエージェントを起動せずに終了する。ラッパー側の「pid書き込み後にマーカー確認」とツール側の「マーカー書き込み後にpid確認」の順序の組により、どちらの観測が先でも遅延起動したラッパーとの並走が排除される
5. エージェントを、タスクのworktree(workspace_path)を作業ディレクトリとして起動し、標準出力・標準エラーをログファイル(§9.2)へリダイレクトする。テンプレートが `{workspace}` を参照するかどうかによらず、カレントディレクトリは常にworktreeである。エージェントの起動自体に失敗した場合(コマンド不在・実行権限なし等)は、シェルの慣例に合わせた非0の値(コマンド不在は127、実行不能は126)をexitファイルに書いて終了する(spawn失敗ではなく、通常の実行失敗(failed)として分類させるため)
6. エージェント終了後に **exitファイル**(終了結果)を書く。正常終了はexit codeを、シグナル等exit codeを持たない終了はシェルの慣例に合わせた非0の数値(POSIXでは 128+シグナル番号)として符号化する(判定のデフォルト(§6.3)では非0はすべてfailedであり、それ以上の区別は要しない)

これによりspawnの成否・プロセス同定・終了コードのすべてがツール側プロセスの生存に依存せず永続化される。ラッパーは**ツール自身のバイナリをラッパーモードで再実行する方式**で実現する(全対象OSで同一の仕組みになり、起動時刻の記録もツールと同一の取得手段で行える)。

起動は次の2フェーズで行い、tickのクラッシュがどの時点で起きても次のtickが安全に復旧できるようにする。

1. **launching記録**: ロック下でタスクファイルに `launching` マーカー・attempt番号・runディレクトリのパスを書き込む(アトミック置換による更新。§4.3)
2. **spawn**: ラッパーをデタッチ起動する

attempt番号はlaunching記録のたびに新しく採番する単調増加の連番とし、過去の試行(spawn失敗でpendingへ戻った試行を含む)のattempt番号は再利用しない。リトライ上限の判定に用いる attempt_count(§6.4)とは独立に管理する。

tickは `launching` のタスクを次の通り分類する。

- pidファイルあり → その内容(PID・kill同定子)とstarttimeをタスクファイルへ取り込み、`running` へ進める(連続spawn失敗カウンタはリセットする)。以降のkill(§6.1・§6.5)はタスクファイルに取り込んだ同定子を参照する
- pidファイルなし・**猶予時間(30秒程度、固定)超過** → spawn失敗とみなす(ラッパーはexitをpidより後に書くため、この分類はexitファイルの有無を参照しない)。まず当該attemptのrunディレクトリへ**無効化マーカー**を書き、その後pidファイルを**再確認**する。なお存在しなければ `pending` へ戻す(以後ラッパーが起動しても、pid書き込み後のマーカー確認で終了するため、新しいattemptと並走しない)。pendingへ戻す際は、attempt_count とは独立の**連続spawn失敗カウンタ**(spawn_fail_count)を加算し、上限(グローバル設定、デフォルト3)超過で pending へ戻さず stopped とする(spawn失敗の継続は環境・設定の不具合であり、再試行では解決しないため)。再確認で存在していれば、pendingへは戻さず通常どおりpidファイルの内容を取り込んで `running` へ進める(ラッパーがマーカーを見て起動せず終了していた場合は、次tickで「プロセス死亡」として failed に分類される)
- pidファイルなし・猶予時間内 → 何もしない(ラッパーの書き込み待ち)

runディレクトリはattempt番号を含むパス(§9.2)とし、前回試行の残骸との混同を構造的に排除する。二重起動の検出は「同一attemptのrunディレクトリの状態確認」に還元される。

### 4.2 終了の観測

- ツールは監視プロセスを持たず、waitも行わない。終了の観測は、tickによる「exitファイルの有無」「PIDの生存」の受動的なチェックのみで行う。
- exitファイルはexit codeの永続化を兼ねるため、tick間で失われない。

### 4.3 プラットフォーム抽象

OS依存の機構に頼る操作は以下に限定し、抽象境界の背後にプラットフォームごとの実装として隔離する。ツールのコアロジック(状態遷移・分類・判定)はOS非依存とする。

| 操作 | 責務 | 実現手段の例 |
|---|---|---|
| プロセス起動時刻の取得 | 自プロセスおよび任意PIDの起動時刻を取得する | Linux: `/proc/<pid>/stat` / macOS: `libproc` / Windows: プロセス作成時刻API |
| デタッチ起動 | ラッパーをツール本体から切り離した新しいプロセスグループ相当の単位で起動する | POSIX: `setsid` / Windows: デタッチ起動＋ジョブオブジェクト |
| プロセスグループ相当のkill | エージェントとその子プロセスの残存確認と一括終了(誤殺なく同定できる場合に限る。§6.2) | POSIX: プロセスグループへのシグナル送出 / Windows: ジョブオブジェクトの終了 |
| ファイルの排他ロック | tickの二重起動防止、およびtickとCLI操作の相互排他を実現する | POSIX: `flock` / Windows: `LockFileEx` 相当 |
| アトミックなファイル置換 | 一時ファイル書き込み後の置換をアトミックに行う | POSIX: `rename` / Windows: 同等のアトミック置換API |

- starttimeの表現・精度はOSごとに異なるため、記録と照合は必ず**同一の取得手段**で行う。値は同一マシン内での比較にのみ使い、可搬な意味を持たせない。
- kill対象の同定子はプラットフォーム実装が定義する(POSIX: プロセスグループID、Windows: タスクID・attempt番号から決定的に導出する名前付きジョブオブジェクト名 等)。pidファイル(§4.1)へ永続化する内容もこれに従い、tickはツールの再起動後でもファイルの情報だけからkillを実行できること。
- プロセスの生存確認は独立した操作とせず、「当該PIDの起動時刻の取得」に還元する。取得できなければ死亡、取得できれば記録済みstarttimeとの照合(§6.2)で同一性を判定する。
- ここに挙げた以外のOS依存操作を追加しないことを設計上の制約とする。新たに必要になった場合はこの一覧に追記して隔離する。

## 5. ワークスペース(worktree)管理

- worktreeの作成はツールの責務とする。1タスクにつき1worktreeを割り当てる。作成はworktreeの用意(git worktree add 相当)のみを指し、依存インストール等の初期化はツールの関知外とする(必要ならワークフロー上のエージェント実行で行う)。
- タスクは対象(リポジトリ、ベースブランチ等)を属性として持ち、ツールはそこからworktreeを作成する。worktreeのパスとブランチ名はタスクIDから決定的に生成する(パスはグローバルホーム配下の `worktrees/<task-id>`、ブランチ名は `pulsen/<task-id>`)。
- 最初の実行時にワークスペース(worktreeパス、ブランチ)を確定してタスクファイルに保存し、以降のすべてのステータスで同じワークスペースを実行対象とする。これにより各実行の対象が常に特定できる。
- worktreeの作成に失敗した場合は failed 相当として attempt_count を消費し、次のtickで再試行する。リトライ上限超過で stopped とする(§6.4)。
- **worktreeの削除はクリーンアップ動作時のみ行う。** 失敗・凍結したタスクのworktreeは自動削除されず、人間が確認・対応するまで保持される。
- **リトライ時、worktreeは前回の状態をそのまま引き継ぐ。** ツールによるリセットは行わない(§2の責務境界)。timeout kill後のworktreeは不整合(`index.lock` 等)を含み得るが、その回復はエージェント実行側の責務であり、必要ならステータスのプロンプト/スキルで指示する。クリーンな再実行が必要なワークフローも同様にプロンプト側で表現する(例: 冒頭で `git reset` を指示)。

## 6. 実行状態と遷移

実行状態は以下の6つに固定する。

```
pending → launching → running → (判定) → completed(→ 次ステータスへ)
                                       → skipped(→ pending に戻る。現状維持)
                                       → failed(→ リトライ、連続の上限超過で stopped(凍結))
```

図中の skipped は実行状態ではなく判定の分類結果である(判定の分類は completed / failed / skipped の3値。§6.3)。skipped の確定と同時に実行状態は pending に書き戻されるため(§6.4)、実行状態は以下の6つのまま変わらない。stopped は判定の分類結果ではなく、各種上限超過または人間の abort(§6.4・§6.5)によってのみ至る実行状態である。

| 実行状態 | 意味 | 次のtickの行動 |
|---|---|---|
| pending | 実行待ち | 起動する(§4.1。動作は現在のタスクステータスの定義に従う。§4) |
| launching | 起動記録済み・spawn確認未了 | pidファイルを確認し running / pending へ分類する(連続spawn失敗の上限超過は stopped。§4.1) |
| running | エージェント起動確認済み・分類未了 | 観測・判定する |
| completed | 正常終了と分類された | 次のタスクステータスへ遷移する |
| failed | 正常終了と分類できなかった | リトライする |
| stopped | 凍結 | 実行の起動・遷移は行わない(未通知なら再通知する。§8。人間の判断待ち) |

`running` は「プロセスが生存中」を意味しない。実プロセスの生死は、PIDの生存確認とexitファイルの有無から導出する。「終了済み・判定未了」は独立した状態としては持たず、「running かつ exitファイルあり」という観測可能な条件で表す。exit codeは永続化されているため、判定の失敗が起きても、次のtickが同じ条件を検出して再判定するだけで復旧できる(判定は冪等)。

### 6.1 tickにおける running タスクの分類

各tickは running のタスクを以下の通り機械的に分類する。

- exitファイルあり → 判定を実行する(§6.3)
- exitファイルなし・プロセス生存・timeout未超過 → 何もしない(実行継続)
- exitファイルなし・プロセス生存・timeout超過 → プロセスグループ相当の単位(§4.3)をkillし failed とする
- timeoutの経過は、記録済みstarttime(§4.1)を起点として判定する(launching記録からpid出現までの猶予時間はtimeoutに含まれない)
- exitファイルなし・プロセス死亡 → プロセスグループ相当の単位(§4.3)に残存プロセスがあれば終了を試みたうえで、failed とする(exit code不明。OOM・マシン再起動等の一過性の死は自動リトライで回復させる)。残存プロセスの終了は、ラッパーのみが死亡した場合の孤児エージェントがリトライと同一worktreeで並走することを防ぐベストエフォートの措置であり、誤殺なく同定できる場合に限って行う(§6.2)
- エージェントの自己申告(出力のパース等)は判定に一切使用しない。

### 6.2 プロセス同定(PID再利用対策)

PIDの「生存」判定およびkillの実行前には、必ず記録済みstarttime(§4.1)と、OSから取得した当該PIDの実起動時刻(§4.3)を照合する。不一致の場合はPIDが別プロセスに再利用されたとみなし、「死亡」と判定する。killは照合一致時のみ行い、無関係なプロセスを誤殺しない。

この照合はPID単位の生存判定・killの規則である。ラッパー死亡後の残存プロセスの終了(§6.1)ではラッパーPIDの照合が使えないため、プラットフォーム実装が対象を誤殺なく同定できる場合(Windowsのジョブオブジェクト、POSIXで生存メンバーが属したままのプロセスグループ等)に限って行い、同定できない場合は行わない(孤児が残存し得ることは許容する)。

### 6.3 判定

- 判定方法はステータスごとにYAMLで定義可能(ステータスの `judge` キーに判定コマンドを指定する)。未定義の場合のデフォルトは exit code(0 = completed、非0 = failed。シグナル死等の異常終了も failed)。
- 判定コマンドを定義した場合、ツールは以下の環境変数を与えて実行する: `TASK_ID` / `WORKSPACE`(worktreeパス)/ `EXIT_CODE`(エージェントの終了結果の数値。異常終了の符号化は§4.1)/ `RUN_DIR`(当該attemptのrunディレクトリ)。引数は使用しない(拡張時の互換性のため)。
- 判定コマンドのexit codeは4値で解釈する: **0 = completed、10 = failed、20 = skipped、それ以外 = 判定失敗**。「判定した結果failedだった」と「判定自体が壊れた」を区別し、スクリプトの内部エラー(慣習的にexit 1)を誤ってfailed分類しないための割り当てである。skipped は「実行したが、やることがなかった(現状維持)」を表し、ポーリング型のステータス(チェック → 対象があれば次へ、なければ待機)に使う(§6.4)。
- skipped を表現できるのは判定コマンドのみである。デフォルト判定(エージェントの exit code)は 0 / 非0 の2値のままとし、エージェントの exit code に skipped 用のコードをグローバルに予約しない(エージェントが偶然そのコードで異常終了すると、attempt_count を消費しないまま永遠に再実行され続け、stopped への到達(§8)が失われるため。判定コマンドは利用者が意図的に書くため偶発衝突が起きない。ADR-008)。skipped を使うステータスには判定コマンドを定義し、エージェントの exit code を判定プロトコルへ写像する。
- 判定コマンドの作業ディレクトリは規定しない。必要な情報はすべて環境変数で渡されるため、cwdに依存しないように書く(notify_cmd(§8)も同様)。トークンへのプレースホルダ展開(§3.1)は行わない(展開はエージェント定義のコマンドテンプレートの機構であり、判定・通知コマンドのトークンは定義どおりに渡る。実行時情報はすべて環境変数で渡すため展開は不要)。
- 判定失敗は `judge_attempt_count`(attempt_count とは独立のカウンタ)を加算し、次tickで再判定する。上限(デフォルト3、グローバル設定で変更可)超過で stopped とする(判定不能は環境・定義の不具合であり、エージェントの再実行では解決しないため、リトライせず凍結する)。
- 判定コマンド自体にも短い固定timeout(グローバル設定、デフォルト60秒程度)を設け、超過は判定失敗として扱う。

### 6.4 分類後の処理

- `completed` → attempt_count・judge_attempt_count をリセットし、YAMLで定義された次のタスクステータスへ遷移して実行状態を pending に戻す。次のtickの動作は遷移先ステータスの定義(§4)に従う。
- `skipped` → タスクステータスを変更せず、attempt_count・judge_attempt_count をリセットし、実行状態を pending に書き戻す。次のtickが同じタスクステータスの実行を新しいattemptで起動する(再実行の周期はtick間隔に律速される)。通知は行わない。確定後は実行状態が pending となるため、同じexitファイルが再判定されることはない(次の実行は新しいattemptのrunディレクトリに分離される)。
- `failed` → attempt_count を加算し(判定自体は成立しているため judge_attempt_count はリセットする)、次のtickで再実行する。上限超過で stopped とする。
- `stopped` → タスクステータスは変更せず、そのまま凍結する。以降のtickは当該タスクに対して実行の起動・遷移を行わない(未通知の場合の再通知(§8)のみ行う)。確定時に通知する(§8)。再開は人間の操作(retry / set-status)による。

リトライ上限・再判定上限は**連続した失敗の上限**である(completed / skipped の確定でカウンタがリセットされる。ADR-009)。循環ワークフロー(§7)やポーリングのような長期稼働タスクで、無関係な一過性失敗が蓄積して凍結することはない。恒久的な失敗は連続するため、エスカレーション(ADR-001)は引き続き機能する。

attempt_count は、エージェント実行の失敗とツール操作の失敗(worktree作成・削除、アーカイブ移動。§5・§9.1)を区別せず数える(恒久失敗の合流。ADR-001)。リセットが起きるのは completed / skipped の判定確定と人間の操作(retry / set-status)のみであり、途中のツール操作の成功(worktree作成の成功等)ではリセットしない。

stopped に至る経路は「リトライ上限超過」「判定不能(再判定上限超過)」「連続spawn失敗の上限超過」「人間によるabort」の4つのみである。

### 6.5 abort

`abort <task-id>` は、stopped・アーカイブ済み以外のすべての実行状態(pending / launching / running / failed / completed)に適用できる。プロセスグループ相当の単位(§4.3)が存在すればkill(§6.2の照合付き)し、存在しなければ(pending / failed / completed 等)プロセス操作なしで、いずれの場合も即座に stopped を記録する。ただしkill操作自体が失敗した場合(照合一致後のシグナル送出・ジョブ終了のエラー)は、状態を変更せず(stoppedを記録せず)エラーとする(プロセスが生きたまま凍結扱いになることを防ぐ。abort の再実行で解決する)。実行状態ごとの例外は設けず、kill対象の有無だけを分岐とする。次のtickを待たずCLI操作自体が確定させる(tickとの競合を避けるため、tickと同一のロックを取得して行う)。

- `launching` のタスクに対しては、pidファイルがあれば通常通りkillする。なければ当該attemptのrunディレクトリへ無効化マーカー(§4.1)を書いたうえでpidファイルを再確認し、なお存在しなければタスクファイルを直接 stopped に書き換える(遅延起動したラッパーはpid書き込み後のマーカー確認で終了する)。再確認で存在していれば通常通り照合付きkillを行って stopped とする。

## 7. ワークフロー定義(YAML)

ワークフローYAMLはグローバルホーム(§9)の `workflows/` ディレクトリに置き、タスク登録時(`add`)にワークフロー名で解決する(`implement` → `workflows/implement.yaml`)。開発・検証用に、名前の代わりにファイルパスを直接指定することもできる。いずれの場合も登録時にスナップショット(§7.1)されるため、以降の解決は発生しない。

- `workflow:` はワークフロー名を表す任意のキーである。名前解決には使われず、ファイルパス指定で登録した場合の表示名に使われる(なければファイル名から拡張子を除いたものが使われる。§10)。
- `initial:` で初期ステータスを必須指定する(キーの記述順には依存しない)。
- 各ステータスは動作を `prompt`(プロンプトでエージェント実行)/ `skill`(スキルでエージェント実行)/ `run`(ツールの組み込み動作)の**いずれか1つ**で宣言する。`run` の値は `cleanup`(クリーンアップ)または `wait`(何もしない)。動作の宣言が無い・複数ある・`run` の値が未知の場合は、読み込み時(登録時のパース)エラーとする。

    ```yaml
    review_waiting:
      run: wait   # 何もしない(人間の set-status 待ち)
    ```

- ステータスごとに以下を定義できる。
    - 動作(エージェント実行 / 何もしない / クリーンアップ。宣言方法は上記)
    - エージェント実行の場合: プロンプトまたはスキルの指定、エージェント / モデルの上書き、timeout、リトライ上限
    - completed時の次ステータス(`next`)。エージェント実行のステータスでは必須とし、欠落は読み込み時(登録時のパース)エラーとする(滞留は「何もしない」ステータスで表現する)
    - 判定コマンド(`judge`。任意。省略時はexit code。§6.3)
- `next` の検証は参照先ステータスの存在のみを確認し、**循環(自己参照を含む)は正当な表現として許容する**(検証でエラーにしない。ADR-010)。「人間が介入するまで続ける」ワークフロー(ポーリング監視等)は循環で表現する。終端(クリーンアップ動作のステータス)の存在は必須ではなく、循環の出口は人間の abort / set-status、または失敗経路の stopped である。遷移経路のない到達不能ステータス(set-status の遷移先として置くクリーンアップステータス等)も従来どおり許容する。

定義イメージ:

```yaml
workflow: implement
agent: claude
model: claude-opus-4-8
initial: queued
statuses:
  queued:
    skill: plan
    next: planned
  planned:
    skill: implement
    model: claude-sonnet-4-6
    timeout: 30m
    next: implemented
  implemented:
    prompt: "変更内容をセルフレビューし、指摘事項があれば修正する"
    next: done
  done:
    run: cleanup
```

### 7.1 定義のスナップショット

タスク登録時にワークフロー定義をタスクファイル側へ**スナップショット**し、以降そのタスクはスナップショットのみを参照する。保存形態(タスクファイルへの埋め込み、または `state/tasks/` 配下の隣接ファイル)の確定はドメイン設計に委ねるが、置き場所はタスクファイルと同じ寿命を持ち(アーカイブ時はともに `state/archive/` へ移動する)、runディレクトリには置かない(gc(§9.2)の削除対象に入れないため)。元YAMLの編集は既存タスクに影響しない(実行途中で定義が変わるとtickの決定性が壊れるため)。定義更新を既存タスクへ適用する操作は提供しない。スナップショットにより「このタスクは何の定義で動いたか」が事後に確定する。

スナップショットの対象はワークフロー定義のみである。グローバル設定(エージェント定義・notify_cmd・各種デフォルト)は各実行時に解決されるため、その編集は既存タスクの以後の実行にも反映される。

### 7.2 デフォルト値

- 期間の表記は共通で `<数値><単位>` とする(単位は `s` / `m` / `h` / `d`。例: `30m`、`1h`、`30d`)。timeout・判定timeout・`run_retention` に適用する。
- timeout: グローバルデフォルト **1h**。ステータス単位で上書き可。`timeout: none` で明示的に無制限化できる(エージェントのハングを事故なく検出するため、無指定を無制限とは扱わない)。
- リトライ上限: デフォルト **2**。ステータス単位で上書き可。
- 判定失敗の再判定上限・判定timeout: §6.3のとおりグローバル設定。
- 連続spawn失敗の上限: §4.1のとおりグローバル設定(デフォルト3)。
- runディレクトリの保持期間(`run_retention`): グローバル設定(例: `run_retention: 30d`)。未設定なら gc は行われない(§9.2)。

## 8. 人間介入と通知

- ツールによるエスカレーションは stopped(凍結)に一本化する。stopped 確定時に、グローバル設定の通知コマンド(`notify_cmd`)を実行する。通知手段の中身はツールは感知しない。
- notify_cmd には判定コマンド(§6.3)と同様に環境変数で情報を渡す: `TASK_ID` / `WORKFLOW`(ワークフロー名)/ `TASK_STATUS`(現在のタスクステータス)。引数は使用しない(拡張時の互換性のため)。作業ディレクトリは規定しないため、cwdに依存しないように書く。コマンドのトークンにプレースホルダ展開は行われない(§6.3)。
- notify_cmd の実行には組み込みの固定timeout(60秒)を適用する(通知は排他ロック保持中に同期実行されるため、ハングした通知コマンドがツール全体を止めないための保護。ADR-018)。超過は通知失敗として扱われ、下記の at-least-once の仕組みで自動再試行される。長時間かかる通知はコマンド側で非同期化する。
- 通知は **at-least-once** とする。処理順序は「stoppedをタスクファイルへ書く → notify_cmd 実行 → `notified_at` を追記」。stopped の記録は常に `notified_at` を伴わない状態で行い、過去の凍結の通知記録を引き継がない(retry / set-status 後に再び凍結した場合も必ず通知される)。`notified_at` のない stopped タスクを次tickが検出して(再)通知する。クラッシュ時の二重通知は許容し、通知の欠落を許さない。notify_cmd 自体の失敗もこの仕組みで自動再試行される。
- 凍結に至った要因はタスクファイルに記録し、参照可能にする。エージェント実行由来なら直前実行の終了情報・最終出力への参照、実行を伴わないツール操作の失敗(worktree作成・削除、アーカイブ移動、spawn失敗)由来なら直近の失敗要因(§9)がそれにあたる。
- 人間はCLIで再試行(retry)または手動ステータス遷移(set-status)を行って再開する。
- 人間の判断を待つステータス(レビュー待ち等)が必要な場合は、「何もしない」動作のステータスとしてワークフロー設計者が任意に定義する。これはワークフロー設計の話であり、ツールの機構ではない。

## 9. 状態管理(ファイル)

- ツールの設定・定義・状態は単一の**グローバルホーム**に集約する。既定は `~/.pulsen/` とし、環境変数 `PULSEN_HOME` またはCLIの `--home` フラグで上書きできる(優先順位: フラグ > 環境変数 > 既定)。タスクは複数リポジトリを対象にできるため、状態はプロジェクトごとではなくツール全体で1つとする。
- グローバルホームの構成: `config.yaml`(グローバル設定: agents・notify_cmd・各種デフォルト)/ `workflows/`(ワークフロー定義YAML)/ `state/`(タスクファイル・runディレクトリ・アーカイブ)/ `worktrees/`(タスクのworktree。§5)。
- 状態はすべてファイルで管理し、データベースは使用しない。これは要件ではなく現時点での方針であり、本節はこの方針の下での仕様を記述する。
- 1タスク = 1ファイル(例: `state/tasks/<task-id>.json`)。主な属性: ワークフロー名、対象(リポジトリ・ベースブランチ等)、現在のタスクステータス、実行状態、workspace_path、branch、attempt_count、judge_attempt_count、spawn_fail_count、現在attemptのrunディレクトリパス・PID・kill同定子・starttime、直近の失敗要因(worktree作成・削除、アーカイブ移動、spawn失敗などツール操作の失敗時に更新するメッセージ)、notified_at、更新日時。
- 更新は「一時ファイルへ書き込み後にアトミック置換(§4.3)」で行い、アトミック性を保証する。書きかけ状態のファイルが観測されてはならない。
- 書き込みは、tickおよびCLI操作が同一の排他ロック(§4.3)を取得して行う。
- tickはタスクディレクトリを走査して全タスクを読み込む。想定規模(単一マシン・数十〜数百タスク)ではフルスキャンで十分とする。
- tickはパース不能なタスクファイルに遭遇した場合、そのタスクをスキップして残りのタスクの処理を続行し、破損したファイルへの書き込み(stopped化を含む)は行わない。破損の検出は `ls` / `show` の報告に、修復は人間の直接修復に委ねる。
- タスクファイルは人間可読とし、直接の閲覧・修復を可能にする。

### 9.1 終端処理(クリーンアップ)

クリーンアップ動作のステータスに到達したタスクについて、tickは次を行う。

- worktreeを削除する(git worktree remove 相当)。削除に失敗した場合は attempt_count を消費し、次のtickで再試行する。リトライ上限超過で stopped とする(確定時に通知する。§8)。stopped 後に retry で pending に戻せば、クリーンアップが再試行される
- **ブランチは削除しない**(成果物そのものであり、ツールの責務外)
- タスクファイルを `state/tasks/` から `state/archive/` へ移動する(削除しない)。これによりtickの走査対象から外れる。移動に失敗した場合もworktree削除と同様に attempt_count を消費して次のtickで再試行し、リトライ上限超過で stopped とする(確定時に通知する。§8)
- runディレクトリは削除しない(保持ポリシーは§9.2)

### 9.2 runディレクトリ

実行の成果メタデータは worktree と完全に分離し、`state/runs/<task-id>/attempt-<n>/` に集約する。

- 内容: `pid` / `starttime` / `exit` / `stdout.log` / `stderr.log`(ラッパーが標準出力・標準エラーをリダイレクトする)。加えて、遅延起動の抑止に用いる無効化マーカー(§4.1)が置かれ得る
- `pid` / `starttime` / `exit` の書き込みは、タスクファイルと同様にアトミック置換(§4.3)で行い、書きかけの内容が観測されないようにする
- attempt番号をパスに含めることで、前回試行との混同を構造的に防ぐ
- クリーンアップでは削除しない(凍結・過去タスクの調査材料を保護するため)。肥大化には保持期間によるgc(下記)で対処する

**runディレクトリのgc**: グローバル設定 `run_retention`(保持期間)を定義した場合のみ、tickは各パスで保持期間を超えたattemptのrunディレクトリを削除する(未設定ならgcは行われない。既存運用のログを黙って消さないための明示オプトイン。ADR-011)。

- attemptの経過時間は、ディレクトリ内のファイルの最終更新時刻の最大値で判定する(ファイルが1つもないattemptディレクトリは、ディレクトリ自体の最終更新時刻で判定する)
- 保護規則: (a) 現役タスク(`state/tasks/`)のタスクファイルが現在参照しているattempt、(b) stopped のタスクの全attempt は、期間によらず削除しない(調査材料の保護)。アーカイブ済みタスク・タスクファイルが存在しない孤児のrunディレクトリは保護しない
- 保護規則(a)の参照は常に決定的である: タスクファイルの現在attemptの参照(runディレクトリパス等)は、次のlaunching記録(§4.1)で新しいattemptに置き換わるまで保持される。実行状態がどの経路で変わっても(skippedやspawn失敗によるpending復帰、failedでの再実行待ち、retry / set-status によるpending化)、この参照が書き換えられることはない
- パース不能なタスクファイルが `state/tasks/` に存在するタスクIDのrunディレクトリは、保護規則を判定できないため全attemptを保護する(読めない帳簿に対して何もしない原則(§9)と同じ。修復またはタスクの決着後にgc対象へ戻る)
- 削除に失敗したattemptはスキップして報告し、次のtickが再試行する。gcの失敗はどのタスクのカウンタも消費せず、stopped を発生させない(タスクの帳簿と無関係な掃除であるため)
- attemptがすべて削除され空になった `state/runs/<task-id>/` も削除する
- gcが削除するのはattemptのrunディレクトリのみである。ワークフロー定義のスナップショットはタスクファイル側(§7.1)にあり、gcの対象に入らない
- 常駐型(循環・ポーリング)のワークフローは周回ごとに新しいattemptを生み蓄積が速いため、その運用では設定を推奨する
- アーカイブ済みタスクファイル(`state/archive/`)の整理は本gcの対象外であり、別途提供する将来機能のままとする

## 10. CLI

最小セット:

- `add` — タスクの登録。ワークフロー(名前またはファイルパス。§7)と対象(リポジトリ・ベースブランチ等)を指定し、pending で登録する。ワークフローの解決・パースに加え、リポジトリパスとベースブランチの存在、およびワークフローが参照するエージェント定義のコマンドテンプレート(未知プレースホルダ等の不備、参照するプレースホルダへの値の供給(`{model}` を使うテンプレートに model 指定がない等)、skill 指定のステータスがある場合は `skill_input` が定義されていることを含む。§3.1)も登録時に検証し、不正ならエラーとしてタスクを作らない。登録後にリポジトリやブランチが失われるケースは実行時のworktree作成失敗(§5)として、登録後の config.yaml 編集で混入したテンプレート不備は起動時の展開失敗として連続spawn失敗経路(§4.1)に合流するため(tickは起動記録の前に展開の失敗を同期検出し、attemptを採番せずspawn失敗として分類する。ADR-016)、この検証は実行時の失敗経路を置き換えるものではない。実行はしない(次のtickが拾う)。次回の定期tickを待たず即座に開始したい場合は、続けて `tick` を呼ぶ(`add && tick`)。登録専用の即実行機構は持たない
- `tick` — 1回のtickパスを実行して終了する(§4。`run_retention` 設定時はrunディレクトリのgcも行う。§9.2)。定期実行は外部スケジューラーがこのコマンドを呼ぶことで実現する
- `abort <task-id>` — タスクの停止(実行中ならkillを伴う。→ stopped。§6.5)
- `retry <task-id>` — 再試行(attempt_count・judge_attempt_count・spawn_fail_count をリセットし pending に戻す)。**stopped のタスクに対してのみ受理し、それ以外は拒否する**(failed は放置すれば自動リトライされる、pending は既に実行待ち、と案内する)
- `set-status <task-id> <status>` — 手動ステータス遷移。受理時は、遷移先の動作種別によらず一律に attempt_count・judge_attempt_count・spawn_fail_count をリセットし、実行状態を pending にする(stopped だった場合は凍結が解ける。retry と対称の一律規則)。遷移先での次のtickの動作は§4の規則に従う(エージェント実行なら起動、何もしないなら滞留、クリーンアップなら終端処理)。**launching / running のタスクには拒否し、「先にabortせよ」と案内する**(kill+遷移の複合動作は提供しない。全ケースは abort → set-status → retry の組み合わせで表現する)
- `ls` — タスク一覧(ステータスでのフィルタ含む。`--all` でアーカイブ済みも表示)
- `show <task-id>` — タスク詳細(最終出力への参照・実行メタデータ含む)

状態を変更するCLI操作(add / abort / retry / set-status)は、tickと同一のロックを取得した上で行う。読み取り専用の `ls` / `show` はロックを取得しない(タスクファイルの更新はアトミック置換(§4.3)で行われるため、ファイル単位の読み取りは常に一貫した内容になる)。
