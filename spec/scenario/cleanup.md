# シナリオ: 終端処理とアーカイブ

利用者は「AIエージェントに任せる作業をワークフロー化し、複数のタスクを自動で進めたい開発者」。ここではタスクが終端に到達したあとの処理と、その後の成果回収・参照を扱う。

要件は [../requirements.md](../requirements.md) の §5・§9.1・§9.2・§10 を参照。

## クリーンアップステータス到達によるworktree削除とアーカイブ

### 目的

ワークフローを完走したタスクの後始末が自動で行われ、開発者が手を動かさなくてもディスク上のworktreeが片付き、タスク一覧が現役のタスクだけに保たれる。

### 前提

- ワークフロー定義に、クリーンアップ動作(`run: cleanup`)のステータスが終端として定義されている(例: `done`)
- タスクが各ステータスのエージェント実行と判定を経て、completed によりクリーンアップステータスへ遷移した
- 外部スケジューラーにより `tick` が定期実行されている

### フロー

1. タスクが最後のエージェント実行を completed で終え、次ステータスとしてクリーンアップステータス(例: `done`)へ遷移する。
2. 次の tick が、クリーンアップ動作が定義されたステータスのタスクを検出する。
3. tick がタスクの worktree を削除する(git worktree remove 相当)。ブランチは削除しない(成果物そのものであり、ツールの責務外)。
4. tick がタスクファイルを `state/tasks/` から `state/archive/` へ移動する(削除しない)。以降このタスクは tick の走査対象から外れる。
5. runディレクトリ(`state/runs/<task-id>/`)はそのまま保持される。過去タスクの実行ログ・終了コードは調査材料として残る。
6. 開発者が `ls` を実行すると、このタスクは既定の一覧には現れない。`ls --all` でアーカイブ済みとして確認できる。

### 異常系・エッジケース

- **worktree削除の失敗(ファイルを掴んでいるプロセスがいる等)**: worktree内のファイルを開いたままのプロセス(エディタ、残存した孤児プロセス等)がいて削除に失敗した場合、tick はアーカイブへ進めず、attempt_count を消費してタスクを `state/tasks/` に残したまま終了する。次の tick が同じ判断を再導出してクリーンアップを再試行する(冪等)。リトライ上限超過で stopped となり、確定時に通知される。開発者は通知を受けて原因(ファイルを掴んでいるプロセス等)を解消し、`retry` で pending に戻すと、次の tick からクリーンアップが再試行される。
- **worktreeが既に存在しない**: 開発者が手動で `git worktree remove` 済み、またはディレクトリを消してしまっていた場合、削除は「達成済み」とみなしてエラーにせず、アーカイブ処理へ進む。クリーンアップは「worktreeが存在しない状態にする」ことが目的であり、既にその状態なら成功である。
- **worktree作成前のタスクがクリーンアップに到達**: 初期ステータスがクリーンアップ動作である、または最初の実行前に set-status でクリーンアップステータスへ遷移させた場合、worktreeは未作成でありタスクファイルにworkspace_pathがない。削除対象がないためアーカイブ処理のみを行う。
- **アーカイブ移動の失敗**: `state/archive/` への移動が失敗した場合(ディレクトリ作成不可・権限不足等)、worktree削除の失敗と同様に、tick は attempt_count を消費してタスクを `state/tasks/` に残したまま終了し、次の tick が再試行する。worktree削除は上記のとおり「既に存在しない」を成功とみなすため、再試行はアーカイブ移動から実質的に再開される。リトライ上限超過で stopped となり、確定時に通知される。開発者が原因(権限不足等)を解消して `retry` で pending に戻すと、次の tick からクリーンアップが再試行される。中途半端な状態(両方に存在・どちらにも存在しない)が観測されないよう、移動はアトミックな操作として行う。
- **worktree削除とアーカイブの間のクラッシュ**: worktree削除後・アーカイブ前に tick がクラッシュしても、次の tick が「クリーンアップステータスのタスクがまだ `state/tasks/` にある」ことから同じ処理を再導出する。worktreeなしの削除は成功扱いのため、二重処理は無害である。
- **凍結(stopped)タスクのworktreeは削除されない**: クリーンアップはクリーンアップ動作のステータスに到達したタスクにのみ行われる。リトライ上限超過・判定不能・abort で stopped になったタスクは、タスクステータスがクリーンアップステータスに達していないため、worktreeもタスクファイルもそのまま保持される。開発者が原因を調査し、retry / set-status で対応するまで何も消えない。stopped のタスクを調査の結果「破棄してよい」と判断した場合は、set-status でクリーンアップステータスへ手動遷移させることで、通常と同じ終端処理に乗せられる。
- **runディレクトリの肥大化**: runディレクトリはクリーンアップでは削除しないため、長期運用では蓄積する。肥大化への対応は明示的な gc 操作または保持期間のグローバル設定として別途提供する(本シナリオのスコープ外)。

## 成果ブランチの回収

### 目的

完了したタスクの成果(コード変更)を、開発者が自分のリポジトリ操作の流儀(マージ・PR作成等)で回収できる。ツールは成果を消さず、回収作業には関与しない。

### 前提

- タスクがクリーンアップステータスに到達し、worktree削除とアーカイブが完了している
- ブランチ名はタスクIDから決定的に生成され、タスクファイル(アーカイブ済み)に記録されている

### フロー

1. 開発者が `ls --all` または `show <task-id>` で、完了したタスクのブランチ名と対象リポジトリを確認する。
2. 対象リポジトリへ移動し、そのブランチを通常のgit操作で扱う(例: `git log <branch>` で成果を確認し、PRを作成する、またはベースブランチへマージする)。
3. 取り込みが済んだら、開発者が自分の判断でブランチを削除する。ツールはブランチのライフサイクルに関与しない。

### 異常系・エッジケース

- **ブランチにコミットがない**: エージェントがコミットせずに完走したワークフロー(調査のみ等)では、ブランチはベースブランチと同一のまま残る。回収するものがないだけで異常ではない。不要なら開発者が削除する。コミットを成果とするワークフローでは、コミットの実施をステータスのプロンプト/スキルで指示するのがワークフロー設計者の責務である。
- **worktree削除前に回収したい**: クリーンアップ到達前(実行途中・停滞中・stopped)でも、ブランチとworktreeは存在するため `show <task-id>` でパスを確認して内容を見られる。ただしworktree内のファイルを掴んだままにすると、後のクリーンアップでのworktree削除が失敗し再試行に回る(リトライ上限超過で凍結する)点に注意する。
- **同一対象に複数タスクを走らせた場合**: タスクの重複は許容されており、各タスクは独立したブランチを持つ。どの成果を採用するかの判断・競合の解消は開発者の作業であり、ツールは関与しない。
- **回収前にリポジトリ側でブランチを消してしまった**: ツールはブランチを再生成しない。worktreeも削除済みであれば成果は失われる。runディレクトリのログ(stdout.log / stderr.log)から実行内容を辿ることはできるが、コードそのものの復元手段はツールにはない。

## アーカイブ済みタスクの一覧・参照

### 目的

過去に完了したタスクを後から一覧・参照し、「いつ・何のワークフローで・どのブランチに成果を残したか」を確認できる。アーカイブ済みタスクへの誤操作は拒否され、帳簿の整合性が保たれる。

### 前提

- 複数のタスクがクリーンアップを経て `state/archive/` にアーカイブされている
- 現役のタスクも並行して存在する

### フロー

1. 開発者が `ls` を実行する。既定ではアーカイブ済みタスクは表示されず、現役のタスクだけが一覧される。
2. 過去のタスクを含めて見たいときは `ls --all` を実行する。アーカイブ済みタスクが、現役タスクと区別できる形で一覧に含まれる。
3. 特定のタスクを深掘りしたいときは `show <task-id>` を実行する。ワークフロー名・対象・ブランチ名・最終的なステータス・実行メタデータ(attempt数・最終実行の終了情報・runディレクトリへの参照)が確認できる。
4. 実行ログが必要なら、show が示す runディレクトリ(`state/runs/<task-id>/attempt-<n>/`)の `stdout.log` / `stderr.log` を直接参照する。runディレクトリはアーカイブ後も保持されている。
5. タスクファイル自体は人間可読であり、`state/archive/` のファイルを直接開いて確認することもできる。

### 異常系・エッジケース

- **アーカイブ済みタスクへの操作(retry / set-status / abort)**: いずれも拒否する。アーカイブは終端であり、worktreeは既に削除されているため再実行の前提(§5の「同じワークスペースを実行対象とする」)が成立しない。同じ作業をやり直したい場合は、`add` で新しいタスクとして登録する(1タスク = 1worktreeの原則どおり、新しいworktree・ブランチで実行される)。
- **アーカイブ済みと現役でタスクIDを照会した場合の解決**: `show <task-id>` は現役(`state/tasks/`)を探し、なければアーカイブ(`state/archive/`)を探して表示する。どちらにもなければ「存在しないタスク」としてエラーを返す。
- **アーカイブ済みタスクのrunディレクトリが消えている**: gc 等でrunディレクトリが削除済みの場合、show はタスクファイルにある情報(ステータス履歴・ブランチ名等)のみを表示し、ログへの参照は「存在しない」ことを明示する。エラーにはしない。
- **アーカイブが大量にある場合の `ls --all`**: 想定規模(数十〜数百タスク)ではフルスキャンで足りる。長期運用でアーカイブが肥大化した場合の整理は、明示的な gc または保持期間設定として別途提供する(本シナリオのスコープ外)。
- **アーカイブファイルの手動修復**: タスクファイルは人間可読であり、直接の閲覧・修復が許されている(§9)。アーカイブ済みファイルも同様に扱えるが、`state/tasks/` へ手で戻す操作は想定しない(worktreeが存在しないタスクを tick の走査対象へ戻すことになるため)。やり直しは新規 `add` で行う。
