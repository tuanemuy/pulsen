# セットアップとワークフロー定義

ツールを使い始める開発者が、グローバル設定・ワークフロー定義・定期実行の仕込みを行うまでのシナリオ。要件は [../requirements.md](../requirements.md) を参照。

## シナリオ1: グローバル設定を作成する

### 目的

エージェントの実体(コマンドテンプレート)・通知コマンド・各種デフォルトをグローバル設定として定義し、ワークフローYAMLから論理名でエージェントを参照できる状態にする。

### 前提

- ツールのバイナリがインストール済みで、PATHが通っている。
- 実行したいエージェントCLI(例: Claude Code の `claude`)がマシンにインストール済み。
- グローバルホームは既定の `~/.pulsen/` を使う。別の場所を使う場合は環境変数 `PULSEN_HOME` または各コマンドの `--home` フラグで指定する(優先順位: フラグ > 環境変数 > 既定)。

### フロー

1. グローバルホームのディレクトリ `~/.pulsen/` を用意する。
2. `~/.pulsen/config.yaml` を作成し、`agents` にエージェント名 → コマンドテンプレートのマップを定義する。

    ```yaml
    agents:
      claude:
        cmd: claude -p {input} --model {model}
        skill_input: "/skill {skill}"
    ```

3. テンプレートにはプレースホルダ(`{model}` `{prompt}` `{skill}` `{workspace}` 等)を使える。スキル指定時の入力変換規則(`skill_input`)もここで定義する。空白を含む引数やシェル機能が必要な場合は、文字列ではなくトークン配列で定義する(例: `["sh", "-c", "cd {workspace} && …"]`)。
4. stopped確定時に実行される通知コマンド `notify_cmd` を定義する(デスクトップ通知・Slack投稿スクリプト等、中身はツールの関知外)。
5. 必要ならグローバルデフォルト(判定失敗の再判定上限、判定コマンドのtimeout等)を定義する。定義しなければ既定値(再判定上限3、判定timeout 60秒程度)が使われる。
6. `ls` など任意のコマンドを一度実行し、設定が読み込めることを確認する。

### 異常系・エッジケース

- config.yaml が存在しない: グローバルホームが未初期化であることをエラーで示す。設定ファイルの場所(解決されたグローバルホームのパス)と、作成が必要であることを案内する。
- config.yaml が不正なYAML: パースエラーの位置とともに読み込みを失敗させる。壊れた設定で部分的に動作しない。
- テンプレートに未知のプレースホルダが含まれる: タスク登録(`add`)時に、ワークフローが参照するエージェント定義のコマンドテンプレートが検証され、不備があればエラーとしてタスクは作られない。登録後の config.yaml 編集で混入した不備は、起動時の展開失敗としてtickがspawn失敗に分類し、連続spawn失敗の上限超過で stopped として凍結・通知される。
- ワークフローに `skill` 指定のステータスがあるのに、参照するエージェント定義に `skill_input` が定義されていない: スキル→入力文字列の変換ができないテンプレートの不備として、未知のプレースホルダと同様に扱われる。タスク登録(`add`)時に検証され、エラーとしてタスクは作られない。登録後の config.yaml 編集で `skill_input` が失われた場合は、起動時の展開失敗としてtickがspawn失敗に分類し、連続spawn失敗の上限超過で stopped として凍結・通知される。
- コマンドはシェルを介さず直接起動されるため、文字列テンプレートにパイプやリダイレクトを書いても機能しない。シェル機能が必要な場合は配列形式で `sh -c` 等を明示する必要がある。文字列形式のクォートはグルーピングとして解釈されない。
- `notify_cmd` が未定義: stopped確定時に通知は行われないが、他の動作には影響しない。
- config.yaml の編集と既存タスク: グローバル設定はスナップショットされず各実行時に解決されるため、編集は既存タスクの以後の実行(retry 後の再実行を含む)にそのまま反映される。設定不備はconfig.yamlの修正と `retry` だけで復旧できる一方、`agents` のエージェント定義を削除・改名すると、その名前を参照する既存タスクの以後の起動が失敗する(連続spawn失敗の上限超過で stopped に至る)。
- `PULSEN_HOME` と `--home` の両方が指定されている: フラグが優先される。意図しないホームを見ていて「設定がない」と誤認するケースがあるため、エラーメッセージには解決後のホームパスを含める。

## シナリオ2: ワークフローYAMLを作成し workflows/ に配置する

### 目的

タスクステータスと各ステータスの動作(エージェント実行・何もしない・クリーンアップ)をYAMLで定義し、`add` でワークフロー名を指定するだけでタスクを登録できる状態にする。

### 前提

- シナリオ1のグローバル設定が作成済みで、`agents` に少なくとも1つのエージェント(例: `claude`)が定義されている。
- 自動化したい作業の流れ(例: 計画 → 実装 → セルフレビュー → クリーンアップ)が決まっている。

### フロー

1. 作業の流れをステータスの列に分解する。各ステータスに動作(エージェント実行 / 何もしない / クリーンアップ)を割り当てる。
2. ワークフローYAMLを書く。`initial:` で初期ステータスを必須指定し、ワークフロー単位のデフォルトエージェント・モデルと、ステータスごとの定義(プロンプトまたはスキル、モデル・エージェントの上書き、timeout、リトライ上限、`next`、判定コマンド)を記述する。

    ```yaml
    workflow: implement
    agent: claude
    model: claude-opus-4-8
    initial: queued
    statuses:
      queued:
        skill: plan
        next: planned
      planned:
        skill: implement
        model: claude-sonnet-4-6
        timeout: 30m
        next: implemented
      implemented:
        prompt: "変更内容をセルフレビューし、指摘事項があれば修正する"
        next: done
      done:
        run: cleanup
    ```

3. 人間の判断待ちが必要な箇所(レビュー待ち等)は「何もしない」ステータスとして定義する。そこからの進行は `set-status` による手動遷移で行う。
4. ファイルを `~/.pulsen/workflows/implement.yaml` として保存する。`add` 時のワークフロー名はファイル名から解決される(`implement` → `workflows/implement.yaml`)。
5. `add` でワークフロー名と対象(リポジトリ・ベースブランチ)を指定して、実際に流すタスクを登録する。定義は登録時に検証され、不備があれば即時にエラーとなってタスクは作られないため、登録の成功がそのまま定義の受理確認になる。登録したタスクはpendingのまま残り、tickの定期実行(シナリオ3)を仕込むと実行が始まる。実タスクを流す前に定義だけ確認したい場合は、確認用のタスクを登録して受理を確かめたうえで、`set-status <task-id> <クリーンアップステータス>` でクリーンアップステータスへ遷移させて片付ける(次のtickが終端処理を行う。worktree未作成のためアーカイブのみ。[cleanup.md](cleanup.md) 参照)。外部スケジューラー(シナリオ3)が既に稼働している環境では、確認用タスクは片付ける前に次のtickで起動され得る。実行中のタスクは set-status が拒否されるため先に `abort` で止める(シナリオ4参照)。`abort` は実行を止めたい場合の手段であり、タスクは stopped として残留するうえ通知(`notify_cmd`)も発火する。

### 異常系・エッジケース

- `initial:` の欠落: 初期ステータスが決まらないため、定義の読み込み時にエラーにする。キーの記述順には依存しないので、`initial` がファイル末尾にあっても問題ない。
- `initial` や `next` が `statuses` に存在しないステータスを参照している: 到達時ではなく読み込み時に検出してエラーにする。
- エージェント実行を定義したステータスに `next` がない: completed時の遷移先が決まらないため、読み込み時(登録時のパース)エラーにする。滞留させたい場合は「何もしない」ステータスで表現する。
- `agents` に定義されていないエージェント名の参照: グローバル設定と突き合わせて解決できないため、タスク登録時にエラーにする。定義済みのエージェント名の一覧を示す。
- 1つのステータスに `prompt` と `skill` の両方を指定: どちらか一方のみ有効なため、定義エラーにする。エージェント実行のステータスでどちらも未指定の場合も同様。
- 不正なYAML(インデント崩れ・重複キー等): パースエラーとして登録を失敗させる。
- `timeout` 未指定のステータスはグローバルデフォルトの1hが適用される。無制限にしたい場合は `timeout: none` を明示する(無指定 = 無制限とは扱われない)。
- 登録済みタスクへの影響: タスク登録時に定義がスナップショットされるため、`workflows/` のYAMLを編集しても既存タスクの動作は変わらない。編集後の定義は以降に登録するタスクからのみ有効になる。定義更新を既存タスクへ適用する操作は存在しない。

## シナリオ3: 外部スケジューラーに tick の定期実行を登録する

### 目的

ツールは常駐しないため、cron・launchd・タスクスケジューラ等の外部スケジューラーに `tick` を登録し、登録済みタスクが自動で進行する状態にする。

### 前提

- シナリオ1・2が完了し、設定とワークフローが配置済み。
- 利用OSのスケジューラー(Linux: cron / macOS: launchd または cron / Windows: タスクスケジューラ)が使える。

### フロー

1. 手動で `tick` を一度実行し、エラーなく1回のtickパスが完了することを確認する(タスクが無ければ何もせず終了する)。
2. 外部スケジューラーに `tick` の定期実行を登録する。cronの例:

    ```
    */5 * * * * /path/to/pulsen tick
    ```

3. 実行間隔を決める。tickは永続化された事実から毎回同じ判断を再導出する冪等な処理なので、間隔は反応速度の要求に合わせて選べばよい(短くしても多重実行は排他ロックで防がれる)。
4. スケジューラー実行の環境がインタラクティブシェルと異なる点を吸収する: バイナリは絶対パスで指定し、既定以外のグローバルホームを使う場合は `PULSEN_HOME` の設定または `--home` フラグをコマンドラインに含める。
5. テスト用のタスクを `add` で登録し、次のtick以降で実行状態が進むことを `ls` / `show` で確認する。

### 異常系・エッジケース

- tickの二重起動: 前回のtickが長引いている間に次のtickが起動した場合、排他ロックの取得に失敗した側は状態を変更せずスキップして終了する。エラーではなく正常な動作であり、次回のtickが処理を引き継ぐ。
- tick実行中のCLI操作: `add` や `abort` などのCLI操作もtickと同一のロックを取得するため、状態の書き込みが競合することはない。
- スケジューラー環境でグローバルホームが解決できない: cron等では `HOME` や環境変数がインタラクティブシェルと異なることがある。tickが「設定がない」で失敗する場合は、解決されたホームパスをエラー出力で確認し、`--home` で明示する。
- tickの途中クラッシュ(マシン再起動を含む): 状態はすべてファイルに永続化されており、次のtickが状態ファイルとプロセスの生存確認から復旧する。スケジューラー側での特別な対処は不要。
- スケジューラーの停止・登録漏れ: タスクは進行しないが状態は壊れない。tickの再開で続きから進む。動作確認には手動の `tick` 実行がそのまま使える。

## シナリオ4: 作成したワークフローを開発中にファイルパス指定で試す

### 目的

ワークフローYAMLを `workflows/` に配置する前に、作業ディレクトリ上のファイルを直接指定してタスクを登録し、定義を試行錯誤する。

### 前提

- グローバル設定(シナリオ1)が作成済み。
- 書きかけのワークフローYAML(例: `./draft.yaml`)が手元にある。
- 試行に使うテスト用のリポジトリがある。

### フロー

1. ワークフローYAMLを任意の場所に書く(`workflows/` に置く必要はない)。
2. `add` でワークフロー名の代わりにファイルパスを指定し、テスト用の対象とともにタスクを登録する。定義は登録時にスナップショットされるため、以降このタスクは元ファイルを参照しない。
3. 登録に続けて手動で `tick` を実行し、初期ステータスのエージェント実行が起動することを確認する(定期実行を待つ必要はない。このtickパスは当該タスク専用ではなく、他に実行可能なタスクがあればそれらも処理される)。
4. `show` と runディレクトリのログ(`stdout.log` / `stderr.log`)で、エージェントの挙動(期待どおりに起動したか)を確認する。
5. 定義を修正し、新しいタスクを登録して再試行する。修正はスナップショット済みの既存タスクに影響しないため、試行ごとに独立して比較できる。試行済みタスクは不要になり次第 `set-status <task-id> <クリーンアップステータス>` でクリーンアップステータスへ遷移させて片付ける(次のtickが終端処理を行う。実行中のタスクは set-status が拒否されるため先に `abort` で止める。[cleanup.md](cleanup.md) 参照)。`abort` だけではタスクは stopped として残留し、通知(`notify_cmd`)も発火する。`set-status` の遷移先はスナップショットされた定義に存在するステータスであればよく、`initial` からの遷移経路は不要なため、ドラフト段階の定義にも終端のクリーンアップステータスを含めておくことを推奨する。クリーンアップステータスがそもそも定義されていない定義では `abort` で止めるのが代替手段になる(残ったタスクの処分は異常系を参照)。
6. 定義が固まったら、ファイルを `~/.pulsen/workflows/<名前>.yaml` に配置し、以降は名前指定で登録する。

### 異常系・エッジケース

- 指定したファイルパスが存在しない: 登録をエラーにする。相対パス指定時はカレントディレクトリからの解決であることに注意する。
- `workflows/` に同名ファイルがない状態での名前指定: 名前解決(`implement` → `workflows/implement.yaml`)に失敗し、登録をエラーにする。ファイルパス指定で試していた定義を名前指定に切り替えた際に起きやすい。解決を試みたパスを示し、配置漏れに気づけるようにする。
- パス指定とワークフロー名の曖昧さ: `add` はパスとして解決できる指定はファイル、それ以外は名前として扱う。名前と同名のファイルがカレントディレクトリにある場合など、どちらとして解釈されたかが結果から分かること。
- 元ファイルの削除・移動: スナップショット済みタスクは影響を受けず、最後まで実行できる。「このタスクが何の定義で動いたか」はスナップショットから事後に確認できる。
- 定義に誤りのあるタスクを登録してしまった: 定義を直しても既存タスクには反映されない。当該タスクは `abort` で止め、修正した定義で新しいタスクを登録し直す。
- クリーンアップステータスのない定義で登録したタスクの最終処分: `abort` で止めても stopped のまま `state/tasks/` に残留し続ける。タスクファイルは人間可読で直接操作できるため、手動で `state/archive/` へ移動すればtickの走査対象から外せる。手動の移動はtickと同一ロックの外での操作になるため、外部スケジューラーを止める等、スケジューラーが動いていないタイミングで行う([monitoring.md](monitoring.md) のタスクファイルの直接閲覧・修復シナリオ参照)。worktreeが作成済みなら、その削除(`git worktree remove` 相当)も手動での後片付けになる。

## シナリオ5: 判定コマンドを定義してexit code以外の基準で判定する

### 目的

エージェントのexit codeだけでは成否を判断できないステータス(例: テストの通過や成果物の有無で判断したい)に判定コマンドを定義し、実行結果を独自の基準で completed / failed に分類できる状態にする。

### 前提

- ワークフローYAML(シナリオ2)が手元にある。配置済みでも、ファイルパス指定での試行中(シナリオ4)でもよい。
- 判定基準をコマンドとして表現できる(例: 成果物ファイルの存在確認、テストコマンドの実行)。

### フロー

1. 判定スクリプトを書く。ツールは判定コマンドに次の環境変数を与えて実行する(引数は渡されない): `TASK_ID` / `WORKSPACE`(worktreeパス)/ `EXIT_CODE`(エージェントの終了結果の数値)/ `RUN_DIR`(当該attemptのrunディレクトリ)。判定の入力には `WORKSPACE` 内の成果物や `RUN_DIR` のログ(`stdout.log` / `stderr.log`)が使える。
2. スクリプトのexit codeで判定結果を表現する。3値で解釈される: **0 = completed、10 = failed、それ以外 = 判定失敗**。「判定した結果failedだった」と「判定自体が壊れた」を区別するための割り当てなので、failedと判断した分岐では明示的に `exit 10` する。慣習的な `exit 1` はfailedではなく判定失敗として扱われる。
3. ワークフローYAMLの該当ステータスに判定コマンドを定義する。判定が必要なステータスにだけ定義すればよく、未定義のステータスはデフォルトのexit code判定(0 = completed、非0 = failed)のまま動く。エージェント定義と同様にコマンドはシェルを介さず直接起動されるため、パイプ等のシェル機能が必要な場合は配列形式で `sh -c` 等を明示する。
4. タスクを登録して当該ステータスまで進め、判定どおりに動くことを確認する: スクリプトが 0 を返すケースで次のタスクステータスへ遷移すること、10 を返すケースでfailedとしてリトライされることを、`show` と `ls` で確認する。
5. 必要なら判定失敗時の挙動もグローバル設定で調整する(再判定上限・判定コマンドのtimeout。シナリオ1)。

### 異常系・エッジケース

- 判定コマンドが 0 / 10 以外で終了する: 判定失敗として `judge_attempt_count`(attempt_count とは独立のカウンタ)が加算され、次のtickで再判定される。上限(デフォルト3、グローバル設定で変更可)の超過で stopped として凍結・通知される。判定不能は環境・定義の不具合であり、エージェントの再実行では解決しないため、リトライは行われない。
- 判定コマンドが応答しない: 判定コマンド自体のtimeout(グローバル設定、デフォルト60秒程度)の超過は判定失敗として扱われ、上記と同じ経路をたどる。
- 判定コマンドの実体が見つからない・起動できない: 判定を完了できないため判定失敗として扱われる。相対パスはスケジューラー実行の環境では解決が変わり得るため、スクリプトは絶対パスで指定するのが安全。
- tickのクラッシュ後の再判定: エージェントのexit codeは永続化されているため、判定の途中でtickが落ちても、次のtickが同じ入力で判定をやり直すだけで復旧する。判定コマンドは同じ入力に対して繰り返し実行され得ることを前提に、冪等に書く。
- エージェントが異常終了(シグナル死等)した場合の `EXIT_CODE`: 非0の数値として符号化されて渡される。判定コマンド側でexit codeの値を細かく解釈する場合は、この符号化値も非0として扱えばよい。
