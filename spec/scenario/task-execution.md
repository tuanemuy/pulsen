# シナリオ: タスクの登録と自動進行

利用者はワークフローと対象を指定してタスクを登録し、以降はtickの定期実行に任せてタスクを自動で進行させる。要件は [../requirements.md](../requirements.md) を参照。

コマンドのフラグ構文やメッセージの詳細はPhase 2で確定する。ここでは利用者から観測できる流れを記述する。

## タスクを登録する

### 目的

自動化したい作業(ワークフロー)と対象(リポジトリ・ベースブランチ)を指定してタスクを投入し、以降の進行をツールに任せる。

### 前提

- グローバル設定(`config.yaml`)とワークフロー定義(`workflows/implement.yaml` 等)が配置済み
- 外部スケジューラーによる `tick` の定期実行が仕込まれている
- 対象リポジトリがローカルに存在する

### フロー

1. 利用者が `add` でワークフロー名(例: `implement`)と対象(リポジトリパス・ベースブランチ)を指定する。開発・検証用にはワークフロー名の代わりにYAMLのファイルパスを直接指定してもよい。
2. ツールはワークフロー定義を解決し、その時点の内容をタスク側へスナップショットする。以降このタスクは元YAMLの編集の影響を受けない。
3. タスクがタスクIDを付与され、タスクステータスはワークフローの `initial:`、実行状態は `pending` で登録される。タスクIDが利用者に表示される。
4. `add` はここで終了する。実行は行われず、次のtickがこのタスクを拾う。次回の定期tickを待たずに開始したい場合は、続けて手動で `tick` を実行する(登録専用の即実行機構はない。tickは排他ロックで多重実行が防がれるため、定期tickと同時刻でも安全に実行できる)。
5. 利用者は `ls` で、登録したタスクが待機中であることを確認できる。

### 異常系・エッジケース

- 存在しないワークフロー名を指定した場合、`workflows/` 配下に解決できないため登録はエラーで失敗する。タスクは作られない(スナップショットは登録時に行うため、解決不能は登録時点で判明する)。
- ファイルパス指定でYAMLが存在しない・パースできない場合も同様に登録時にエラーとなる。
- 存在しないリポジトリパスを指定した場合、登録時の検証で検知され、登録はエラーで失敗する。タスクは作られない(ワークフロー解決と同様、不正は登録時点で判明する)。登録後にリポジトリが失われたケースはこの検証では防げず、worktree作成の失敗(後述の自動進行シナリオの異常系)として表面化する。
- 存在しないベースブランチを指定した場合も同様に、登録時の検証で検知され、登録はエラーで失敗する。タスクは作られない。登録後にブランチが削除されたケースはこの検証では防げず、worktree作成の失敗として表面化する。
- 同一対象・同一ワークフローのタスクが既に存在しても、登録は拒否されない(重複排除はツールの責務外。後述の並行実行シナリオを参照)。

## tickによるタスクの自動進行(登録から完了まで)

### 目的

登録したタスクが、人手を介さずワークフロー定義のステータス遷移に沿って最後まで進むことを確認する。

### 前提

- ワークフロー例(§7の `implement`): `queued`(plan) → `planned`(implement) → `implemented`(セルフレビュー) → `done`(クリーンアップ)
- タスクが `queued` / `pending` で登録済み
- 外部スケジューラーが定期的に `tick` を呼んでいる

### フロー

1. 最初のtickがpendingのタスクを検出し、タスクIDから決定的に生成されたパス・ブランチ名でworktreeを作成する。ワークスペース(worktreeパス・ブランチ)はタスクファイルに保存され、以降の全ステータスで同じworktreeが実行対象となる。
2. tickは現在のタスクステータス `queued` に定義されたエージェント実行(スキル `plan`、ワークフローデフォルトのエージェント・モデル)をデタッチ起動する。実行状態は `launching`(起動記録済み)となり、後続のtickが起動の確認を経て `running` へ進める。tick自身はエージェントの終了を待たずに終了する。
3. エージェントはworktree内で自律的に作業する。ツールは内部処理に関与せず、標準出力・標準エラーはrunディレクトリのログに記録される。利用者は `show` やログでいつでも様子を確認できる。
4. エージェントが終了すると、以降のtickがそれを観測して判定する。判定はステータスに判定コマンドが定義されていなければexit codeによる(0 = completed、非0 = failed)。
5. tickが completed と分類すると、以降のtickがタスクステータスをYAML定義の次ステータス `planned` へ遷移させ、実行状態を実行待ちに戻す。
6. さらに以降のtickが `planned` に定義された実行(スキル `implement`、モデル上書きあり、timeout 30m)を同じworktreeで起動する。各実行は独立した新規セッションであり、前段のコンテキストは引き継がれない。ステータス間で受け渡されるのはworktreeに残された成果(コード・ファイル)のみである。
7. 同様に `implemented`(プロンプト実行)を経て、completedのたびに次ステータスへ進む。
8. クリーンアップ動作の `done` に到達すると、tickがworktreeを削除し(ブランチは残る)、タスクファイルをアーカイブへ移す。以降このタスクはtickの走査対象から外れ、`ls --all` で参照できる。
9. 利用者から見れば、登録後は何もしなくても、tickのたびに `ls` 上のタスクステータスが進んでいき、最終的に成果物のブランチが残る。

### 異常系・エッジケース

- worktree作成の失敗(パス衝突・git異常・登録後にリポジトリが失われた・登録後にベースブランチが削除された等): failed相当としてattempt_countを消費し、次のtickで再試行される。失敗はタスクに記録され、利用者が `show` で原因を確認できる。リトライ上限超過でstoppedとして凍結され、通知される(自動リトライのシナリオと同じ経路)。
- 進行中のworktreeの手動削除・消失: ワークスペースは最初の実行時に確定・保存され、ツールはworktreeを再作成しない。以降の実行は存在しないワークスペースを対象に失敗を繰り返し(失敗の現れ方はエージェント・コマンドテンプレートに依る)、リトライ上限超過でstoppedとして凍結され、通知される。タスクは復旧できないため、`set-status` でクリーンアップ動作のステータスへ手動遷移させてアーカイブし(worktreeが既に存在しない場合の削除は達成済み扱い)、やり直すなら新規に `add` する。ブランチはworktree削除後も残るため、コミット済みの成果は回収できる。
- エージェント起動(spawn)の失敗: 起動が確認できないまま猶予時間を超えると実行待ちに戻され、次のtickで再起動される。一過性の失敗であれば、利用者には一時的な遅延として見えるだけで、二重起動は起きない。
- spawn失敗の恒久化(エージェントのコマンドパス誤り等、設定起因の失敗): 連続spawn失敗のカウンタ(spawn_fail_count)が上限(デフォルト3)を超えると、タスクはstoppedとして凍結され、通知される(設定の不具合は再試行では解決しないため)。カウンタは起動が確認されるとリセットされる。利用者は通知と `show` で失敗に気づき、設定を修正してから `retry` で再開する。
- timeout超過: ステータスのtimeout(未指定ならデフォルト1h)を超えても終了しない実行は、tickがプロセスグループ相当の単位ごとkillし、failedとして扱う(自動リトライのシナリオへ)。`timeout: none` を明示したステータスでは無制限となる。
- 判定コマンドの失敗: 判定コマンドが0でも10でもないexit codeで終了した(または判定timeoutを超えた)場合、「判定自体が壊れた」として再判定される。再判定上限(デフォルト3)を超えるとリトライせずstoppedとなり通知される(エージェントの再実行では解決しないため)。
- 判定コマンドが10で終了した場合は通常のfailedであり、自動リトライの対象となる。
- 「何もしない」動作のステータス(レビュー待ち等)に到達した場合、tickはそのタスクに対して何もしない。進行は人間の `set-status` による(介入カテゴリのシナリオ)。
- tick自体のクラッシュ: どの時点で落ちても、次のtickが永続化された事実(タスクファイル・runディレクトリ・プロセス生存)から同じ判断を再導出して復旧する。利用者による修復操作は不要。
- パース不能なタスクファイル: tickは読めないタスクファイルをスキップして残りのタスクの処理を続行し、破損したファイルへの書き込み(stopped化を含む)は行わないため、通知も発生しない。他のタスクの進行には影響しない。破損には `ls` / `show` の報告で気づき、修復はタスクファイルの直接閲覧・修復のシナリオ(monitoring.md)による。

## 同一対象に複数のタスクを並行して走らせる

### 目的

同じリポジトリに対する複数の作業(別々のIssue対応等)を、互いに干渉させず同時に進める。

### 前提

- ワークフロー定義済み、tick定期実行中
- 同一リポジトリ・同一ベースブランチを対象とする作業が複数ある

### フロー

1. 利用者が同じリポジトリ・ベースブランチを対象に、`add` を複数回実行する(ワークフローは同一でも異なってもよい)。
2. ツールは重複排除を行わず、すべて独立したタスクとして登録する。
3. tickは実行可能なタスクをすべて起動する(並列度制御は行わない)。各タスクにはタスクIDから決定的に生成された別々のworktree・ブランチが割り当てられるため、作業ディレクトリが衝突することはない。
4. 各タスクは独立に進行し、それぞれのブランチに成果を残す。利用者は `ls` で全タスクの進行を並べて確認できる。

### 異常系・エッジケース

- 同一対象・同一ワークフローのタスクを誤って二重登録しても、ツールは検知・排除しない。両方が最後まで走り、2つのブランチが残る。不要なタスクは人間が `abort` で実行を止める(タスクはstoppedとして残り、通知が発火する)。片付けるには、abort後(pendingなら直接)に `set-status` でクリーンアップ動作のステータスへ遷移させ、次のtickにアーカイブさせる(介入・終端処理カテゴリのシナリオを参照)。
- 並行数が多い場合の負荷制御はツールの責務外。tickは実行可能なものをすべて起動するため、絞りたければ利用者が投入量を調整する。
- 成果ブランチ同士のコンフリクトはツールの関知外である(マージ・PR作成はツール外の作業。終端処理カテゴリのシナリオを参照)。

## 失敗したエージェント実行が自動リトライで回復する

### 目的

一過性の失敗(エージェントの一時的なエラー、timeout、OOM、マシン再起動等)を人手なしで回復させ、恒久的な失敗だけを人間へエスカレーションする。

### 前提

- タスクが自動進行中
- あるステータスのエージェント実行が失敗する(exit code非0、timeout kill、プロセス死亡のいずれか)

### フロー

1. tickが実行の失敗を観測し、failedと分類する。失敗の観測は次のいずれかによる。
   - エージェントが非0のexit codeで終了した(または判定コマンドが10を返した)
   - timeoutを超過し、tickがプロセスグループ相当の単位をkillした
   - exit記録がないままプロセスが死亡していた(OOM・マシン再起動等。exit code不明)
2. failedのタスクはattempt_countを加算し、次のtickで同じステータスのエージェント実行を再起動する。worktreeは前回の状態をそのまま引き継ぎ、ツールによるリセットは行われない。
3. 再実行が成功(completed)すれば、タスクは何事もなかったように次ステータスへ進む。利用者から見れば、`show` の試行回数が増えている以外は通常の進行と変わらない。
4. リトライ上限(ステータス未指定ならデフォルト2)を超えて失敗が続くと、タスクはstoppedとして凍結され、worktreeは保持されたまま通知コマンドが実行される。以降のtickはこのタスクに何も行わず、再開は人間の `retry` / `set-status` による(介入カテゴリのシナリオ)。

### 異常系・エッジケース

- timeout kill後のworktreeは不整合(`index.lock` 等)を含み得る。回復はエージェント実行側の責務であり、必要ならワークフロー設計者がステータスのプロンプト/スキルで回復手順(冒頭の `git reset` 等)を指示しておく。指示がなくエージェントが不整合で失敗し続ければ、リトライ上限超過でstoppedに至り、人間が対応する。
- マシン再起動をまたいだ場合: 再起動後の最初のtickが、実行中だったタスクのプロセス死亡を検出してfailedとし、自動リトライで回復させる。PIDが別プロセスに再利用されていても、起動時刻の照合により誤って「生存」と判定されることはない。利用者に必要な操作はない(外部スケジューラーがtickを呼び続けている限り)。
- タスクステータスは失敗・リトライ・凍結を通じて一切変化しない。ツールがタスクステータスを動かすのはcompletedによる次ステータスへの遷移のみで、失敗の履歴は実行状態とattempt_countに表れる。凍結後に `retry` すればカウンタがリセットされ、同じタスクステータスから再開される。
- stoppedに至る経路は「リトライ上限超過」「判定不能(再判定上限超過)」「連続spawn失敗の上限超過」「人間によるabort」の4つのみである。それ以外の理由でタスクが勝手に凍結されることはない。
