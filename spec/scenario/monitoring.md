# シナリオ: 状態の確認と追跡

利用者はタスクを投入したあと、tickによる自動進行を前提に、必要なときだけ状態を確認する。確認できる情報は要件の状態モデル(requirements §6, §9)に基づく。

- タスクステータス: ワークフローYAMLでユーザーが定義した状態(例: queued / planned / implemented)
- 実行状態: ツールが固定管理する pending / launching / running / completed / failed / stopped
- 実行メタデータ: attempt_count、judge_attempt_count、spawn_fail_count(連続spawn失敗カウンタ)、worktreeパス(workspace_path)、ブランチ、現在attemptのrunディレクトリパス、notified_at、更新日時
- スナップショットされたワークフロー定義: タスク登録時に固定された定義(定義済みタスクステータスの一覧を含む。requirements §7.1)
- 実行の成果: runディレクトリ(`state/runs/<task-id>/attempt-<n>/`)の `stdout.log` / `stderr.log` / `exit`

## タスク一覧とステータス絞り込み

### 目的

走らせている複数タスクの全体像を把握し、注意が必要なタスク(失敗・凍結・滞留)を素早く見つける。

### 前提

- 複数のタスクが登録済みで、それぞれ異なるワークフロー・タスクステータス・実行状態にある
- tickが外部スケジューラーで定期実行されている

### フロー

1. 利用者が `ls` を実行する。
2. ツールは `state/tasks/` を走査し、各タスクについて少なくともタスクID・ワークフロー名・対象・現在のタスクステータス・実行状態・更新日時が判別できる一覧を返す。
3. 利用者はタスクステータスと実行状態の両方を手がかりに読む。同じタスクステータス(例: planned)でも、実行状態が pending(次tick待ち)、running(起動確認済み。終了・判定待ちを含む)、stopped(凍結)では意味が異なるため、両方が一覧上で区別できる。
4. 注意が必要なタスクに絞りたい場合、利用者はステータスでフィルタする(例: stopped のみ、特定のタスクステータスのみ)。タスクステータスはユーザー定義、実行状態は固定の6値であり、いずれでも絞り込める。
5. 絞り込み結果からタスクIDを特定し、詳細確認(`show`)やログ確認へ進む。

### 異常系・エッジケース

- タスクが1件もない: 空の一覧を返して正常終了する。エラーにしない。
- アーカイブ済みタスク: 既定では表示されない(`state/archive/` は走査対象外)。`--all` を付けたときのみアーカイブ済みも含めて表示される。アーカイブ済みであることが判別できる。
- 存在しないタスクステータス名でフィルタ: タスクステータスはワークフローごとのユーザー定義であり、ツールは名前の正当性を検証できない。該当0件として空の一覧を返す(typoかどうかの判断は利用者に委ねる)。
- 壊れたタスクファイルが混在: 走査中にパース不能なファイルがあっても一覧全体を失敗させない。当該ファイルを読み取り不能として報告しつつ、残りのタスクは表示する(直接修復のシナリオへ続く)。
- tickと同時に実行: `ls` / `show` は読み取り専用でロックを取得しない(requirements §10)。タスクファイルの更新はアトミック置換で行われるため書きかけの内容を観測することはなく、一覧が中途半端な状態を表示することはない。

## タスク詳細の確認

### 目的

特定のタスクについて「いまどこにいて、何を対象に、どんな履歴で動いているか」を確認する。worktreeの場所やブランチ名を知り、成果物を直接見に行く起点にもする。

### 前提

- 一覧・通知などからタスクIDが分かっている

### フロー

1. 利用者が `show <task-id>` を実行する。
2. ツールはタスクファイルの内容に基づき、少なくとも次を表示する。
   - ワークフロー名と対象(リポジトリ・ベースブランチ等)
   - 現在のタスクステータスと実行状態
   - workspace_path(worktreeパス)とブランチ名
   - attempt_count / judge_attempt_count / spawn_fail_count(連続spawn失敗カウンタ)と、それぞれの上限(スナップショットされた定義とグローバル設定に基づく)
   - スナップショットされたワークフロー定義に定義済みのタスクステータス一覧(set-status の遷移先はこのスナップショットを基準に検証されるため、手動遷移の前の確認に使う)
   - 現在attemptのrunディレクトリパス(ログ確認の起点)
   - stopped の場合: 凍結要因の記録(直前実行の終了情報・最終出力への参照)と notified_at
   - 更新日時
3. 利用者は表示された worktreeパスへ移動して成果物を直接確認したり、runディレクトリパスからログ確認へ進んだりする。
4. running のタスクでは、実行メタデータ(PID・starttime・runディレクトリ)から「どのattemptが動いているか」が特定できる。

### 異常系・エッジケース

- 存在しないタスクID: 「見つからない」ことを明確に示すエラーで終了する。似たIDの列挙などの補助は必須ではないが、無言で空を返さない。
- アーカイブ済みタスクのID: `state/tasks/` にはないが `state/archive/` には存在する。詳細を表示できること。worktreeは削除済みのため、workspace_path は「削除済み」であることが分かる形で示す(ブランチは残っている。requirements §9.1)。
- まだ一度も実行されていないタスク(pending・attempt 0): workspace_path・ブランチは未確定(最初の実行時に確定する。requirements §5)。runディレクトリも存在しない。未確定・未実行であることをそのまま表示し、エラーにしない。
- launching のタスク: pidファイル取り込み前でPID・starttimeがタスクファイルに未反映の場合がある。「起動記録済み・spawn確認未了」という状態として表示する。
- タスクファイルが壊れている: パースエラーの内容とファイルパスを示して失敗する。利用者はタスクファイルを直接開いて修復できる(後述のシナリオ)。

## エージェント実行ログの確認

### 目的

エージェントが実際に何を出力したかを確認する。進行中タスクの様子見と、終了済み実行の検分の両方に使う。

### 前提

- 対象タスクのIDが分かっている
- ログは worktree ではなく `state/runs/<task-id>/attempt-<n>/` にある(requirements §9.2)

### フロー

1. 利用者が `show <task-id>` で現在attemptのrunディレクトリパスを得る。
2. runディレクトリ内の `stdout.log` / `stderr.log` を閲覧する。ラッパーがリダイレクトした生の出力であり、ツールによる加工はない。
3. `exit` ファイルで終了結果を確認する。exit codeが数値で永続化されている(シグナル死等も非0の数値として符号化。requirements §4.1)。`exit` がまだ無ければ実行は未終了である。
4. 過去のattemptを見たい場合は、attempt番号違いのディレクトリ(`attempt-<n>`)を辿る。attempt番号がパスに含まれるため、リトライを跨いだ試行同士が混ざらない。

### 異常系・エッジケース

- まだ一度も実行されていないタスク: runディレクトリ自体が存在しない。「実行履歴なし」として扱い、エラーとしない(pendingのタスクにログはない、が自然な答え)。
- 実行中タスクのログ追跡: エージェントは実行中でもログへ書き続けるため、`tail -f` 等で追跡できる。ツールは監視プロセスを持たないので、リアルタイム性はファイルを見る側の手段に依存する。`exit` が現れた時点で実行終了と分かる。
- exitファイルなし・プロセスも死亡している場合: ログは途中で途切れて見える。次のtickが「プロセス死亡」として failed に分類する(requirements §6.1)ので、ログだけで判断せず `show` で実行状態を併読する。
- 空のログ: エージェントが何も出力せず終了した場合、ログファイルは空または存在し得る最小限となる。異常とは限らない(`exit` と判定結果で判断する)。
- spawn失敗でpendingへ戻ったattempt: runディレクトリに無効化マーカーが残り、pid・exitが揃わないまま放置されている場合がある。これは失敗した起動試行の痕跡であり、最新のattempt番号のディレクトリと取り違えないこと(タスクファイルが指す現在attemptのパスを起点にすれば混同しない)。
- 判定コマンドを使うワークフロー: 判定コマンドには `RUN_DIR` が渡される(requirements §6.3)。判定結果に疑義があるとき、利用者は同じrunディレクトリを見て判定コマンドの入力(exit・ログ)を再現的に確認できる。

## stoppedタスクの原因調査

### 目的

凍結(stopped)したタスクについて、なぜ止まったのかを特定し、retry / set-status / abort後の修正といった次の行動を決める。

### 前提

- stopped確定時の通知を受けた、または `ls` で stopped のタスクを見つけた
- stopped に至る経路は「リトライ上限超過」「判定不能(再判定上限超過)」「連続spawn失敗の上限超過」「人間によるabort」の4つのみ(requirements §6.4)

### フロー

1. 利用者が `show <task-id>` を実行する。
2. タスクファイルに記録された凍結要因(直前実行の終了情報・最終出力への参照。requirements §8)から、4経路のどれで止まったかを判別する。
   - attempt_count がリトライ上限を超過している → 実行失敗の繰り返し
   - judge_attempt_count が上限を超過している → 判定自体の不能(環境・定義の不具合の疑い)
   - spawn_fail_count が上限を超過している → エージェント起動自体の失敗(設定・環境起因の疑い)
   - abort の記録 → 自分または他の操作による中断
3. 実行失敗が原因なら、最終attemptのrunディレクトリの `stderr.log` / `stdout.log` / `exit` を読み、失敗の中身(エージェントのエラー、timeout kill、プロセス死亡など)を確認する。timeout killやプロセス死亡では `exit` が存在しない場合があり、それ自体が手がかりになる。
4. 判定不能が原因なら、判定コマンドの定義(スナップショットされたワークフロー定義)とグローバル設定を確認する。エージェントの再実行では解決しないため、定義・環境を直す(requirements §6.3)。
5. 連続spawn失敗が原因なら、最終attemptのrunディレクトリを確認する。無効化マーカーが残り pid・exit が揃っていない(ラッパーの起動に至っていない)ことが手がかりになる(requirements §4.1)。エージェントの再実行では解決しないため、エージェント名の解決・テンプレート展開・ツールバイナリの起動環境といった設定を直してから再開する(エージェント実体のコマンドパス誤りはspawn失敗ではなくfailed経路(exit 127等)に現れる。requirements §4.1)。
6. 必要に応じて worktree(workspace_path)を直接開き、成果物の状態(中途半端な変更、`index.lock` 等の残骸)を確認する。stoppedのworktreeは自動削除されないため、現場がそのまま残っている(requirements §5)。
7. 原因に応じて介入する: 一過性の失敗なら `retry`、ワークフロー上の別の地点からやり直すなら `set-status`、放棄するならクリーンアップ相当のステータスへ手動遷移する(介入の詳細は intervention.md)。
8. notified_at を確認し、通知が届いているか(at-least-onceの再通知が機能しているか)を検証できる。

### 異常系・エッジケース

- 複数attemptにまたがる失敗: attempt-1 から順にログを辿ると、毎回同じ失敗か・失敗の質が変わっているかが分かる。リトライはworktreeを引き継ぐため、attempt間で状況が悪化している(前回の残骸が次を壊している)ケースを識別できる。
- 通知が来ていないのに stopped: notified_at が無ければ次tickで(再)通知されるはずである。tickが動いているのに notified_at が付かない場合は notify_cmd の失敗が疑われる(通知コマンドの修正はセットアップの領域)。
- ログを見ても原因が分からない: エージェントの内部処理はツールの関知外であり、ログが不十分ならプロンプト/スキル側でログ出力を改善するのがワークフロー設計上の対処になる。
- stopped だがプロセスが残っている疑い: ラッパーのみ死亡した孤児エージェントは、誤殺なく同定できない場合に残存し得る(requirements §6.2)。タスクファイルのPID・starttimeを手がかりに、利用者がOSのツールで確認・後始末する。
- タスクファイルの記録自体が壊れている・矛盾している: 次のシナリオ(タスクファイルの直接閲覧・修復)で対応する。

## タスクファイルの直接閲覧・修復

### 目的

タスクファイルの記録をエディタで直接確認し、破損・不整合があれば修復して通常の自動進行へ復帰させる。タスクファイルは人間可読であり、直接の閲覧・修復が可能である(requirements §9)。

### 前提

- `show` や `ls` がパースエラーを報告した、または記録内容に矛盾がある(例: クラッシュ時の不整合)
- タスクファイルの場所は `state/tasks/<task-id>.json`(アーカイブ済みなら `state/archive/`)

### フロー

1. tickの書き込みが起きないタイミングを作る。CLI操作とtickは同一の排他ロックの下で書き込むが、エディタでの手動編集はこのロックの外で行われるため、同時に走ると更新が失われ得る。外部スケジューラーを一時停止する、実行中(launching / running)のタスクなら先に abort する等で確保する。
2. `state/tasks/<task-id>.json` をエディタで開き、内容を確認する。閲覧だけで済む(記録に問題がない)なら、そのまま閉じて終わる。
3. 必要な箇所を修正して保存する。
4. `show <task-id>` で読めることを確認し、次のtickに委ねる。tickは永続化された事実から判断を再導出する(冪等)ため、ファイルが正しければ通常の進行に復帰する。
5. 外部スケジューラーを止めていた場合は再開する。

### 異常系・エッジケース

- tickやCLI操作と同時に手で書き換えた: ロック外の書き込みであり、tick側のアトミック置換に上書きされて更新が失われ得る。失われた場合は、tickが走っていないタイミングを確保し直して修復をやり直す。
- 閲覧のみの場合: 読み取りは書き込みと競合しない。タスクファイルの更新はアトミック置換で行われるため、tickと同時に開いても書きかけの内容を観測することはない。
- 修復した内容が依然として不正(パース不能、未知の実行状態名等): 次の `show` / tick が再びエラーを報告する。壊れたタスクファイルが混在しても `ls` は一覧全体を失敗させないため、他のタスクの進行には影響しない。
- 修復のしようがないほど壊れている: タスクを復元せず放棄する判断もある。worktree・ブランチ・runディレクトリはタスクファイルとは独立に残っており、成果の回収やログの調査はタスクファイルなしでも行える。
- アーカイブ済みタスクファイルの修復: 同様に直接扱えるが、`state/tasks/` へ手で戻す操作は想定しない(終端処理カテゴリのシナリオを参照)。
