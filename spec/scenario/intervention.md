# 人間の介入と復旧

利用者は、自動進行に任せられなくなったタスク(凍結・暴走・判断待ち)に対して、通知の受信・中断(abort)・再試行(retry)・手動遷移(set-status)で介入する。ツールがタスクステータスを変更するのは「completed による次ステータスへの遷移」と「人間による手動遷移」のみであり、本カテゴリのシナリオはすべて後者と、その前後の観測・復旧の流れを扱う。

kill と遷移を一度に行う複合操作は存在しない。実行中タスクへのあらゆる介入は abort → set-status → retry の組み合わせで表現する。

## stopped確定の通知を受け取る

### 目的

タスクが凍結(stopped)したことを、tickを見張らなくても確実に知る。

### 前提

- グローバル設定 `config.yaml` に通知コマンド(`notify_cmd`)が定義されている(例: デスクトップ通知やチャットへの投稿を行うスクリプト)。
- 外部スケジューラーによる `tick` の定期実行が仕込まれている。
- あるタスクが stopped に至る経路のいずれかを踏む: 各種上限超過(リトライ・判定失敗・spawn失敗)、または人間による abort。

### フロー

1. tickがタスクを stopped と確定する(または利用者が abort する)。処理順序は「stopped をタスクファイルへ書く → notify_cmd を実行する → `notified_at` を追記する」。凍結に至った要因(直前実行の終了情報・最終出力への参照)もタスクファイルに記録される。
2. notify_cmd が実行され、利用者が通知を受け取る。通知手段の中身(デスクトップ・チャット等)はツールの関知外で、コマンドはシェルを介さず直接起動される。
3. 利用者は `ls` で stopped のタスクを絞り込み、`show <task-id>` で凍結要因と実行メタデータ(exit code・runディレクトリ・最終出力への参照)を確認する。
4. runディレクトリの `stdout.log` / `stderr.log` を読み、原因(エージェントの失敗・timeout kill・判定コマンドの不具合など)を特定する。worktree は凍結後も保持されているため、作業ツリーの中身を直接確認できる。
5. 原因に応じて、後続のシナリオ(retry / set-status / 放置してクリーンアップ方針の検討)へ進む。

### 異常系・エッジケース

- notify_cmd 自体が失敗した(または通知前にツールがクラッシュした)場合、`notified_at` は書かれない。次のtickが「`notified_at` のない stopped タスク」を検出して再通知するため、通知は at-least-once で保証される。利用者が特別な操作をする必要はない。
- notify_cmd 実行後・`notified_at` 追記前にクラッシュすると、同じタスクについて通知が二重に届く。これは仕様上許容される(欠落よりも重複を選ぶ)ため、利用者は同一タスクIDの重複通知を無視してよい。
- notify_cmd が未設定の場合、stopped は通知されない。`ls` での定期確認が代替手段となるため、無人運用では notify_cmd の設定を前提とする(セットアップシナリオ参照)。
- 通知は stopped 確定時のみ発生する。failed からの自動リトライ中は通知されず、リトライ上限を超えて stopped になった時点で初めて届く。

## 実行中のタスクを中断する(abort)

### 目的

暴走・見込み違い・優先度変更などの理由で、実行中のエージェントを直ちに止め、タスクを凍結する。

### 前提

- 対象タスクの実行状態が stopped・アーカイブ済み以外(pending / launching / running / failed / completed)である。killを伴うのはプロセスが存在する場合(launching / running)のみで、kill対象のない実行状態へのふるまいは異常系・エッジケースに記す。
- 利用者は `ls` / `show` でタスクIDと実行状態を確認済み。

### フロー

1. 利用者が `abort <task-id>` を実行する。CLI操作はtickと同一の排他ロックを取得するため、進行中のtickと競合しない。
2. ツールはタスクファイルに記録済みのkill同定子と starttime を用い、PIDの実起動時刻と照合したうえでプロセスグループ相当の単位をkillする。照合が不一致(PID再利用)なら対象はすでに死んでいるとみなし、killしない。
3. タスクファイルへ即座に stopped を記録する。次のtickを待たず、CLI操作自体が確定させる。
4. stopped 確定なので通知フローが動く(前シナリオ)。worktree はそのまま保持され、中断時点の作業状態を後から確認・再開できる。
5. 利用者は必要に応じて retry / set-status で再開するか、クリーンアップ方針を判断する。

### 異常系・エッジケース

- 存在しないタスクIDを指定した場合、エラーを返して何も変更しない。
- すでに stopped のタスクへの abort は、killすべきプロセスが存在しないため状態を変えずにその旨を伝える(すでに凍結済みであることが結果として満たされているため、失敗扱いにする必要はない)。
- アーカイブ済みタスクへの abort は、走査対象外のタスクとしてエラーになる。
- launching 中(pidファイル未出現)の abort: 当該attemptのrunディレクトリへ無効化マーカーを書き、pidファイルを再確認する。なお存在しなければタスクファイルを直接 stopped に書き換える(遅れて起動したラッパーはpid書き込み後のマーカー確認で自ら終了するため、凍結後にエージェントが走り出すことはない)。再確認でpidファイルが現れていれば、通常どおり照合付きでkillして stopped とする。
- pending のタスクへの abort は、kill対象が存在しないため、プロセス操作なしで stopped を記録するのみとなる。次のtickによる起動を止めたい場合に使う。
- failed のタスクへの abort も同様に stopped の記録のみとなる。failed は放置すれば次のtickで自動リトライされるため、これ以上リトライさせずに凍結したい場合に使う。
- completed のタスクへの abort も同様に stopped の記録のみとなる。次のtickによる次ステータスへの遷移を打ち切りたい場合に使う。
- killの照合が不一致だった場合(エージェントは既に死亡し、PIDが別プロセスに再利用されていた)、無関係なプロセスは殺さず、stopped の記録のみ行う。
- timeout による自動kill(failed → リトライ)と人間の abort(→ stopped)は別物である。リトライさせたくない実行を止めるのは abort であり、timeout を待っても凍結にはならない(上限内ならリトライされる)。

## 凍結したタスクを再試行する(retry)

### 目的

一過性の要因(レート制限・ネットワーク断・マシン再起動など)で凍結したタスクを、同じタスクステータスからもう一度自動進行に戻す。

### 前提

- 対象タスクが stopped である。
- 利用者は `show` とログで原因を確認し、「同じ定義のまま再実行すれば通る見込み」と判断した。

### フロー

1. 利用者が `retry <task-id>` を実行する。
2. ツールは attempt_count・judge_attempt_count・spawn_fail_count をリセットし、実行状態を pending に戻す。タスクステータスは変更しない。
3. 次のtickが pending のタスクとして拾い、現在のタスクステータスに定義されたエージェント実行を新しいattempt番号で起動する。
4. worktree は前回の状態をそのまま引き継ぐ。エージェントは前回までの成果(途中までのコード・コミット)の上で作業を続行する。
5. 以降は通常の自動進行(観測 → 判定 → completed / failed)に合流する。

### 異常系・エッジケース

- 存在しないタスクIDへの retry はエラーを返して何も変更しない。
- retry を受理するのは stopped のタスクのみで、それ以外の実行状態への retry はすべて拒否する。failed には「放置すれば次のtickで自動リトライされる」、pending には「既に実行待ちである」と案内する(completed は次ステータスへの遷移待ちであり、同様に拒否する)。
- launching / running のタスクへの retry も拒否し、先に abort するよう案内する(実行中プロセスと新attemptの並走を避けるため。set-status と同じ原則)。
- 恒常的な原因(壊れたプロンプト・環境不備)のまま retry すると、再びリトライ上限まで失敗して stopped に戻る。通知が再度届くため、無限ループにはならない。
- 判定不能で凍結したタスクの retry は judge_attempt_count もリセットするが、判定コマンドの不具合が直っていなければ再び凍結する。ワークフロー定義はタスク登録時のスナップショットで固定されており既存タスクへ定義変更を適用する操作はないため、修正はスナップショットが参照するコマンドの実体(スクリプトファイル等)側で行うか、修正済み定義でタスクを登録し直す。
- 連続spawn失敗の上限超過で凍結したタスクも retry で復旧できる。原因(エージェント定義のコマンドパスの誤りなど)を直してから retry すると、spawn_fail_count がリセットされ、pending から新しいattemptで再起動される。エージェント定義を含むグローバル設定は各実行時に解決されるため、ワークフロー定義と異なり修正がそのまま既存タスクに効く。原因を直さないまま retry すると、再び上限まで数えて stopped に戻る。
- timeout kill 後の worktree は `index.lock` 等の不整合を含み得る。ツールはリセットしないため、回復が必要なワークフローではステータスのプロンプト/スキル側に回復手順(冒頭での `git reset` 等)を含めておく。含めていなかった場合、retry 後の実行が不整合で失敗し得る。
- retry 直後・tick前に abort すれば、起動前に再度凍結できる(pending への abort)。

## タスクステータスを手動で遷移させる(set-status)

### 目的

凍結したタスクを別のステータスからやり直す、あるいは自動判定に任せられない遷移を人間の判断で行う。

### 前提

- 対象タスクが launching / running 以外(stopped、pending、「何もしない」ステータス滞留中など)である。
- 遷移先のステータス名は、そのタスクにスナップショットされたワークフロー定義に存在する。

### フロー

1. 利用者が `show <task-id>` で現在のタスクステータスと、スナップショットされたワークフローのステータス一覧を確認する。
2. `set-status <task-id> <status>` を実行する。CLI操作はtickと同一のロック下で行われる。
3. ツールはタスクステータスを指定のステータスへ書き換え、遷移先の動作種別によらず一律に attempt_count・judge_attempt_count・spawn_fail_count をリセットし、実行状態を pending にする(stopped だった場合は凍結が解ける。retry と対称の一律規則)。新しいステータスの定義に従って次のtickから動作させる(エージェント実行のステータスなら起動される。「何もしない」ステータスなら pending のまま滞留する。クリーンアップのステータスなら終端処理される)。
4. worktree・ブランチは同一のものを引き継ぐ。遷移先ステータスのエージェントは、これまでの成果が残った作業ツリーの上で実行される。

代表的な組み合わせ:

- stopped から前のステータスへ戻してやり直す: `set-status` のみ(例: 実装ステータスで凍結 → 計画ステータスへ戻して計画から再実行)。
- 実行中タスクを別ステータスへ移す: `abort <task-id>` → `set-status <task-id> <status>`(kill+遷移の複合操作は提供しないため、必ずこの順で行う)。
- 失敗したステータスをスキップして先へ進める: `set-status` で次のステータスを直接指定する。
- 途中のタスクを打ち切って片付ける: `set-status` でクリーンアップ動作のステータスへ遷移させ、次のtickに終端処理させる。

### 異常系・エッジケース

- 存在しないタスクIDへの set-status はエラーを返して何も変更しない。
- launching / running のタスクへの set-status は拒否され、「先に abort せよ」と案内される。実行中プロセスを残したままステータスだけ変わる、という中途半端な状態を作らないための制約である。
- スナップショットされた定義に存在しないステータス名を指定した場合、エラーを返して何も変更しない。判定の基準は登録時のスナップショットであり、`workflows/` の元YAMLをその後編集して追加したステータスは既存タスクでは指定できない。
- stopped のタスクを set-status で動かした場合、遷移先の種別によらず凍結は解かれ、実行状態は pending となる(以後 stopped ではないため retry は拒否される)。遷移先がエージェント実行のステータスなら次のtickから通常どおり実行され、「何もしない」ステータスなら滞留し、クリーンアップのステータスなら終端処理される。同じステータスのままリトライしたいだけなら retry を使う(set-status で同一ステータスを指定し直す必要はない)。
- set-status はタスクステータスの遷移のみを行い、プロセス操作・worktree操作は一切行わない。abort 済みタスクの孤児プロセス残存(同定不能で終了できなかった場合)は set-status では解消されない。

## レビュー待ちステータスから手動で進める

### 目的

ワークフロー上に定義した「何もしない」ステータス(レビュー待ち等)で滞留しているタスクを、人間の確認後に次のステータスへ進める。

### 前提

- ワークフロー定義に「何もしない」動作のステータスが含まれる(例: 実装完了後の `review_waiting`)。これはワークフロー設計者が任意に定義するものであり、ツール固有の機構ではない。
- タスクが自動進行の結果としてそのステータスに到達し、滞留している。tickはこのタスクに対して何もしない。

### フロー

1. 利用者が `ls` で滞留中のタスクを見つける(このステータスへの到達は stopped ではないため通知されない。気づく手段は `ls` での確認か、直前のエージェント実行ステータスにレビュー依頼の送信などの外部連携を組み込んでおくこと)。
2. `show <task-id>` で worktree パスとブランチを確認し、成果物をレビューする(worktree を直接開く・ブランチをローカルで確認するなど、ツール外の作業)。
3. 承認するなら `set-status <task-id> <次のステータス>` を実行する。次のtickが新しいステータスの定義に従って進行を再開する。
4. 差し戻すなら、修正用のステータス(実装ステータス等)を `set-status` で指定する。修正指示の伝達が必要なら、worktree 内にレビューコメントのファイルを残すなど、ワークフロー設計(プロンプト側の取り決め)で表現する。
5. 打ち切るなら、クリーンアップ動作のステータスへ `set-status` する。

### 異常系・エッジケース

- 「何もしない」ステータスのタスクは launching / running ではないため、set-status は拒否されない。abort を挟む必要もない。
- レビュー待ちのまま放置してもツールは何もしない(timeout・自動エスカレーションはない)。滞留の検出は利用者の運用(定期的な `ls`)に委ねられる。
- 遷移先を誤って指定した場合も、tickがまだ動いていなければ set-status で指定し直せる。すでにエージェントが起動(launching / running)していたら、abort → set-status でやり直す。
- レビュー待ちステータスを経由せずに凍結したタスク(stopped)との混同に注意する。stopped は実行状態であり通知される。「何もしない」ステータスでの滞留はタスクステータスであり通知されない。`ls` の表示上も両者は区別される(実行状態とタスクステータスは別の属性)。
